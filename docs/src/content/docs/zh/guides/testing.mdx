SDK 为智能体工作流、沙盒会话和 Realtime 会话提供确定性、与提供方无关的测试替身。它们在内存中运行，不会向模型、沙盒提供方或 Realtime API 发送请求，并会记录 SDK 负责的规范化交互。

<Aside type="note" title="完全离线测试需禁用追踪">
  脚本化工具会替换模型、沙盒提供方和 Realtime API 的 I/O。 追踪是 SDK
  的一个独立边界，除非在测试环境中禁用，否则仍可能导出运行数据。 本页代码示例向
  `new Runner(...)` 传入 `tracingDisabled: true`。您也可以设置
  `NODE_ENV=test`、设置
  `OPENAI_AGENTS_DISABLE_TRACING=1`，或在测试初始化时调用一次
  `setTracingDisabled(true)`。
</Aside>

### 检查模型调用

`ScriptedModel` 会在完成所选步骤或抛出错误之前记录调用。

| 成员             | 内容                                     |
| ---------------- | ---------------------------------------- |
| `calls`          | 按调用顺序排列的所有 `RecordedModelCall` |
| `firstCall`      | 第一次调用，或 `undefined`               |
| `lastCall`       | 最近一次调用，或 `undefined`             |
| `remainingSteps` | 尚未使用的已配置步骤数                   |

每次调用都有一个从零开始的 `index`，与它在 `calls` 中的位置一致，还包含一个 `streamed` 标志和规范化的 `request`。记录请求中的可变数据容器会在调用时复制为独立快照。读取或修改某个返回的快照不会改写模型保留的历史记录。回调、类实例和 `AbortSignal` 等运行时对象则保持对象身份不变。

常见断言包括：

- 使用 `call.request.input` 检查用户输入、工具调用和工具结果
- 使用 `call.request.modelSettings` 检查发送给模型的实际设置
- 使用 `call.request.tools` 和 `call.request.handoffs` 检查已准备好的能力
- 使用 `call.streamed` 区分流式传输和非流式传输路径

### 测试流式传输

常规响应步骤既适用于流式运行，也适用于非流式运行。当 `run(..., { stream: true })` 调用模型时，`ScriptedModel` 会发出规范化的开始事件、助手文本增量，以及包含完整输出和用量的终止响应事件。

自动生成的流事件是独立快照。修改已产出的增量不会改变后续的终止响应事件。

仅当精确的规范化 `StreamEvent` 序列本身属于被测行为时，才使用 `modelStream(events)`。当该序列依赖于记录的调用时，使用 `modelStreamResponder(callback)`。这些事件是 SDK 规范化的事件，而不是 Responses 或 Chat Completions 的线上传输分块。

<Aside type="tip" title="大多数工作流测试应优先使用自动流式传输">
  常规 `assistantMessage()` 响应可让测试不依赖底层事件组装。
  仅在测试事件顺序、部分输出、取消或异常流行为时，才使用精确的流。
</Aside>

如果非流式调用使用了原始流步骤，就会抛出 `InvalidScriptedModelStepError`，其中包含 `reason: 'incompatible_call'`。

### 注入模型故障

使用 `modelError(error, retryAdvice?)` 使一次模型调用失败。重试建议可以是固定的 `ModelRetryAdvice` 值，也可以是回调。运行器执行的重试是另一次模型调用，会使用脚本中的下一个步骤。

```text
modelError(error)
modelError(error, { suggested: true, replaySafety: 'safe' })
modelError(error, ({ attempt }) => ({ suggested: attempt === 1 }))
```

上文展示的是签名而非 TypeScript 示例，因为重试建议是否会触发再次尝试，取决于外围运行器的重试策略。

已中止的请求不会使用任何步骤。记录的调用到达中止检查点后，如果请求已中止，就会抛出名为 `AbortError` 的错误，其中包含 `callIndex`。

自定义代码运行期间，取消采用协作方式。`ScriptedModel` 不会让正在执行的 `modelResponder()` 或 `modelStreamResponder()` 回调，或异步迭代器尚未完成的 `next()`，与请求信号进行竞速。可能无限等待的代码必须自行监听 `call.request.signal`，或在迭代器内部监听同一个信号，并随后完成执行。当回调或迭代器交还控制权后，`ScriptedModel` 会在接受响应或发出下一个事件之前再次检查信号。

### 检测工作流偏移

将脚本中的轮次视为预期的工作流结构。下面的测试在两轮订单查询时通过，并在清理阶段执行 `assertComplete()`，因此即使其他断言或工作流本身失败，也会检查脚本。

例如，如果应用代码后来将 `lookup_order` 改为需要审批，运行会在第一个脚本响应之后停止。清理阶段随后会报告一个未使用的步骤。如果编排发生变化，导致在预期步骤之后又发出一次模型请求，模型会在该请求处失败。因此，现有回归测试无需让真实模型推断新路径，就能捕获智能体控制流的变化。

  code={workflowDriftExample}
  title="固定预期的工作流结构"
/>

不要在常规回归测试中捕获这些不匹配错误。应让测试失败，并使用错误类型和字段诊断预期工作流的哪一侧发生了变化。

| 错误 | 结构化字段 | 含义 |
| --- | --- | --- |
| `UnexpectedModelCallError` | `callIndex`、`streamed` | 脚本结束后，工作流又进行了一次模型调用 |
| `UnconsumedModelStepsError` | `remainingSteps` | 工作流在使用完所有步骤之前结束 |
| `InvalidScriptedModelStepError` | `reason`、`inputIndex?`、`callIndex?`、`stepType?` | 步骤格式有误，或与调用模式不兼容 |
| `ScriptedModelRequestAbortedError` | `callIndex?` | 请求在脚本化操作之前或期间被中止 |

构造函数或 `enqueue()` 会在模型调用使用步骤之前拒绝格式有误的步骤封装。这样，配置错误就会在靠近测试定义的位置暴露，而不是在后续工作流中才失败。

此测试跨越 SDK 负责的两个规范化边界。`ScriptedModel` 驱动面向模型的轮次，脚本化沙盒接收真实 shell 能力生成的 `execCommand` 参数。因此，该测试涵盖工具参数验证、能力路由、沙盒会话调用、向下一轮模型调用传递工具结果，以及最终输出处理。

它不测试真实模型是否会选择该命令、沙盒提供方是否能成功启动，或该提供方如何执行命令。请使用评估来检验模型决策质量，并使用真实沙盒提供方的集成测试来检验提供方生命周期、文件系统、进程和隔离行为。

### 配置沙盒步骤

每个步骤对应一次 `SandboxSession` 方法调用。请只选择一种结果，并且仅在参数重要时添加匹配器：

| 步骤成员         | 使用场景                                 |
| ---------------- | ---------------------------------------- |
| `result`         | 方法应返回固定值                         |
| `respond(call)`  | 结果取决于带类型的调用参数或调用索引     |
| `error`          | 方法应抛出指定错误，或以该错误拒绝       |
| `match(...args)` | 测试应在产生结果之前拒绝非预期的方法参数 |

沙盒方法按一个全局顺序匹配，包括 `supportsPty()` 等同步方法和 `execCommand()` 等异步方法。返回的会话只会安装脚本中指定的方法。这可以保留能力检测行为：例如，当工作流应公开交互式 shell 支持时，需要同时为 `supportsPty` 和 `writeStdin` 编写脚本。

`sandbox.calls` 记录调用时的独立参数快照，包含从零开始的 `index`（与每次调用在数组中的位置一致）、`method` 和位置参数 `args`。诊断失败时可使用 `sandbox.remainingSteps`，并在测试结束时调用 `sandbox.assertComplete()`，以免工作流提前退出而悄然留下未使用的预期操作。

| 错误 | 结构化字段 | 含义 |
| --- | --- | --- |
| `UnexpectedSandboxCallError` | `callIndex`、`actualMethod`、`expectedMethod`、`remainingSteps` | 工作流调用了错误的方法，或在脚本结束后继续调用 |
| `SandboxCallMatcherError` | `callIndex`、`method` | 某个步骤的匹配器返回了 `false` |
| `UnconsumedSandboxStepsError` | `remainingSteps`、`pendingMethods` | 工作流在使用完所有步骤之前结束 |
| `InvalidScriptedSandboxStepError` | `reason`、`inputIndex`、`method?` | 步骤格式有误，或指定了不受支持的方法 |

### 测试远端断开连接

调用 `transport.disconnect(error?)` 来模拟远端关闭连接。它会将传输层状态切换为 `disconnected`，发出 `connection_change`，并可选地发出传输层 `error`。

对于连接丢失和远端关闭，使用 `disconnect()`。当应用发起清理，且测试应预期出站 `close` 调用时，使用 `session.close()`。

### 检查 Realtime 调用

`transport.calls` 按调用顺序包含独立快照。可变数组、普通对象和缓冲区会在调用边界处复制，而运行时类实例保持对象身份不变。记录的 `connect` 调用包含 `apiKeyProvided`，但绝不会存储 API 密钥。

常见方法名称包括 `connect`、`sendEvent`、`requestResponse`、`sendMessage`、`addImage`、`sendAudio`、`updateSessionConfig`、`close`、`mute`、`sendFunctionCallOutput`、`interrupt`、`resetHistory` 和 `sendMcpResponse`。导出的方法和调用类型派生自 `RealtimeTransportLayer`，因此新增的传输方法不会悄然从带类型的测试接口中遗漏。

### 验证完成状态和清理

Realtime 测试结束时应执行以下两个断言：

| 断言 | 检查内容 |
| --- | --- |
| `transport.assertComplete()` | 不存在未匹配的调用、尚未完成的预期或未使用的注入故障 |
| `transport.assertClosed()` | 生命周期状态为 `disconnected` |

Realtime 错误还会公开结构化状态：

| 错误 | 结构化字段 |
| --- | --- |
| `UnexpectedRealtimeCallError` | `callIndex`、`expectedMethod`、`actualMethod` |
| `RealtimeCallMatcherError` | `callIndex`、`actualMethod` |
| `IncompleteRealtimeScenarioError` | `unconsumedCalls`、`pendingExpectations`、`pendingFailures` |
| `ScriptedRealtimeScenarioCancelledError` | `pendingExpectations` |
| `RealtimeTransportNotClosedError` | `status` |
| `ScriptedRealtimeConnectionSupersededError` | `operation` |

| --- | --- |

## 正确边界的选择

当测试需要在不依赖模型提供方的情况下检验 SDK 运行循环、工具、交接、护栏、会话、重试或流式传输时，使用 `ScriptedModel`。

当测试需要在不启动沙盒提供方的情况下检验 `SandboxAgent` 的能力与编排时，将 `scriptedSandboxSession()` 与 `ScriptedModel` 配合使用。提供方创建、进程执行、文件系统保真度、持久化和隔离检查应放在针对真实提供方的集成测试中。

当测试需要在不建立 WebRTC 或 WebSocket 连接的情况下检验 `RealtimeSession` 行为，或 `RealtimeAgent` 的工具与交接编排时，使用 `ScriptedRealtimeTransport`。将智能体业务逻辑保留在附加到 `RealtimeAgent` 的工具、交接和护栏中；将连接、历史记录、音频和中断断言保留在会话与传输边界。

不要使用这些测试替身来测试提供方请求转换、HTTP 或 WebSocket 载荷、身份验证标头、提供方特有的流式传输分块，或沙盒提供方生命周期与隔离。模型线上协议测试应保留真实模型适配器并配合模拟网络传输，沙盒集成测试则应使用真实沙盒提供方。

## 最终检查清单

- 仅为规范化模型、沙盒会话或 Realtime 传输边界负责的交互编写脚本。
- 断言重要的请求字段，而不是运行器的私有状态。
- 优先使用固定响应步骤；仅对依赖请求的行为使用响应器。
- 优先使用自动流式传输；仅在事件级行为重要时使用精确的流。
- 模型测试结束时调用 `model.assertComplete()`。
- 沙盒测试结束时调用 `sandbox.assertComplete()`。
- Realtime 测试结束时调用 `transport.assertComplete()` 和 `transport.assertClosed()`。
- 断言结构化错误字段，而不是解析错误消息。
- 提供方线上协议测试应使用真实适配器配合模拟网络传输。

## 范围与当前限制

### 明确排除在测试模块之外的内容

这些工具替换的是 SDK 负责的规范化边界。它们并非用于证明模型或外部提供方负责的行为：

- 模型质量、指令遵循和工具选择质量应通过评估或使用真实模型的测试来检验。
- Responses 和 Chat Completions 请求序列化、身份验证、提供方默认设置、HTTP 行为及提供方流分块，需要使用真实模型适配器配合模拟或受控的网络传输来测试。
- 沙盒启动、进程执行、文件系统保真度、持久化、资源限制、安全隔离和提供方清理，需要使用真实沙盒提供方进行集成测试。
- Realtime 服务器行为、原始 WebSocket 或 WebRTC 帧、音频编码与播放、身份验证和网络恢复，需要真实传输层或集成环境。

脚本化工具不会尝试模拟这些层。在这里添加提供方特有的行为，会让工作流测试依赖于提供方协议的第二套不完整实现。

### 当前未提供的功能

当前测试模块不提供：

- 面向每一种规范化模型输出项的便捷构建器。请对常见助手消息和函数调用使用这些小型辅助函数，并直接传入其他规范化项。
- 高层模拟 Realtime 模型。Realtime 测试会显式匹配出站调用，并发出场景所需的规范化入站事件。
- 无序的沙盒预期。`scriptedSandboxSession()` 按一个全局顺序使用方法步骤。
- 特定于测试运行器的匹配器、测试夹具或自动清理。请使用 Node.js、Vitest、Jest 或其他运行器的断言和清理 API，并显式调用所提供的完成状态和清理断言。
- 用于提供方线上协议测试的模拟传输。在这些测试中，应保留真实提供方适配器，并模拟其网络边界。

这些内容描述的是当前 API 接口范围，并不承诺在未来版本中添加上述缺失功能。
