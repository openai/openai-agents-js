护栏可以与智能体并行运行，也可以阻塞执行，直到自身运行完成，从而对用户输入或智能体输出进行检查和验证。例如，可以在调用高成本模型之前，先运行一个轻量级模型作为护栏。如果护栏检测到恶意使用，就可以触发错误，阻止高成本模型运行。

护栏分为三类：

1. **输入护栏**针对初始用户输入运行。
2. **输出护栏**针对智能体的最终输出运行。
3. **工具护栏**在每次自定义函数工具调用前后运行。

## 工作流边界

护栏附加在智能体上，但不一定会在工作流中的每个智能体上运行：

- **输入护栏**仅在链中的第一个智能体上运行。
- **输出护栏**仅在生成最终输出的智能体上运行。
- **工具护栏**在每次函数工具调用时运行，其中输入护栏在执行前运行，输出护栏在执行后运行。

如果需要在包含管理型智能体或交接的工作流中，对每次自定义函数工具调用进行检查，请使用**工具护栏**，而不是智能体级别的输入护栏和输出护栏。

## 输入护栏

输入护栏分三个步骤运行：

1. 护栏接收与传递给智能体相同的输入。
2. 护栏函数执行并返回一个封装在 [`InputGuardrailResult`](/openai-agents-js/openai/agents/interfaces/inputguardrailresult) 中的 [`GuardrailFunctionOutput`](/openai-agents-js/openai/agents/interfaces/guardrailfunctionoutput)。
3. 如果 `tripwireTriggered` 为 `true`，则抛出 [`InputGuardrailTripwireTriggered`](/openai-agents-js/openai/agents/classes/inputguardrailtripwiretriggered) 错误。

> **注意** 输入护栏用于检查用户输入，因此仅当智能体是工作流中的*第一个*智能体时才会运行。护栏配置在智能体本身上，因为不同的智能体通常需要不同的护栏。

### 执行模式

- `runInParallel: true`（默认值）会在智能体执行的同时并发启动输入护栏。并发执行可最大程度降低延迟，但如果护栏随后被触发，模型可能已经消耗了 token 或调用了工具。
- `runInParallel: false` 会在调用模型**之前**运行护栏，从而在护栏阻止请求时避免消耗 token 和执行工具。如果更看重安全性和成本控制，而非延迟，请使用此模式。

## 输出护栏

输出护栏分 3 个步骤运行：

1. 护栏接收智能体生成的输出。
2. 护栏函数执行并返回一个封装在 [`OutputGuardrailResult`](/openai-agents-js/openai/agents/interfaces/outputguardrailresult) 中的 [`GuardrailFunctionOutput`](/openai-agents-js/openai/agents/interfaces/guardrailfunctionoutput)。
3. 如果 `tripwireTriggered` 为 `true`，则抛出 [`OutputGuardrailTripwireTriggered`](/openai-agents-js/openai/agents/classes/outputguardrailtripwiretriggered) 错误。

> **注意** 输出护栏仅当智能体是工作流中的*最后一个*智能体时才会运行。有关实时语音交互，请参阅[构建语音智能体](/openai-agents-js/zh/guides/voice-agents/build#guardrails)。

输出护栏函数还会接收一个可选的 `details` 对象，其中包含底层的 `modelResponse` 和该轮生成的输出条目。当仅凭最终输出不足以判断响应是否应通过时，可以使用此对象，例如在触发护栏之前检查完整的生成条目列表或提供商响应元数据。

### 被拒绝的最终工具输出

当 `toolUseBehavior` 将已完成的函数工具结果作为本次运行的最终输出时，输出护栏会先评估该结果，然后 SDK 才会将其视为可重放的最终数据。护栏接收的是原始候选输出。如果护栏被触发，SDK 会在其管理的运行状态、重放数据、会话历史和对外暴露的熔断错误中，将被拒绝的最终结果替换为 `Output withheld by an output guardrail.`。

SDK 还会清理可能通过别名引用保留被拒绝输出的元数据。对于当前响应，`OutputGuardrailResult.agentOutput` 会变为相同的占位文本，`OutputGuardrailResult.outputInfo` 则会被移除。当前工具输出护栏的结果会保留判定，但省略 `outputInfo`；`rejectContent` 结果会使用该占位文本作为消息。此前已通过检查的轮次中的结果和历史记录保持不变。

对于能够识别的函数调用与结果对，SDK 会在替换结果内容的同时，保留可安全重放的标识和状态字段。如果 SDK 无法确定当前响应中的哪些条目属于被拒绝的最终输出，就会丢弃当前响应中归属不明的尾部内容，或采取安全阻断策略，而不会重放这些内容。

这项保护不会撤销外部工具的副作用、撤回已发送给应用程序代码的输出、清除已存储在 SDK 控制范围之外的数据，也不会修改应用程序持有的对提供商原始数据的引用。

如果应用程序需要使用不同的不含数据的占位文本，请在 `Runner` 上或单次 `run()` 调用的选项中设置 `outputGuardrailBlockedMessage`。单次运行的值优先于 `Runner` 的值。可以提供非空字符串，也可以提供接收 `defaultMessage`、`guardrailName`、`agent` 和 `runContext` 的格式化函数。该函数可以是异步的，但不会接收被拒绝的输出。如果格式化函数抛出异常、返回的 Promise 被拒绝，或返回空值或非字符串值，SDK 会使用默认占位文本进行安全阻断，而不会暴露格式化函数的错误。

## 工具护栏

工具护栏封装**函数工具**，让你能够在执行前后验证或阻止工具调用。可以通过 `tool()` 选项为单个工具配置护栏，也可以在本地 MCP 服务器上配置护栏，使其针对 SDK 从该服务器转换的每个工具运行。

对于自定义函数工具，请在 `tool({...})` 上设置 `inputGuardrails`、`outputGuardrails` 或同时设置两者。对于 `MCPServerStreamableHttp`、`MCPServerStdio` 或 `MCPServerSSE`，请在服务器构造函数选项中设置 `toolInputGuardrails`、`toolOutputGuardrails` 或同时设置两者。服务器级别的 MCP 护栏使用相同的本地函数工具执行流程，并应用于从该服务器转换的每个工具。

- **工具输入护栏**在工具执行前运行，可以通过返回消息拒绝调用，或抛出熔断错误。
- **工具输出护栏**在工具执行后运行，可以将输出替换为拒绝消息，或抛出熔断错误。

如果本地函数工具还需要人工审批，工具输入护栏通常会在审批通过后、执行前运行。要让这些输入护栏也在发出待审批请求之前运行，请在 `run()` 或 `Runner` 上设置 `toolExecution: { preApprovalInputGuardrails: true }`。审批通过后，护栏仍会在工具执行前再次运行。

工具护栏返回一个 `behavior`：

- `allow` — 继续运行下一个护栏或执行工具。
- `rejectContent` — 通过一条消息提前结束处理（跳过工具调用或替换输出）。
- `throwException` — 立即抛出熔断错误。

工具护栏适用于通过 `tool()` 定义的函数工具，以及从配置了工具护栏的本地 MCP 服务器转换的工具。交接以类似函数的工具形式呈现给模型，但通过 SDK 的交接路径运行，而非普通的函数工具执行流程，因此工具护栏不适用于交接调用本身。托管 MCP 工具、其他托管工具和内置执行工具（`computerTool`、`shellTool`、`applyPatchTool`）也不使用这套护栏流程，且 `agent.asTool()` 目前不直接提供工具护栏选项。

## 熔断机制

当护栏检查未通过时，会通过熔断机制发出信号。运行器会先等待同一批次中启动的其他护栏全部结束，并记录它们已完成的结果。随后，运行器会抛出相应的错误，停止后续运行处理。使用并行输入护栏时，模型调用或工具执行可能已经开始，具体如[执行模式](#execution-modes)中所述。
