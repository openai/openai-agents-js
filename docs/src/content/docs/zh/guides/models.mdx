## 模型选择

### 默认模型

初始化 `Agent` 时，如果没有指定模型，就会使用默认模型。目前的默认模型是 [`gpt-5.6-luna`](https://developers.openai.com/api/docs/models/gpt-5.6-luna)，其配置为 `reasoning.effort: "none"` 和 `text.verbosity: "low"`，适合高效、大规模的智能体工作负载。

如果你想切换到其他模型，例如 `gpt-5.6-sol`，可以通过两种方式配置智能体。

第一种方式，如果你希望所有未设置自定义模型的智能体都使用同一个指定模型，请在运行智能体之前设置 `OPENAI_DEFAULT_MODEL` 环境变量。

```bash
export OPENAI_DEFAULT_MODEL=gpt-5.6-sol
node my-awesome-agent.js
```

第二种方式，可以为 `Runner` 实例设置默认模型。如果没有为智能体设置模型，就会使用此 `Runner` 的默认模型。

## OpenAI 提供方配置

### OpenAI 提供方

默认的 `ModelProvider` 使用 OpenAI API 解析名称。它支持两个不同的端点：

| API | 用途 | 调用 `setOpenAIAPI()` |
| --- | --- | --- |
| Chat Completions | 标准聊天和函数调用 | `setOpenAIAPI('chat_completions')` |
| Responses | 全新的流式传输优先的生成式 API（工具调用、灵活的输出） | `setOpenAIAPI('responses')` _（默认）_ |

#### 提供方选项参考

直接实例化 `OpenAIProvider` 时，以下选项用于控制客户端构建、端点选择和功能验证：

| 选项 | 用途 |
| --- | --- |
| `apiKey` | 提供方创建自己的 OpenAI 客户端时使用的 API 密钥。默认为 SDK 级别的 OpenAI 密钥。 |
| `baseURL` | OpenAI 兼容端点的 HTTP 基础 URL。不能与 `openAIClient` 同时使用。 |
| `websocketBaseURL` | Responses WebSocket 传输的 WebSocket 基础 URL。不能与 `openAIClient` 同时使用。 |
| `openAIClient` | 使用 `openai` 7.2 或更高版本的预配置客户端。不能与 `apiKey`、`baseURL`、`websocketBaseURL`、`organization` 或 `project` 同时使用。 |
| `organization` / `project` | 提供方创建自己的 OpenAI 客户端时传入的组织和项目值。不能与 `openAIClient` 同时使用。 |
| `useResponses` | 为此提供方解析的字符串模型名称选择 Responses API（`true`）或 Chat Completions API（`false`）。默认使用进程级的 `setOpenAIAPI(...)` 设置。 |
| `useResponsesWebSocket` | 为此提供方解析的 Responses 模型使用 WebSocket 传输。默认使用进程级的 `setOpenAIResponsesTransport(...)` 设置。 |
| `cacheResponsesWebSocketModels` | 复用基于 WebSocket 的 Responses 模型包装器，以复用连接。默认为 `true`；请在关闭时调用 `provider.close()`，关闭缓存的包装器。 |
| `responsesWebSocketOptions` | 使用 `pingIntervalMs` 和 `pingTimeoutMs` 配置客户端保活。 |
| `strictFeatureValidation` | 对于 Chat Completions 模型，使用仅限 Responses 的功能（例如 `previousResponseId`、`conversationId`、`prompt` 和助手消息阶段）时抛出 `UserError`。默认情况下，会发出警告并忽略这些功能。 |

设置了 `apiKey`、`baseURL`、`organization` 或 `project` 时，该 `OpenAIProvider` 会使用提供方专属的值构建自己的 OpenAI 客户端，而不是复用通过 `setDefaultOpenAIClient(...)` 配置的客户端。如果既未设置这些选项，也未设置 `openAIClient`，提供方可以复用 SDK 级别的默认客户端。`websocketBaseURL` 会更改 Responses WebSocket 的目标地址，但单独设置它不会替换 HTTP 客户端。

当 Responses 助手消息包含值为 `commentary` 或 `final_answer` 的 `phase` 时，SDK 会将其保留为历史记录项的顶层字段。通过 `OpenAIConversationsSession` 和序列化的 `RunState` 重放会话时，该阶段信息仍会保留。Chat Completions 没有对应字段，因此默认会发出警告并丢弃阶段信息；设置 `strictFeatureValidation: true` 则会拒绝此转换。

#### Responses 终止状态

[Responses 流式传输协议](https://developers.openai.com/api/reference/resources/responses/streaming-events)使用带类型的终止事件。SDK 将带有响应载荷的 `response.completed` 事件视为成功的模型结果。对于 `failed` 或 `incomplete` 响应，`response.failed`、`response.incomplete` 或 `response.error` 事件，`error` 事件，以及缺少必需响应载荷的 `response.completed` 事件，SDK 在流式和非流式运行中都会抛出 `ModelBehaviorError`。

SDK 将未成功的终止状态视为响应可能已经开始，因此重放并不安全。对于非流式运行，默认重试建议不会自动重复请求；自定义重试策略必须明确批准不安全的重放，运行器才能重试。对于流式运行，一旦发出原始终止事件，运行器就不会重试，即使自定义重试策略批准了不安全的重放也是如此。如果未成功的响应报告了用量，运行器仍会将该用量计入追踪和运行统计。即使 `result.completed` 被拒绝，流式执行结果也会在 `result.state.usage` 中保留用量。

未成功的响应不会成为成功的 `ModelResponse`，不会追加到 `rawResponses` 或会话历史记录中，也不会执行该响应中的输出项。在 `result.completed` 被拒绝之前，流式消费者仍可通过原始模型事件流查看原始终止事件。不要将终止时的部分输出视为可重放的历史记录或最终输出。

#### Chat Completions 截断

对于 Chat Completions，`finish_reason: 'length'` 表示提供方因达到 token 或上下文限制而停止生成。当候选项包含有用的文本、拒绝内容、音频、推理或函数调用时，SDK 会保留该部分助手载荷。当被截断的候选项不包含上述任何载荷时，SDK 在流式和非流式运行中都会抛出 `ModelBehaviorError`，而不是将空候选项视为成功响应。

SDK 将这种空截断视为响应可能已经开始，因此重放并不安全。在 `result.completed` 被拒绝之前，流式消费者可能已经收到了原始数据块。如果失败的尝试报告了用量，运行器仍会将该用量计入追踪和运行统计。

#### Chat Completions 音频

支持音频的 Chat Completions 模型可通过 `modelSettings.providerData` 接收端点专属的 `modalities` 和 `audio` 请求字段。请使用支持音频的模型，并参阅官方[音频与语音指南](https://developers.openai.com/api/docs/guides/audio#add-audio-to-your-existing-application)，了解支持的请求值。

非流式和流式调用都会保留仅含音频的助手输出。标准化后的 `ModelResponse.output` 包含一个 `audio` 内容部分。当该消息成为运行项时，`RunMessageOutputItem.rawItem` 包含相同的内容部分。其 `audio` 字段包含 base64 数据，而 `providerData` 保留提供方元数据，例如 `id`、`transcript`、`format` 和 `expires_at`。当同一候选项还包含文本或拒绝内容时，标准化后的助手消息会保留这些文本或拒绝内容。对于非流式调用，完整的提供方响应（包括音频）仍可通过 `result.rawResponses[].providerData` 获取。对于流式调用，请在原始模型流事件到达时从中消费源 Chat Completions 数据块；重建的音频会保留用于追踪，而不会保存在 `result.rawResponses` 中。值为 null 的音频片段会被忽略。格式错误或无法克隆的音频增量，以及结束时没有音频数据的流，都会引发 `ModelBehaviorError`。`toTextStream()` 仅输出助手文本。如果应用需要低延迟的双向音频，请改用[语音智能体概述](/openai-agents-js/zh/guides/voice-agents)中介绍的 Realtime API。

#### Responses WebSocket 传输

通过 OpenAI 提供方使用 Responses API 时，可以通过 WebSocket 传输发送请求，而不使用默认的 HTTP 传输。

通过 `setOpenAIResponsesTransport('websocket')` 全局启用，或通过 `new OpenAIProvider({ useResponses: true, useResponsesWebSocket: true })` 为单个提供方启用。

仅仅使用 WebSocket 传输并不需要 `withResponsesWebSocketSession(...)` 或自定义 `OpenAIProvider`。如果可以接受每次运行或请求都重新连接，那么启用 `setOpenAIResponsesTransport('websocket')` 后，现有的 `run()` / `Runner.run()` 用法仍可继续正常工作。

传输选择取决于模型解析：

- `setOpenAIResponsesTransport('websocket')` 仅影响后续通过 OpenAI 提供方解析、且使用 Responses API 的字符串模型名称。
- 如果向 `Agent` 或 `Runner` 传入具体的 `Model` 实例，则会原样使用该实例。`OpenAIResponsesWSModel` 仍使用 WebSocket，`OpenAIResponsesModel` 仍使用 HTTP，`OpenAIChatCompletionsModel` 仍使用 Chat Completions。
- 如果提供自己的 `modelProvider`，模型解析由该提供方控制。请在该提供方中启用 WebSocket，而不是依赖全局设置函数。
- 如果通过代理、网关或其他 OpenAI 兼容端点路由请求，目标必须支持 WebSocket `/responses` 端点。你可能还需要显式设置 `websocketBaseURL`。

只有在希望优化连接复用，并更明确地管理 WebSocket 提供方生命周期时，才需要使用 `withResponsesWebSocketSession(...)` 或自定义 `OpenAIProvider` / `Runner`：

- `withResponsesWebSocketSession(...)`：提供便捷的作用域生命周期管理，在回调结束后自动清理。
- 自定义 `OpenAIProvider` / `Runner`：在自己的应用架构中显式控制生命周期（包括关闭时的清理）。

尽管名称中带有 Session，`withResponsesWebSocketSession(...)` 实际上是传输生命周期辅助函数，与[会话](/openai-agents-js/zh/guides/sessions)指南中描述的记忆 `Session` 接口无关。

如果使用 WebSocket 代理或网关，请在 `OpenAIProvider` 上配置 `websocketBaseURL`，或设置 `OPENAI_WEBSOCKET_BASE_URL`。

在 `responsesWebSocketOptions` 中，`pingIntervalMs` 设置客户端发送 ping 的间隔；省略该选项或将其设为 `null` 可禁用 ping。`pingTimeoutMs` 设置在终止或关闭套接字之前等待 pong 的时长；省略该选项或将其设为 `null` 可禁用心跳超时，同时保持 ping 启用。保活功能需要 WebSocket 实现提供 ping 和 pong 支持。

如果自行实例化 `OpenAIProvider`，请注意，基于 WebSocket 的 Responses 模型包装器默认会被缓存，以便复用连接。请在关闭时调用 `await provider.close()`，释放这些缓存的连接。`withResponsesWebSocketSession(...)` 的主要作用就是为你管理该生命周期：它会创建启用 WebSocket 的提供方和运行器，将它们传入回调，并始终在回调结束后关闭提供方。使用 `providerOptions` 配置临时提供方，使用 `runnerConfig` 配置回调作用域内的运行器默认设置。

有关使用 Responses WebSocket 传输的完整流式传输 + HITL 代码示例，请参阅 [`examples/basic/stream-ws.ts`](https://github.com/openai/openai-agents-js/tree/main/examples/basic/stream-ws.ts)。

#### 仅限 Responses 的延迟工具加载

`toolSearchTool()`、`toolNamespace()`，以及设置了 `deferLoading: true` 的函数工具或托管 MCP 工具，都需要 OpenAI Responses API。Chat Completions 提供方会拒绝带命名空间或延迟加载的函数工具，AI SDK 适配器也不支持 Responses 的延迟工具加载流程。需要工具搜索时，请直接使用 Responses 模型。

工具搜索仅在 GPT-5.6 Sol 及更新且在 Responses API 中支持该功能的模型版本上受支持。

当运行包含延迟加载的工具时，请将 `toolSearchTool()` 添加到同一个智能体，并将 `modelSettings.toolChoice` 保持为 `'auto'`。SDK 不允许按名称强制使用内置的 `tool_search` 工具或延迟加载的函数工具，因为模型需要自行决定何时加载这些定义。有关完整配置，请参阅[工具](/openai-agents-js/zh/guides/tools#deferred-tool-loading-with-tool-search)指南和官方 [OpenAI 工具搜索指南](https://developers.openai.com/api/docs/guides/tools-tool-search)。

### 托管多智能体（实验性）

<Aside type="caution" title="实验性 Beta 版">
  托管多智能体使用 Beta 版 Responses API 的条目模式，并且只能 通过实验性的
  `@openai/agents-openai/experimental/hosted-multi-agent` 导出使用。API 和 SDK
  接口可能会发生变化。
</Aside>

请将提供方包和 OpenAI 客户端安装为直接依赖，因为代码示例会直接导入这两个包：

```bash
npm install @openai/agents-openai openai
```

托管多智能体允许 GPT-5.6 模型通过 Responses API 创建和协调树状的子智能体结构。这与 [SDK 交接](/openai-agents-js/zh/guides/handoffs/)和 agents-as-tools 不同：应用不会为托管子智能体创建本地 `Agent` 对象，也不会调度其工作。托管根智能体负责委派工作，服务负责协调子智能体，`/root` 则综合生成最终答案。有关 Beta 版 API 的行为和支持的模型，请参阅官方[多智能体指南](https://developers.openai.com/api/docs/guides/tools-multi-agent)。

省略 `maxConcurrentSubagents` 可保留服务默认值，目前为 3。如果提供该值，则必须为正整数。

#### 工具执行与归属

每个托管智能体都使用请求中的模型，并且可以看到相同的本地工具定义。当任何托管智能体发出普通的 `function_call` 时，现有的 Agents SDK 运行器会执行应用工具。Responses API 的调用 ID 是路由标识：SDK 会将匹配的 `function_call_output` 注入正在进行的托管响应，交给发起请求的调用方。

`getHostedAgentMetadata(details)` 从工具回调的第三个参数中读取托管智能体名称。该元数据可用于日志记录和应用授权，但不控制路由。不要按智能体名称分发函数结果；请保留并使用调用 ID。

工具参数通过 WebSocket 从服务传入，工具输出则注入回正在进行的托管响应。请在应用中保留敏感数据策略、工具授权和审批检查。如果工具具有副作用，请基于调用 ID 确保其幂等性，以免中断后继续执行时重复产生副作用。

#### 输出与流式传输行为

只有阶段为 `final_answer` 的 `/root` 消息会成为普通助手输出，并计入 `finalOutput`。函数调用仍是普通的 SDK 工具调用，以便运行器执行；推理和托管工具调用等稳定的 Responses 条目也保留现有的 SDK 表示形式。子智能体消息、根智能体的过程说明以及托管协作记录仅保留在正在进行的 WebSocket 响应中，不会添加到 SDK 历史记录。

原始流式事件仍可通过 `raw_model_stream_event` 获取，包括托管记录和子智能体消息。高级条目流式传输会保留稳定的 Responses 条目，同时过滤仅限 Beta 版的协作记录；高级文本流式传输仅包含根智能体的最终答案。这样既能保持 RunState 和会话历史记录不依赖特定提供方，又能保留完整的托管事件流以实现可观测性。

请持续消费流式运行，直到其终止事件。如果流消费者提前停止，SDK 会关闭 WebSocket 并放弃正在进行的托管响应；后续运行会启动新的托管响应，而不是恢复被放弃的响应。

#### 当前限制

该实验性 SDK 模型仅支持 Responses WebSocket 传输。Beta 版 Responses API 也支持通过 HTTP 使用托管多智能体，但 `OpenAIHostedMultiAgentModel` 会保持一个 WebSocket 连接打开，以便 SDK 运行器在继续执行前，将每个本地函数输出注入正在进行的响应。

正在进行的托管响应的续接状态由 `OpenAIHostedMultiAgentModel` 实例保存。模型可以在注入待处理的函数输出之前，重新连接已关闭的 WebSocket，但审批和中断的工具仍必须使用同一个模型实例，以及相同的 WebSocket 传输标头和查询参数来恢复。重新创建模型会丢失续接状态。一个模型实例同一时间也只能支持一次活动运行。

只有当 SDK 确定请求帧尚未发送时，传输失败后的重放才是安全的。一旦服务器可能已经收到请求帧，SDK 就会将错误标记为不安全重放，并且不会自动重复该托管轮次。有关通用重试策略，请参阅[模型重试](#model-retries)。

不要将此模型与 SDK 交接、`reasoning.summary` 或 `max_tool_calls` 组合使用；这些组合会在发送请求之前失败。通过 `modelSettings.contextManagement` 配置的服务器端压缩阈值仍受支持，但对 Responses 压缩端点的显式调用不在此模型的生命周期范围内。你仍可继续将 SDK 交接和 agents-as-tools 与稳定版 `OpenAIResponsesModel` 配合使用。

`Runner` 级别的设置会覆盖与之冲突的智能体级别设置。运行器和智能体设置中的 `reasoning`、`text`、`promptCacheOptions` 和 `retry` 嵌套字段会合并，除非你使用 `undefined` 显式清除继承的值。

### 模型重试

重试仅在运行时生效，且需要显式启用。除非你配置了 `modelSettings.retry` 并且策略返回重试决定，否则 SDK 不会重试模型请求。

<Code lang="typescript" code={retryExample} title="启用模型重试" />

`ModelRetrySettings` 包含三个字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `maxRetries` | `number` | 初始请求之后允许的重试次数。 |
| `backoff` | `{ initialDelayMs?, maxDelayMs?, multiplier?, jitter? }` | 策略决定重试但未返回 `delayMs` 时使用的默认延迟策略。`backoff.maxDelayMs` 仅限制此计算得出的退避延迟；它不限制策略返回的显式 `delayMs` 值或 retry-after 提示指定的延迟。 |
| `policy` | `RetryPolicy` | 决定是否重试的回调。此函数仅在运行时生效，不会序列化到持久化的运行状态中。 |

重试策略会收到一个 `RetryPolicyContext`，其中包含：

- `attempt` 和 `maxRetries`，以便根据尝试次数做出决定。
- `stream`，以便分别处理流式和非流式行为。
- `error`，用于查看原始错误。
- `normalized`，包含 `statusCode`、`retryAfterMs`、`errorCode`、`isNetworkError` 和 `isAbort` 等标准化信息。
- `providerAdvice`，在底层模型或提供方能够提供重试指导时可用。
- `replaySafety`、`responseStarted` 和 `statefulRequest`，使应用策略可以查看运行器的稳定重放分类，而无需重新解读提供方专属的错误。

策略可以返回以下任一种形式：

- `true` / `false`，用于简单的重试决定。
- `{ retry, delayMs?, reason?, approveUnsafeReplay? }`，用于覆盖延迟、附加供日志记录的诊断原因，或明确授权提供方标记为不安全的非流式重放。

SDK 通过 `retryPolicies` 导出现成的辅助函数：

| 辅助函数 | 行为 |
| --- | --- |
| `retryPolicies.never()` | 始终不重试。 |
| `retryPolicies.providerSuggested()` | 在可用时遵循提供方的重试建议。 |
| `retryPolicies.networkError()` | 匹配暂时性的传输或连接故障。 |
| `retryPolicies.httpStatus([..])` | 匹配指定的 HTTP 状态码。 |
| `retryPolicies.retryAfter()` | 仅在有 retry-after 提示时重试，并将该提示用作显式延迟，不受 `backoff.maxDelayMs` 限制。 |
| `retryPolicies.any(...)` | 任一嵌套策略同意时重试。 |
| `retryPolicies.all(...)` | 仅在所有嵌套策略都同意时重试。 |

组合策略时，`providerSuggested()` 是最安全的起始组件，因为在提供方能够区分这些情况时，它会保留提供方的否决决定和重放安全批准。

#### 安全边界

某些失败绝不会自动重试：

- 中止错误。
- 已发出任何可见事件或原始模型事件后的流式运行。
- 提供方建议将重放标记为不安全的情况。

对于使用 `previousResponseId` 或 `conversationId` 的有状态后续请求，也会采取更保守的处理。对于这些请求，仅靠 `networkError()` 或 `httpStatus([500])` 等非提供方判定条件并不足够。重试策略必须包含提供方关于可安全重放的批准，通常通过 `retryPolicies.providerSuggested()` 获取。

应用可以通过返回 `{ retry: true, approveUnsafeReplay: true }`，覆盖提供方对非流式请求的不安全分类。这表示明确承认先前的请求可能已经被接受，重试可能导致重复响应或其他提供方端工作的重复执行。仅当应用能够接受这种结果时才使用它。该设置不会覆盖中止处理、已发出事件的流式请求限制，也不会允许不安全的流式重放。使用 `retryPolicies.any(...)` 或 `retryPolicies.all(...)` 组合策略时，只有返回的决定显式设置了 `approveUnsafeReplay: true`，该批准才会被保留。

#### 运行器与智能体的合并行为

运行器级别和智能体级别的 `modelSettings` 之间会对 `retry` 进行深度合并：

- 智能体可以仅覆盖 `retry.maxRetries`，同时仍继承运行器的 `policy`。
- 智能体可以仅覆盖 `retry.backoff` 的一部分，同时保留来自运行器的其他同级退避字段。
- 如果需要移除继承的 `policy` 或 `backoff`，请将该字段显式设为 `undefined`。

有关包含日志记录的更完整代码示例，请参阅 [`examples/basic/retry.ts`](https://github.com/openai/openai-agents-js/tree/main/examples/basic/retry.ts) 和 [`examples/ai-sdk/retry.ts`](https://github.com/openai/openai-agents-js/tree/main/examples/ai-sdk/retry.ts)。
