请尽早选择架构：

- `OpenAIRealtimeWebRTC` 是最简单的浏览器端方案，可自动处理音频输入和输出。
- `OpenAIRealtimeWebSocket` 可提供更多控制能力，但您必须自行管理音频采集和播放。

## 会话设置

### 音频处理

某些传输层（例如默认的 `OpenAIRealtimeWebRTC`）会自动为您处理音频输入和输出。对于 `OpenAIRealtimeWebSocket` 等其他传输机制，您必须自行处理会话音频：

<Code lang="typescript" code={handleAudioExample} />

底层传输支持时，`session.muted` 会报告当前静音状态，`session.mute(true | false)` 则用于切换麦克风采集状态。`OpenAIRealtimeWebSocket` 未实现静音功能：`session.muted` 返回 `null`，而 `session.mute()` 会抛出异常。因此，在 WebSocket 配置中，您应在自己的实现中暂停采集，并停止调用 `sendAudio()`，直到需要重新启用麦克风。

### 会话配置

创建 [`RealtimeSession`](/openai-agents-js/openai/agents-realtime/classes/realtimesession/) 时配置会话本身，通常通过 `model` 选项和 `config` 对象进行配置。`connect(...)` 用于处理连接时的事项，例如凭证、端点 URL 和 SIP 通话附加，而不是任意会话字段。

<Code lang="typescript" code={configureSessionExample} />

在底层，SDK 会将此配置规范化为 Realtime [`session.update`](https://developers.openai.com/api/reference/resources/realtime/client-events/#session.update) 结构。如果需要使用 [RealtimeSessionConfig](/openai-agents-js/openai/agents-realtime/type-aliases/realtimesessionconfig/) 中没有对应属性的原始会话字段，请使用 `providerData`，或通过 `session.transport.sendEvent(...)` 发送原始 `session.update`。

建议优先使用包含 `outputModalities`、`audio.input` 和 `audio.output` 的新版 SDK 配置结构。为保持向后兼容，`modalities`、`inputAudioFormat`、`outputAudioFormat`、`inputAudioTranscription` 和 `turnDetection` 等旧版 SDK 别名仍会被规范化，但新代码应使用此处所示的嵌套 `audio` 结构。

对于 `gpt-realtime-2.1` 等支持推理的 Realtime 模型，请在会话配置中设置 `reasoning.effort`。更高的推理强度可能会增加延迟和 token 用量。您还可以设置 `parallelToolCalls`，以控制模型是否可以并行调用多个工具。

对于语音到语音会话，通常选择 `outputModalities: ['audio']`，这样既可获得音频输出，也可获得转录文本。仅当需要纯文本响应时，才切换为 `['text']`。

对于较新的参数，如果 [RealtimeSessionConfig](/openai-agents-js/openai/agents-realtime/type-aliases/realtimesessionconfig/) 中没有对应参数，可以使用 `providerData`。传入 `providerData` 的所有内容都会作为原始 `session` 对象的一部分进行转发。

还可以在构造时设置以下 `RealtimeSession` 选项：

| 选项 | 类型 | 用途 |

| `callId` | `string` | 附加到由 SIP 发起的现有通话或会话。 |

### 对话生命周期

`RealtimeSession` 建立在长期运行的 Realtime 连接之上。它会保存对话历史记录的本地副本、监听传输事件、运行工具和输出护栏，并使当前智能体配置与传输层保持同步。

底层 API 的行为仍然很重要：

- 连接成功后，会先收到 `session.created` 事件，后续配置更改会产生 `session.updated`。
- 大多数会话属性都可以随时间更改，但 `model` 不能在对话过程中更改；`voice` 只能在会话尚未生成音频输出时更改；追踪应预先确定，因为 Realtime API 不允许在启用追踪后修改相关设置。
- Realtime API 目前将单个会话限制为 60 分钟。
- 输入音频转录是异步的，因此最新话语的转录文本可能在响应生成已开始后才到达。

在 SDK 层，`await session.connect()` 表示"传输已就绪，可以开始对话"，但具体的就绪时点因传输方式而异：

- 在默认的浏览器 WebRTC 传输中，SDK 会在数据通道打开后立即发送初始 `session.update`，并尝试等待对应的 `session.updated` 事件，然后才解析 `connect()`。这样可以避免音频在您的 instructions、工具和模态应用前到达服务器。如果始终未收到该确认，`connect()` 会在短暂超时后回退为直接解析。
- 在默认的服务器端 WebSocket 传输中，套接字打开且初始配置发送后，`connect()` 就会解析。因此，对应的 `session.updated` 事件可能在 `connect()` 已解析后才到达。

如果需要了解原始事件模型，请结合本页阅读官方的 [Realtime 对话指南](https://developers.openai.com/api/docs/guides/realtime-conversations/)。

## 交互流程

### 轮次检测与语音活动检测

默认情况下，Realtime 会话使用内置语音活动检测（VAD），使 API 能够判断用户何时开始或停止说话，以及何时创建响应。SDK 通过 `audio.input.turnDetection` 公开此功能。

<Code lang="typescript" code={turnDetectionExample} />

两种常见模式是：

- `semantic_vad`，旨在提供更自然的轮次边界。当用户听起来还没说完时，它可以多等待一会儿。
- `server_vad`，更依赖阈值，并提供 `threshold`、`prefixPaddingMs`、`silenceDurationMs` 和 `idleTimeoutMs` 等设置。

如果要自行管理轮次边界，请将 `audio.input.turnDetection` 设置为 `null`。官方[语音活动检测指南](https://developers.openai.com/api/docs/guides/realtime-vad/)和 [Realtime 对话指南](https://developers.openai.com/api/docs/guides/realtime-conversations/#voice-activity-detection)更详细地介绍了底层行为。

### 中断

启用 VAD 后，用户在智能体说话时插话可中断当前响应。在 WebSocket 传输中，SDK 会监听 `input_audio_buffer.speech_started`，将助手音频截断到用户实际听到的位置，并发出 `audio_interrupted` 事件。当您在 WebSocket 配置中自行管理播放时，此事件尤其有用。

### 手动响应控制

在较高层级的 SDK 中，`sendMessage()` 和 `addImage()` 默认会为您触发响应。当您处理原始传输事件、按键说话流程或自定义审核／验证步骤时，手动响应控制非常重要。

<Code lang="typescript" code={transportEventsExample} />

常见情况有两种：

1. 如果通过 `audio.input.turnDetection = null` 完全禁用 VAD，您需要负责提交音频轮次，然后发送 `response.create`。
2. 如果保留 VAD，但将 `turnDetection.interruptResponse = false` 和 `turnDetection.createResponse = false`，API 仍会检测轮次，但由您负责创建响应。

第二种模式适用于希望在模型响应前检查或审核用户输入的场景。它与官方 [Realtime 对话指南中关于禁用自动响应的说明](https://developers.openai.com/api/docs/guides/realtime-conversations/#keep-vad-but-disable-automatic-responses)一致。

## 智能体能力

### 交接

与常规智能体类似，您可以使用交接将一个智能体拆分为多个智能体，并在它们之间进行编排，从而提高性能并更准确地限定问题范围。

<Code lang="typescript" code={multiAgentsExample} />

与常规智能体不同，实时智能体的交接行为略有差异。执行交接时，正在进行的会话会直接更新为新智能体的配置。因此，新智能体会自动访问当前对话历史记录，并且目前不会应用输入过滤器。

由于会话保持实时连接，在交接期间，该会话使用的模型不会改变。语音更改遵循底层 Realtime API 规则：只有在会话尚未生成音频输出时才会生效。实时交接主要用于在同一会话中的不同 `RealtimeAgent` 配置之间切换；如果需要使用不同的模型（例如 `gpt-5.4` 这样的推理模型），或将任务委派给非实时后端智能体，请使用[通过工具委派](#delegation-through-tools)。

### 工具

与常规智能体一样，实时智能体可以调用工具来执行操作。Realtime 支持**函数工具**（在本地执行）和**托管 MCP 工具**（由 Realtime API 远程执行）。您可以使用为常规智能体定义工具时所用的同一个 `tool()` 辅助函数来定义函数工具。

Responses 专属的工具选项不适用于实时智能体。函数工具中包含 `'programmatic'` 的 `outputSchema` 和 `allowedCallers` 值会被拒绝，托管 MCP 工具上的编程式调用方也同样会被拒绝。请在 Realtime 会话中使用可直接调用的函数工具或托管 MCP 工具；需要编程式工具调用（Programmatic Tool Calling）的工作则应委派给 Responses 智能体。

<Code lang="typescript" code={defineToolExample} />

#### 函数工具

函数工具与您的 `RealtimeSession` 在同一环境中运行。这意味着，如果会话在浏览器中运行，工具也会在浏览器中执行。如果需要执行敏感操作，请从工具内部调用后端，并让服务器执行需要特权的工作。

这样，浏览器端工具就可以充当连接服务器端逻辑的轻量级反向通道。例如，[`examples/realtime-next`](https://github.com/openai/openai-agents-js/tree/main/examples/realtime-next) 在浏览器中定义了一个 `refundBackchannel` 工具，该工具会将请求和当前对话历史记录转发给服务器上的 `handleRefundRequest(...)`。服务器上的另一个 `Runner` 可以使用不同的智能体或模型评估退款，然后将结果返回给语音会话。

#### 托管 MCP 工具

可以使用 `hostedMcpTool` 配置托管 MCP 工具，这些工具会远程执行。当 MCP 工具的可用性发生变化时，会话会发出 `mcp_tools_changed`。若要防止会话在 MCP 工具调用完成后自动触发模型响应，请设置 `automaticallyTriggerResponseForMcpToolCalls: false`。

当前经过筛选的 MCP 工具列表也可通过 `session.availableMcpTools` 获取。该属性和 `mcp_tools_changed` 事件都仅反映当前智能体上已启用的托管 MCP 服务器，并且已应用智能体配置中的所有 `allowed_tools` 过滤器。

要更轻松地理解托管 MCP 的设置，可以将安全服务器选择、请求头和审批都视为连接前配置。在 `RealtimeSession.connect()` 打开传输之前，SDK 会解析当前智能体的托管 MCP 工具定义，并将支持的 MCP 字段包含在发送给 Realtime API 的初始会话配置中。

这一时序对于浏览器 WebRTC 应用最为重要。临时客户端密钥始终在您的服务器上生成，因此，任何必须保密的托管 MCP 凭证或自定义 `headers` 都应作为初始 `session` 负载的一部分，附加到服务器端的 `POST /v1/realtime/client_secrets` 请求中。不要将长期凭证放入浏览器代码，并计划在 `connect()` 开始后再添加。

在 Realtime API 层面，后续 `session.update` 调用仍可更改工具和其他可变会话字段，并且当前智能体发生变化时，SDK 本身也会发送 `session.update`。不过，在浏览器应用中，您应将安全的托管 MCP 初始化视为服务器端的连接前事项，并确保浏览器端 `RealtimeSession` 配置与服务器生成密钥时使用的配置保持一致。

#### 后台结果

工具执行期间，智能体无法处理用户的新请求。改善体验的一种方式是，让智能体在即将执行工具时先进行说明，或说出特定短语，为工具执行留出一些时间。

如果函数工具应在完成后不立即触发另一个模型响应，请从 `@openai/agents/realtime` 返回 `backgroundResult(output)`。这会将工具输出发送回会话，同时仍由您控制响应触发。

#### 超时

函数工具超时选项（`timeoutMs`、`timeoutBehavior`、`timeoutErrorFunction`）在 Realtime 会话中的工作方式相同。使用默认的 `error_as_result` 时，超时消息会作为工具输出发送。使用 `raise_exception` 时，会话将发出包含 [`ToolTimeoutError`](/openai-agents-js/openai/agents-core/classes/tooltimeouterror) 的 `error` 事件，并且不会为该调用发送工具输出。

除了智能体调用特定工具时使用的参数外，您还可以访问 Realtime 会话所跟踪的当前对话历史记录快照。如果需要根据对话的当前状态执行更复杂的操作，或计划使用[工具进行委派](#delegation-through-tools)，这会很有用。

#### 工具执行前审批

如果定义工具时设置了 `needsApproval: true`，智能体会在执行工具前发出 `tool_approval_requested` 事件。

通过监听此事件，您可以向用户显示 UI，让其批准或拒绝工具调用。

使用 `await session.approve(request.approvalItem)` 或 `await session.reject(request.approvalItem)` 处理请求。对于函数工具，您可以传入 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }`，以便在会话剩余时间内对重复调用复用相同决定；也可以使用 `session.reject(request.approvalItem, { message: '...' })`，针对该次调用向模型返回自定义拒绝消息。托管 MCP 审批不支持持续生效的批准或拒绝；请改用托管 MCP 的 `allowedTools` 配置来限制这些工具。

如果未传入单次调用的拒绝 `message`，会话会回退到 `toolErrorFormatter`（如果已配置），然后再回退到 SDK 的默认拒绝文本。

默认情况下，函数工具输入护栏会在审批后、工具执行前立即运行。如果将 `toolExecution: { preApprovalInputGuardrails: true }` 传给 `new RealtimeSession(...)`，本地函数工具输入护栏也会在会话发出 `tool_approval_requested` 前运行。护栏拒绝会将拒绝消息作为工具输出返回，并跳过审批事件。如果护栏允许该调用，仍会发出审批事件；在调用 `session.approve(...)` 后、执行工具前，护栏会再次运行。

### 护栏

护栏可用于监控智能体说出的内容是否违反一组规则，并立即停止响应。这些检查会针对智能体响应的转录文本流运行。在音频会话中，SDK 使用输出音频转录文本和转录增量，因此关键前提是转录文本可用，而不是需要单独的文本输出模态。

您提供的护栏会在模型响应返回时异步运行，从而能够根据预定义的分类触发条件停止响应，例如"提及某个特定的禁用词"。

护栏触发时，会话会发出 `guardrail_tripped` 事件。该事件还会提供一个 `details` 对象，其中包含触发护栏的 `itemId`。

<Code lang="typescript" code={guardrailsExample} />

默认情况下，护栏每生成 100 个字符运行一次，并在最终转录文本可用时再次运行。由于说出文本通常比生成转录文本耗时更长，因此护栏通常可以在用户听到不安全输出前将其停止。

如果要修改此行为，可以向会话传入 `outputGuardrailSettings` 对象。

如果只想在响应结束时对完整生成的转录文本评估一次，请设置 `debounceTextLength: -1`。

## 对话状态与委派

### 对话历史记录管理

`RealtimeSession` 会自动维护本地 `history` 快照，用于跟踪用户消息、助手输出、工具调用和截断状态。您可以在 UI 中呈现它、在工具中检查它，或在需要纠正或删除条目时更新它。

当对话发生变化时，会话会发出 `history_updated`。如果需要请求更改历史记录，请使用 `updateHistory()`。它会要求传输层对当前历史记录进行差异比较，并发送必要的删除／创建事件；当对应的对话事件返回时，本地 `session.history` 视图会随之更新。

#### 限制

1. 目前无法在事后编辑函数工具调用。
2. 历史记录中的助手文本取决于可用的转录文本，包括 `output_audio.transcript`。
3. 因中断而截断的响应不会保留最终转录文本。
4. 最好将输入音频转录视为用户所述内容的大致参考，而不是模型如何理解音频的精确副本。
