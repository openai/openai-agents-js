请尽早选择架构：

- `OpenAIRealtimeWebRTC` 是最简单的浏览器方案，可自动处理音频输入和输出。

## 会话设置

### 音频处理

默认的 `OpenAIRealtimeWebRTC` 等传输层会自动处理音频输入和输出。对于 `OpenAIRealtimeWebSocket` 等其他传输机制，您必须自行处理会话音频：

<Code lang="typescript" code={handleAudioExample} />

如果底层传输支持静音，`session.muted` 会报告当前静音状态，而 `session.mute(true | false)` 可切换麦克风采集状态。`OpenAIRealtimeWebSocket` 未实现静音功能：`session.muted` 返回 `null`，而 `session.mute()` 会抛出异常。因此，在 WebSocket 设置中，您应在客户端暂停采集，并停止调用 `sendAudio()`，直到需要重新启用麦克风。

在底层，SDK 会将此配置规范化为 Realtime [`session.update`](https://developers.openai.com/api/reference/resources/realtime/client-events/#session.update) 结构。如果需要使用 [RealtimeSessionConfig](/openai-agents-js/openai/agents-realtime/type-aliases/realtimesessionconfig/) 中没有对应属性的原始会话字段，请使用 `providerData`，或通过 `session.transport.sendEvent(...)` 发送原始 `session.update`。

建议使用较新的 SDK 配置结构，其中包含 `outputModalities`、`audio.input` 和 `audio.output`。为实现向后兼容，`modalities`、`inputAudioFormat`、`outputAudioFormat`、`inputAudioTranscription` 和 `turnDetection` 等旧版 SDK 别名仍会被规范化，但新代码应使用此处所示的嵌套 `audio` 结构。

对于 `gpt-realtime-2.1` 等具备推理能力的 Realtime 模型，请在会话配置中设置 `reasoning.effort`。更高的推理强度可能会增加延迟和 token 用量。如果需要控制模型是否可以并行调用多个工具，还可以设置 `parallelToolCalls`。

对于输入转录，`audio.input.transcription` 接受正式发布（GA）的转录模型及其上下文选项。使用 `gpt-live-transcribe` 可实现低延迟的流式转录；其 `delay` 设置可在更快生成部分转录和最终转录质量之间进行权衡。`gpt-live-transcribe` 和 `gpt-transcribe` 都接受自由格式的 `prompt`、字面量 `keywords` 和 `languages` 数组。这些模型使用 `languages`；接受单一语言提示的旧版转录模型仍使用单数形式的 `language` 字段。有关特定模型的工作流，请参阅官方[转录上下文指南](https://developers.openai.com/api/docs/guides/transcription/#improve-transcription-quality)和 [Realtime 转录指南](https://developers.openai.com/api/docs/guides/realtime-transcription/)。

对于语音到语音会话，通常选择 `outputModalities: ['audio']`，以同时获得音频输出和转录。仅当需要纯文本响应时，才切换到 `['text']`。

对于 [RealtimeSessionConfig](/openai-agents-js/openai/agents-realtime/type-aliases/realtimesessionconfig/) 中没有对应参数的新参数，可以使用 `providerData`。传入 `providerData` 的所有内容都会作为原始 `session` 对象的一部分转发。

### 对话生命周期

`RealtimeSession` 构建在长期运行的 Realtime 连接之上。它会保留对话历史记录的本地副本、监听传输事件、运行工具和输出护栏，并使当前智能体配置与传输保持同步。

底层 API 的行为仍然很重要：

- 成功建立连接时会先收到 `session.created` 事件，后续配置更改会生成 `session.updated`。
- 大多数会话属性都可以随时间更改，但 `model` 无法在对话期间更改；`voice` 只能在会话尚未生成音频输出时更改；追踪应提前确定，因为 Realtime API 不允许在启用追踪后对其进行修改。
- Realtime API 目前将单个会话限制为 60 分钟。
- 输入音频转录是异步进行的，因此最新话语的转录可能会在响应生成已经开始后才到达。

在 SDK 层，`await session.connect()` 表示"传输已准备就绪，可以开始对话"，但确切时机因传输方式而异：

- 在默认的浏览器 WebRTC 传输中，SDK 会在数据通道打开后立即发送初始 `session.update`，并尝试等待对应的 `session.updated` 事件，然后再完成 `connect()`。WebRTC 传输会等待此确认，以防止音频在您的指令、工具和模态生效前到达服务器。如果始终没有收到确认，`connect()` 会在短暂超时后转为完成状态。
- 在默认的服务器端 WebSocket 传输中，套接字打开且初始配置发送后，`connect()` 即完成。因此，对应的 `session.updated` 事件可能会在 `connect()` 已经完成后才到达。

如果需要了解原始事件模型，请结合本页阅读官方 [Realtime 对话指南](https://developers.openai.com/api/docs/guides/realtime-conversations/)。

## 交互流程

### 轮次检测与语音活动检测

默认情况下，Realtime 会话使用内置语音活动检测（VAD），以便 API 确定用户何时开始或停止说话，以及何时创建响应。SDK 通过 `audio.input.turnDetection` 提供此功能。

<Code lang="typescript" code={turnDetectionExample} />

两种常见模式是：

- `semantic_vad`，旨在提供更自然的轮次边界；当用户听起来尚未说完时，它可以多等待一会儿。
- `server_vad`，更依赖阈值，并提供 `threshold`、`prefixPaddingMs`、`silenceDurationMs` 和 `idleTimeoutMs` 等设置。

如果要自行管理轮次边界，请将 `audio.input.turnDetection` 设置为 `null`。官方[语音活动检测指南](https://developers.openai.com/api/docs/guides/realtime-vad/)和 [Realtime 对话指南](https://developers.openai.com/api/docs/guides/realtime-conversations/#voice-activity-detection)更详细地介绍了底层行为。

### 中断

启用 VAD 后，用户在智能体说话时插话可以中断当前响应。在 WebSocket 传输中，SDK 会监听 `input_audio_buffer.speech_started`，将助手音频截断到用户实际听到的部分，并发出 `audio_interrupted` 事件。在 WebSocket 设置中自行管理播放时，该事件尤其有用。

### 手动响应控制

在较高层的 SDK 中，`sendMessage()` 和 `addImage()` 默认会自动触发响应。当您使用原始传输事件、按键说话流程或自定义审核/验证步骤时，手动响应控制非常重要。

常见情况有两种：

1. 如果通过 `audio.input.turnDetection = null` 完全禁用 VAD，则需要自行提交音频轮次，然后发送 `response.create`。
2. 如果保持启用 VAD，但将 `turnDetection.interruptResponse = false` 和 `turnDetection.createResponse = false`，API 仍会检测轮次，但由您负责创建响应。

## 智能体能力

### 交接

与普通智能体类似，您可以使用交接将一个智能体拆分为多个智能体，并在它们之间进行编排，从而提高性能并更好地限定问题范围。

<Code lang="typescript" code={multiAgentsExample} />

与普通智能体不同，实时智能体的交接行为略有差异。执行交接时，进行中的会话会直接更新为新的智能体配置。因此，新智能体会自动访问当前对话历史记录，而输入过滤器目前不会应用。

由于会话保持实时连接，该会话的模型不会在交接过程中发生变化。语音更改遵循底层 Realtime API 的规则：只有在会话尚未生成音频输出时才会生效。实时交接主要用于在同一会话中切换不同的 `RealtimeAgent` 配置；如果需要使用其他模型（例如 `gpt-5.4` 之类的推理模型），或委派给非实时后端智能体，请使用[通过工具委派](#delegation-through-tools)。

### 工具

与普通智能体一样，实时智能体可以调用工具来执行操作。Realtime 支持**函数工具**（在本地执行）和**托管 MCP 工具**（由 Realtime API 远程执行）。您可以使用为普通智能体定义工具时使用的同一个 `tool()` 辅助函数来定义函数工具。

Responses 专用工具选项不适用于实时智能体。包含 `'programmatic'` 的函数工具 `outputSchema` 和 `allowedCallers` 值会被拒绝，托管 MCP 工具上的程序化调用方同样会被拒绝。请在 Realtime 会话中使用可直接调用的函数工具或托管 MCP 工具，或者将需要程序化工具调用的工作委派给 Responses 智能体。

<Code lang="typescript" code={defineToolExample} />

#### 函数工具

函数工具与 `RealtimeSession` 在相同环境中运行。这意味着，如果会话在浏览器中运行，工具也会在浏览器中执行。如果需要执行敏感操作，请从工具内部调用后端，并让服务器执行需要特权的工作。

这样，浏览器端工具便可以充当连接服务器端逻辑的轻量级反向通道。例如，[`examples/realtime-next`](https://github.com/openai/openai-agents-js/tree/main/examples/realtime-next) 在浏览器中定义了 `refundBackchannel` 工具，用于将请求和当前对话历史记录转发给服务器上的 `handleRefundRequest(...)`。服务器上的另一个 `Runner` 可以使用不同的智能体或模型评估退款，然后将结果返回给语音会话。

#### 托管 MCP 工具

可以使用 `hostedMcpTool` 配置托管 MCP 工具，这些工具会远程执行。当 MCP 工具的可用性发生变化时，会话会发出 `mcp_tools_changed`。若要防止会话在 MCP 工具调用完成后自动触发模型响应，请设置 `automaticallyTriggerResponseForMcpToolCalls: false`。

当前经过过滤的 MCP 工具列表也可通过 `session.availableMcpTools` 获取。该属性和 `mcp_tools_changed` 事件都只反映当前智能体上启用的托管 MCP 服务器，并且已应用智能体配置中的所有 `allowed_tools` 过滤器。

如果将安全服务器选择、标头和审批视为连接前配置，托管 MCP 设置会更容易理解。在 `RealtimeSession.connect()` 打开传输之前，SDK 会解析当前智能体的托管 MCP 工具定义，并将受支持的 MCP 字段包含在发送给 Realtime API 的初始会话配置中。

在浏览器 WebRTC 应用中，尤其需要在 `connect()` 之前提供安全的托管 MCP 配置。临时客户端密钥始终由服务器生成，因此，任何必须保密的托管 MCP 凭据或自定义 `headers` 都应在服务器端的 `POST /v1/realtime/client_secrets` 请求中，作为初始 `session` 负载的一部分附加。不要将长期有效的凭据放入浏览器代码，并计划在 `connect()` 启动后再添加它们。

在 Realtime API 层，后续 `session.update` 调用仍可更改工具和其他可变会话字段；当前智能体发生变化时，SDK 本身也会发送 `session.update`。但在浏览器应用中，应将安全的托管 MCP 初始化视为服务器端的连接前事项，并确保浏览器端 `RealtimeSession` 配置与服务器生成密钥时使用的配置保持一致。

#### 后台结果

工具执行期间，智能体无法处理来自用户的新请求。改善体验的一种方式是让智能体在即将执行工具时进行说明，或说出特定话语，为工具执行争取一些时间。

如果函数工具完成后不应立即触发另一个模型响应，请从 `@openai/agents/realtime` 返回 `backgroundResult(output)`。这会将工具输出发送回会话，同时让您继续控制响应触发。

#### 超时

函数工具超时选项（`timeoutMs`、`timeoutBehavior`、`timeoutErrorFunction`）在 Realtime 会话中的工作方式相同。使用默认的 `error_as_result` 时，超时消息会作为工具输出发送。使用 `raise_exception` 时，会话会发出包含 [`ToolTimeoutError`](/openai-agents-js/openai/agents-core/classes/tooltimeouterror) 的 `error` 事件，并且不会为该调用发送工具输出。

#### 对话历史记录访问

除了智能体调用特定工具时传入的参数外，您还可以访问 Realtime 会话所追踪的当前对话历史记录快照。如果需要根据对话当前状态执行更复杂的操作，或计划使用[工具进行委派](#delegation-through-tools)，此功能会很有用。

#### 工具执行前审批

如果使用 `needsApproval: true` 定义工具，智能体会在执行工具前发出 `tool_approval_requested` 事件。

通过监听此事件，您可以向用户显示 UI，让用户批准或拒绝工具调用。

使用 `await session.approve(request.approvalItem)` 或 `await session.reject(request.approvalItem)` 处理请求。对于函数工具，可以传入 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }`，以便在会话剩余期间对重复调用沿用相同决定；还可以使用 `session.reject(request.approvalItem, { message: '...' })`，为该特定调用向模型返回自定义拒绝消息。托管 MCP 审批不支持持续沿用批准或拒绝决定；请改用托管 MCP 的 `allowedTools` 配置来限制这些工具。

如果未传入针对单次调用的拒绝 `message`，会话会先使用 `toolErrorFormatter`（如果已配置），否则使用 SDK 的默认拒绝文本。

默认情况下，函数工具输入护栏会在审批完成后、工具执行前立即运行。如果将 `toolExecution: { preApprovalInputGuardrails: true }` 传给 `new RealtimeSession(...)`，本地函数工具输入护栏还会在会话发出 `tool_approval_requested` 前运行。护栏拒绝会将拒绝消息作为工具输出返回，并跳过审批事件。如果护栏允许该调用，仍会发出审批事件，并且在 `session.approve(...)` 之后、工具执行之前再次运行护栏。

### 护栏

护栏可用于监控智能体所说的内容是否违反一组规则，并立即中止响应。这些检查针对智能体响应的输出流运行。在纯文本会话中，SDK 会评估输出文本增量。在音频会话中，SDK 使用输出音频转录和转录增量，因此关键前提是转录可用，而不是需要单独的文本输出模态。

您提供的护栏会在模型响应返回期间异步运行，以便根据预定义的分类触发条件中止响应，例如"提到了某个特定禁用词"。

当护栏被触发时，会话会发出 `guardrail_tripped` 事件。该事件还会提供一个 `details` 对象，其中包含触发护栏的 `itemId`。

默认情况下，护栏每生成 100 个字符运行一次，并在最终转录可用时再次运行。由于朗读文本通常比生成转录耗时更长，因此护栏往往可以在用户听到不安全输出之前将其中止。

如果要修改此行为，可以向会话传入 `outputGuardrailSettings` 对象。

## 对话状态与委派

### 对话历史记录管理

`RealtimeSession` 会自动维护本地 `history` 快照，用于追踪用户消息、助手输出、工具调用和截断状态。您可以在 UI 中呈现它、在工具内部检查它，或在需要更正或移除条目时更新它。

随着对话发生变化，会话会发出 `history_updated`。如需请求更改历史记录，请使用 `updateHistory()`。它会要求传输层比较当前历史记录的差异并发送必要的删除/创建事件；当对应的对话事件从传输层返回时，本地 `session.history` 视图会随之更新。

#### 限制

1. 目前无法在函数工具调用完成后对其进行编辑。
2. 历史记录中的助手文本取决于可用的转录，包括 `output_audio.transcript`。
3. 因中断而截断的响应不会保留最终转录。
4. 最好将输入音频转录视为用户所说内容的大致参考，而不是模型如何理解音频的精确副本。
