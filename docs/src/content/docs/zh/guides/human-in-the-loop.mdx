本指南介绍 SDK 中基于审批的人机协作流程。当工具调用需要审批时，SDK 会暂停运行、返回 `interruptions`，并允许您稍后从同一 `RunState` 恢复运行。

该审批机制适用于整个运行，而不仅限于当前的顶层智能体。无论工具属于当前智能体、通过交接到达的智能体，还是嵌套的 `agent.asTool()` 执行，都适用同一模式。在嵌套的 `agent.asTool()` 场景中，中断仍会出现在外层运行中，因此您需要在外层 `result.state` 上批准或拒绝它，然后恢复原始根运行。

使用 `agent.asTool()` 时，审批可能发生在两个不同层级：智能体工具本身可以通过 `asTool({ needsApproval })` 要求审批；嵌套运行开始后，嵌套智能体中的工具也可能进一步发起各自的审批请求。两者都通过同一个外层运行中断流程处理。

本页重点介绍通过 `interruptions` 完成的手动审批流程。如果您的应用可以通过代码做出决定，某些工具类型还支持编程式审批回调，使运行无需暂停即可继续。如果您正在设置 `agent.asTool()` 本身，请参阅[工具指南](/openai-agents-js/zh/guides/tools#4-agents-as-tools)；本页介绍该运行层级结构中的任意工具需要审批后会发生什么。

### 流程

1. 当工具调用即将执行时，SDK 会评估其审批规则（`needsApproval` 或托管 MCP 的对应设置）。
2. 如果需要审批且尚未存储任何决定，工具调用不会执行。运行会改为记录一个 [`RunToolApprovalItem`](/openai-agents-js/openai/agents/classes/runtoolapprovalitem)。
3. 在该轮结束时，运行会暂停，并在[执行结果](/openai-agents-js/zh/guides/results)的 `interruptions` 数组中返回所有待处理的审批。这包括嵌套 `agent.asTool()` 运行中发起的审批。
4. 使用 `result.state.approve(interruption)` 或 `result.state.reject(interruption)` 处理每个待审批项。如果要在本次运行的剩余过程中始终批准或拒绝同一工具，请传入 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }`。拒绝时，您还可以传入 `{ message: '...' }`，以控制针对该特定工具调用发回给模型的拒绝文本。
5. 将更新后的 `result.state` 传回 `runner.run(agent, state)` 以恢复运行，其中 `agent` 是本次运行的原始顶层智能体。SDK 会从中断点继续执行，包括嵌套的智能体工具执行。

默认情况下，函数工具的输入护栏仅在审批后、工具即将执行前运行。如果您希望在显示待审批请求之前，使用相同的输入护栏验证本地函数工具调用，请向 `run()` 或 `Runner` 传入 `toolExecution: { preApprovalInputGuardrails: true }`。如果审批前护栏拒绝调用，SDK 会将护栏消息作为工具输出返回给模型，而不会创建审批中断。如果护栏允许调用，运行仍会暂停以等待审批；审批完成后，输入护栏会再次运行，以防工具调用在等待期间变得不安全。

当 `needsApproval` 是函数时，SDK 仅会在工具参数解析为可检查的对象后调用它。格式错误的 JSON 和非对象值会以安全拒绝方式处理：SDK 会请求审批，但不会调用回调或执行工具。即使批准该调用，工具仍不会执行；流程会继续进入常规的参数解析错误处理路径。实时函数工具遵循同一规则，并会针对无效调用发出 `tool_approval_requested`。

使用 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }` 创建的持续有效决定会存储在运行状态中，因此稍后恢复同一暂停运行时，这些决定可以在 `toString()` / `fromString()` 操作后保留。

在 GA 模型中，计算机工具中断可以表示单个 `computer_call` 中的一批操作。SDK 会在执行前针对每个操作评估 `needsApproval`，因此一个待审批项可以涵盖移动和点击等一系列操作。如果您检查 `interruption.rawItem` 来呈现 UI，请同时处理 GA 的 `actions` 数组和旧版的单个 `action` 字段。

序列化的 `RunState` 还会为当前的 `computer` 工具名称和旧版的 `computer_use_preview` 名称保留计算机操作审批，因此在从预览版迁移到 GA 期间，暂停的运行也能顺利恢复。

如果您未提供 `message`，SDK 会依次回退到已配置的 `toolErrorFormatter`（如有）和默认拒绝文本。

您不必在同一次处理中解决所有待审批项。如果仅批准或拒绝部分项目后重新运行，已处理的调用可以继续执行，而未处理的调用仍会保留在 `interruptions` 中，并再次暂停运行。

通过 `alwaysApprove: true` 或 `alwaysReject: true` 创建的持续有效决定，会作为后续同一工具调用的默认决定。针对某个调用 ID 的具体决定优先于该持续有效的默认决定：即使设置了持续批准，您仍可以拒绝某次调用；即使设置了持续拒绝，您也可以批准某次调用，而不会更改其他调用的默认决定。如果您之后替换该具体决定，新决定将应用于该调用，而持续有效的默认决定仍适用于其余调用。

### 恢复前的输入添加

如果运行暂停期间收到新的用户输入，并且应在下一次恢复后的模型调用前接纳该输入，请使用 `RunState.addInput()`。请先添加输入，然后处理审批，并将同一状态传回 `Runner.run()`。暂存的输入属于序列化状态的一部分，因此即使未处理的审批或本地工具工作延迟了该模型调用，它也可以在 `toString()` / `fromString()` 操作后保留。

读取 `state.pendingInput` 可检查暂存项目的克隆快照，也可以在恢复前调用 `state.clearPendingInput()` 将其全部移除。`addInput()` 接受字符串或输入项数组。当状态无法安全到达下一次模型调用时，例如状态已终止、没有剩余轮次，或某个中断的工具结果可能结束运行，它会抛出 `UserError`。

接纳后，每个暂存的输入都会成为运行的 `newItems` 中的一个 [`RunInputItem`](/openai-agents-js/openai/agents/classes/runinputitem)，其原始输入项则会包含在 `history` 中。使用本地 `session` 时，SDK 会在开始模型请求前将已接纳的输入持久化一次。使用 `conversationId` 或 `previousResponseId` 时，输入会保持待处理状态，直到服务器接受响应，因此如果已知故障发生在服务器接受响应之前，恢复时不会丢失输入。如果提供方报告请求可能已被接受，SDK 会为该次输入创建检查点并以安全拒绝方式终止，而不会在不提示的情况下重放。有关单独的、显式启用的不安全重放覆盖设置，请参阅[模型重试](/openai-agents-js/zh/guides/models#model-retries)。

### 自动审批决策

手动处理 `interruptions` 是最通用的模式，但并非唯一方式：

- 本地 `shellTool()` 和 `applyPatchTool()` 可以使用 `onApproval`，直接在代码中批准或拒绝。
- 托管 MCP 工具可以同时使用 `requireApproval` 和 `onApproval`，以相同方式进行编程式决策。
- 普通函数工具使用本页介绍的手动中断流程。

当这些回调返回决定时，运行会继续，而无需暂停等待人工响应。对于 Realtime 会话 API，请参阅[构建实时智能体指南](/openai-agents-js/zh/guides/voice-agents/build#approval-before-tool-execution)中的审批流程。

### 流式传输与会话

相同的中断流程也适用于流式运行。流式运行暂停后，请等待 `stream.completed`，读取 `stream.interruptions` 并处理它们；如果希望恢复后的输出继续以流式方式传输，请使用 `{ stream: true }` 再次调用 `run()`。有关此模式的流式版本，请参阅[流式传输期间的人机协作](/openai-agents-js/zh/guides/streaming#human-in-the-loop-while-streaming)。

如果您还使用 `session`，从 `RunState` 恢复时，请继续传入同一个 `session`。恢复后的轮次将追加到会话记忆中，无需重新准备输入。有关会话生命周期的详细信息，请参阅[会话指南](/openai-agents-js/zh/guides/sessions)。

## 较长审批时间的处理

人机协作流程支持长时间中断，而无需让服务器持续运行。如果您需要结束当前请求并在稍后继续，可以序列化状态并在之后恢复。

您可以使用 `result.state.toString()`（或 `JSON.stringify(result.state)`）序列化状态，之后再将序列化状态传入 `RunState.fromString(agent, serializedState)` 以恢复运行，其中 `agent` 是触发整个运行的智能体实例。

序列化 `RunState` 时，SDK 会记录交接和 `Agent.asTool()` 图中稳定的智能体身份标识。只要恢复运行的进程重新构建相同的智能体图，即使不同智能体具有相同的 `name`，暂停的运行也能恢复。

传入 `RunState.fromString(agent, serializedState)` 的 `agent` 是重新构建的智能体图的根。反序列化期间，SDK 会遍历该智能体的交接和 `Agent.asTool()` 引用，然后根据重新构建的图解析状态中每个已序列化的智能体引用。这包括当前智能体，以及生成项目、已处理的模型响应和排队等待执行的后续步骤所持有的嵌套引用。

如果您需要使用替代后的智能体图恢复运行，例如智能体的模型或工具已被其他运行时封装，请先使用原始智能体图反序列化状态，再次将其序列化，然后使用替代后的根智能体反序列化该字符串。调用 `state.setCurrentAgent(agent)` 只会更改当前活跃的智能体，不会重写反序列化期间已经解析的嵌套引用。

如果恢复运行的进程需要注入新的上下文对象，请改用 `RunState.fromStringWithContext(agent, serializedState, context, { contextStrategy })`。

- `contextStrategy: 'merge'`（默认）会保留所提供的 `RunContext`，合并序列化的审批状态，并在新上下文尚未定义 `toolInput` 时恢复已序列化的 `toolInput`。
- `contextStrategy: 'replace'` 会直接使用所提供的 `RunContext` 重新构建运行。

序列化的运行状态包括应用上下文，以及由 SDK 管理的运行时元数据，例如审批、用量、嵌套的 `toolInput` 和待恢复的嵌套智能体工具执行。如果您计划存储或传输序列化状态，请将 `runContext.context` 视为持久化数据；除非您有意让密钥随状态一起传输，否则请避免将密钥放入其中。

默认情况下，追踪 API 密钥不会包含在序列化状态中，以免您意外持久化密钥。仅当您确实需要随状态一起传输追踪凭据时，才传入 `result.state.toString({ includeTracingApiKey: true })`。

这样，您就可以将序列化状态存储在数据库中，或与请求一起存储。

### 待处理任务的版本管理

<Aside>
  这主要适用于您在更改智能体的同时，尝试将序列化状态存储 较长时间的情况。
</Aside>

如果审批请求需要较长时间，并且您计划以实质性方式对智能体定义进行版本管理，或升级 Agents SDK 版本，我们目前建议您使用包别名并行安装两个版本的 Agents SDK，从而实现自己的分支逻辑。

实际操作中，这意味着为您自己的代码分配版本号，将其与序列化状态一起存储，并引导反序列化流程使用正确的代码版本。
