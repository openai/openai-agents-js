本指南介绍 SDK 基于审批的人机协作流程。当工具调用需要审批时，SDK 会暂停运行、返回 `interruptions`，并允许您稍后从同一 `RunState` 恢复运行。

这种审批范围覆盖整个运行，并不局限于当前的顶层智能体。无论工具属于当前智能体、通过交接到达的智能体，还是嵌套的 `agent.asTool()` 执行，都适用相同的模式。在嵌套的 `agent.asTool()` 场景中，中断仍会出现在外层运行中，因此您需要在外层的 `result.state` 上批准或拒绝该中断，然后恢复原始的根运行。

使用 `agent.asTool()` 时，审批可能发生在两个不同层级：智能体工具本身可以通过 `asTool({ needsApproval })` 要求审批；嵌套运行开始后，嵌套智能体内部的工具也可能提出自己的审批请求。两者都通过同一个外层运行中断流程进行处理。

本页重点介绍通过 `interruptions` 实现的手动审批流程。如果您的应用可以通过代码做出决定，某些工具类型也支持编程式审批回调，使运行无需暂停即可继续。如果您正在配置 `agent.asTool()` 本身，请参阅[工具](/openai-agents-js/zh/guides/tools#4-agents-as-tools)；本页介绍该运行层级中的任意工具需要审批后会发生什么。

### 流程

1. 当工具调用即将执行时，SDK 会评估其审批规则（`needsApproval` 或托管 MCP 的对应设置）。
2. 如果需要审批且尚未存储任何决定，工具调用不会执行。运行会改为记录一个 [`RunToolApprovalItem`](/openai-agents-js/openai/agents/classes/runtoolapprovalitem)。
3. 在该轮结束时，运行会暂停，并在[执行结果](/openai-agents-js/zh/guides/results)的 `interruptions` 数组中返回所有待审批项。这包括嵌套 `agent.asTool()` 运行中提出的审批请求。
4. 使用 `result.state.approve(interruption)` 或 `result.state.reject(interruption)` 处理每个待审批项。如果要在此次运行的剩余时间内始终批准或拒绝同一工具，请传入 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }`。拒绝时，您还可以传入 `{ message: '...' }`，以控制针对该特定工具调用返回给模型的拒绝文本。
5. 将更新后的 `result.state` 传回 `runner.run(agent, state)` 以恢复运行，其中 `agent` 是此次运行最初的顶层智能体。SDK 会从中断点继续执行，包括嵌套的智能体工具执行。

默认情况下，函数工具输入护栏仅在审批通过后、工具即将执行前运行。如果您希望在显示待审批项之前，使用相同的输入护栏验证本地函数工具调用，请将 `toolExecution: { preApprovalInputGuardrails: true }` 传给 `run()` 或 `Runner`。如果审批前护栏拒绝调用，SDK 会将护栏消息作为工具输出返回给模型，而不是创建审批中断。如果护栏允许该调用，运行仍会暂停以等待审批；审批通过后，输入护栏还会再次运行，以防工具调用在等待期间变得不安全。

当 `needsApproval` 是函数时，SDK 只会在工具参数解析为可检查对象后调用它。对于格式错误的 JSON 和非对象值，SDK 会以安全失败方式处理：请求审批，但不调用回调，也不执行工具。即使批准该调用，工具仍不会执行；流程会继续进入正常的参数解析错误路径。实时函数工具遵循相同规则，并会针对无效调用发出 `tool_approval_requested`。

使用 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }` 创建的持久性决定会存储在运行状态中，因此稍后恢复同一个已暂停运行时，这些决定可在 `toString()` / `fromString()` 后保留。

在 GA 模型中，计算机工具中断可以表示单个 `computer_call` 中的一批操作。SDK 会在执行前逐个操作评估 `needsApproval`，因此一个待审批项可以覆盖移动加点击等操作序列。如果您通过检查 `interruption.rawItem` 来渲染 UI，请同时处理 GA 版本的 `actions` 数组和旧版的单个 `action` 字段。

序列化的 `RunState` 还会同时保留当前 `computer` 工具名称和旧版 `computer_use_preview` 名称对应的计算机操作审批，因此在从预览版迁移到 GA 期间，暂停的运行也能正常恢复。

如果您没有提供 `message`，SDK 会依次回退到配置的 `toolErrorFormatter`（如果有），然后使用默认拒绝文本。

您无需在同一次处理中解决所有待审批项。如果只批准或拒绝其中一些项目后重新运行，已处理的调用可以继续执行，而未处理的项目仍会保留在 `interruptions` 中并再次暂停运行。

### 恢复前的输入添加

当运行暂停期间收到新的用户输入，并且该输入需要在下一次恢复后的模型调用之前纳入处理时，请使用 `RunState.addInput()`。先添加输入，再处理审批项并将同一状态传回 `Runner.run()`。暂存的输入是序列化状态的一部分，因此即使未处理的审批项或本地工具工作延迟了该模型调用，它也能在 `toString()` / `fromString()` 后保留。

读取 `state.pendingInput` 可检查暂存项的克隆快照，也可以在恢复前调用 `state.clearPendingInput()` 将它们全部移除。`addInput()` 接受字符串或输入项数组。如果状态无法安全到达下一次模型调用，它会引发 `UserError`，例如状态已经终止、没有剩余轮次，或者某个中断的工具结果可能会结束运行。

纳入处理后，每个暂存项都会成为运行的 `newItems` 中的一个 [`RunInputItem`](/openai-agents-js/openai/agents/classes/runinputitem)，其原始输入项则会包含在 `history` 中。使用本地 `session` 时，SDK 会在开始模型请求前持久化一次已纳入的输入。使用 `conversationId` 或 `previousResponseId` 时，该输入会保持待处理状态，直到服务器接受响应；因此，如果已知故障发生在接受之前，便可以恢复运行而不丢失输入。如果提供方报告该请求可能已经被接受，SDK 会为该次输入建立检查点并以安全失败方式终止，而不是静默重放。有关独立且显式的不安全重放覆盖选项，请参阅[模型重试](/openai-agents-js/zh/guides/models#model-retries)。

### 自动审批决策

手动处理 `interruptions` 是最通用的模式，但并非唯一模式：

- 本地 `shellTool()` 和 `applyPatchTool()` 可以使用 `onApproval`，直接在代码中批准或拒绝。
- 托管 MCP 工具可以结合使用 `requireApproval` 和 `onApproval`，实现相同类型的编程式决策。
- 普通函数工具使用本页介绍的手动中断流程。

当这些回调返回决定时，运行无需暂停等待人工响应即可继续。对于 Realtime 会话 API，请参阅[构建实时智能体](/openai-agents-js/zh/guides/voice-agents/build#approval-before-tool-execution)中的审批流程。

### 流式传输与会话

相同的中断流程也适用于流式运行。流式运行暂停后，等待 `stream.completed`，读取 `stream.interruptions` 并处理这些中断；如果您希望恢复后的输出继续以流式传输方式返回，请再次调用 `run()` 并传入 `{ stream: true }`。有关此模式的流式版本，请参阅[流式传输期间的人机协作](/openai-agents-js/zh/guides/streaming#human-in-the-loop-while-streaming)。

如果您还在使用 `session`，从 `RunState` 恢复时，请继续传入同一个 `session`。恢复后的轮次会追加到会话记忆中，而无需重新准备输入。有关会话生命周期的详细信息，请参阅[会话](/openai-agents-js/zh/guides/sessions)。

## 长时间审批的处理

人机协作流程支持长时间中断，无需让服务器持续运行。如果您需要结束当前请求并在以后继续，可以序列化状态并稍后恢复。

您可以使用 `result.state.toString()`（或 `JSON.stringify(result.state)`）序列化状态，之后将序列化状态传入 `RunState.fromString(agent, serializedState)` 以恢复运行，其中 `agent` 是触发整个运行的智能体实例。

序列化 `RunState` 时，SDK 会记录交接和 `Agent.asTool()` 图中的稳定智能体标识。只要恢复运行的进程重新构建相同的智能体图，即使不同智能体使用相同的 `name`，暂停的运行也能恢复。

传给 `RunState.fromString(agent, serializedState)` 的 `agent` 是重建图的根节点。反序列化期间，SDK 会遍历该智能体的交接和 `Agent.asTool()` 引用，然后将状态中的每个序列化智能体引用解析到重建图中。这包括当前智能体，以及生成项、已处理的模型响应和已排队后续步骤中保存的嵌套引用。

如果需要使用替换后的图恢复运行，例如某些智能体的模型或工具已由其他运行时封装，请先使用原始图反序列化状态，再次将其序列化，然后使用替换后的根智能体反序列化该字符串。调用 `state.setCurrentAgent(agent)` 只会更改当前活动智能体，不会重写反序列化期间已解析的嵌套引用。

如果恢复运行的进程需要注入新的上下文对象，请改用 `RunState.fromStringWithContext(agent, serializedState, context, { contextStrategy })`。

- `contextStrategy: 'merge'`（默认）会保留所提供的 `RunContext`、合并序列化的审批状态，并在新上下文尚未定义 `toolInput` 时恢复序列化的 `toolInput`。
- `contextStrategy: 'replace'` 会直接使用所提供的 `RunContext` 重建运行。

序列化运行状态包含您的应用上下文，以及由 SDK 管理的运行时元数据，例如审批、用量、嵌套的 `toolInput` 和待恢复的嵌套智能体工具执行。如果您计划存储或传输序列化状态，请将 `runContext.context` 视为持久化数据；除非您有意让密钥随状态一起传输，否则请避免将密钥放入其中。

默认情况下，追踪 API 密钥不会包含在序列化状态中，以免意外持久化密钥。只有在确实需要让追踪凭据随状态一起转移时，才应传入 `result.state.toString({ includeTracingApiKey: true })`。

这样，您便可以将序列化状态存储在数据库中，或与请求一起保存。

### 待处理任务的版本管理

<Aside>
  这主要适用于您需要较长时间存储序列化状态，同时还要更改 智能体的情况。
</Aside>

如果审批请求需要较长时间处理，并且您打算以有实际意义的方式管理智能体定义版本，或升级 Agents SDK 版本，目前建议您使用软件包别名并行安装两个版本的 Agents SDK，以实现自己的分支逻辑。

实际操作中，这意味着为您自己的代码分配版本号，将其与序列化状态一起存储，并引导反序列化过程使用正确的代码版本。
