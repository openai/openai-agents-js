本指南介绍 SDK 基于审批的人机协作流程。当工具调用需要审批时，SDK 会暂停运行、返回 `interruptions`，并允许您稍后从同一 `RunState` 恢复运行。

该审批机制适用于整个运行过程，不局限于当前的顶层智能体。无论工具属于当前智能体、通过交接到达的智能体，还是嵌套的 `agent.asTool()` 执行，都适用相同的模式。对于嵌套的 `agent.asTool()`，中断仍会出现在外层运行中，因此您需要在外层的 `result.state` 上批准或拒绝中断，然后恢复原始的根运行。

使用 `agent.asTool()` 时，审批可能发生在两个不同层级：智能体工具本身可以通过 `asTool({ needsApproval })` 要求审批；嵌套智能体中的工具也可能在嵌套运行开始后提出自己的审批请求。两者都通过相同的外层运行中断流程进行处理。

本页重点介绍通过 `interruptions` 实现的手动审批流程。如果您的应用可以通过代码作出决定，某些工具类型还支持编程式审批回调，使运行无需暂停即可继续。如果您正在设置 `agent.asTool()` 本身，请参阅[工具](/openai-agents-js/zh/guides/tools#4-agents-as-tools)；本页介绍该运行层级中的任何工具需要审批后会发生什么。

### 流程

1. 当工具调用即将执行时，SDK 会评估其审批规则（`needsApproval` 或托管 MCP 的对应规则）。
2. 如果需要审批且尚未存储决定，则不会执行工具调用。运行会改为记录一个 [`RunToolApprovalItem`](/openai-agents-js/openai/agents/classes/runtoolapprovalitem)。
3. 在该轮结束时，运行会暂停，并在[执行结果](/openai-agents-js/zh/guides/results)的 `interruptions` 数组中返回所有待处理审批。这包括嵌套 `agent.asTool()` 运行中提出的审批请求。
4. 使用 `result.state.approve(interruption)` 或 `result.state.reject(interruption)` 处理每个待处理项。如果希望在本次运行的其余过程中始终批准或拒绝同一工具，请传入 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }`。拒绝时，您还可以传入 `{ message: '...' }`，以控制针对该工具调用返回给模型的拒绝文本。
5. 将更新后的 `result.state` 传回 `runner.run(agent, state)` 以恢复运行，其中 `agent` 是本次运行的原始顶层智能体。SDK 会从中断处继续执行，包括嵌套的智能体工具执行。

默认情况下，函数工具输入护栏仅在获得批准后、工具即将执行前运行。如果您希望在显示待处理审批前，使用相同的输入护栏验证本地函数工具调用，请向 `run()` 或 `Runner` 传入 `toolExecution: { preApprovalInputGuardrails: true }`。当审批前护栏拒绝调用时，SDK 会将护栏消息作为工具输出返回给模型，而不是创建审批中断。当护栏允许调用时，运行仍会暂停以等待审批；批准后，输入护栏会再次运行，以防工具调用在等待期间变得不安全。

当 `needsApproval` 是函数时，SDK 仅会在工具参数解析为可检查对象后调用它。对于格式错误的 JSON 和非对象值，SDK 会采取安全失败策略：请求审批，但不会调用回调或执行工具。即使批准该调用，工具仍不会执行；调用会继续进入正常的参数解析错误流程。Realtime 函数工具遵循相同规则，并会为无效调用发出 `tool_approval_requested`。

通过 `{ alwaysApprove: true }` 或 `{ alwaysReject: true }` 创建的持续有效决定会存储在运行状态中，因此稍后恢复同一暂停运行时，这些决定可以通过 `toString()` / `fromString()` 保留下来。

在 GA 模型上，计算机工具中断可以表示单个 `computer_call` 中的一批操作。SDK 会在执行前逐项评估 `needsApproval`，因此一个待处理审批可以涵盖移动并点击等操作序列。如果您检查 `interruption.rawItem` 以呈现 UI，请同时处理 GA 的 `actions` 数组和旧版的单个 `action` 字段。

序列化的 `RunState` 还会保留当前 `computer` 工具名称和旧版 `computer_use_preview` 名称下的计算机操作审批，因此暂停的运行可以在从预览版迁移到 GA 版本期间顺利恢复。

如果您未提供 `message`，SDK 会依次回退到已配置的 `toolErrorFormatter`（如果有）和默认拒绝文本。

您无需一次处理所有待处理审批。如果仅批准或拒绝部分项目后重新运行，已处理的调用可以继续执行，而未处理的调用会保留在 `interruptions` 中，并再次暂停运行。

通过 `alwaysApprove: true` 或 `alwaysReject: true` 创建的持续有效决定，会作为之后调用同一工具时的默认决定。针对某个调用 ID 的精确决定优先于该持续有效的默认决定：即使设置了持续批准，您也可以拒绝某次调用；即使设置了持续拒绝，您也可以批准某次调用，而不会更改其他调用的默认决定。如果稍后替换了该精确决定，新决定将应用于该调用，而持续有效的默认决定仍可用于其余调用。

### 恢复前的输入添加

当运行暂停期间有新的用户输入到达，并且应在下一次恢复后的模型调用前纳入时，请使用 `RunState.addInput()`。在处理审批并将同一状态传回 `Runner.run()` 之前添加输入。暂存的输入是序列化状态的一部分，因此即使未处理的审批或本地工具工作延迟了该模型调用，它也能通过 `toString()` / `fromString()` 保留下来。

读取 `state.pendingInput` 可以检查暂存项的克隆快照；也可以在恢复前调用 `state.clearPendingInput()` 将其全部移除。`addInput()` 接受字符串或输入项数组。当状态无法安全地到达另一次模型调用时，例如状态已终止、没有剩余轮次，或某个中断的工具结果可能结束运行时，它会引发 `UserError`。

纳入后，每个暂存输入实例都会成为运行的 `newItems` 中的一个 [`RunInputItem`](/openai-agents-js/openai/agents/classes/runinputitem)，其原始输入项则会包含在 `history` 中。使用本地 `session` 时，SDK 会在启动模型请求前将纳入的输入持久化一次。使用 `conversationId` 或 `previousResponseId` 时，输入会保持待处理状态，直到服务器接受响应；因此，如果已知故障发生在接受之前，则可在不丢失输入的情况下恢复。如果提供方报告请求可能已被接受，SDK 会为该输入实例创建检查点并采取安全失败策略，而不会静默重放。有关单独且明确的不安全重放覆盖选项，请参阅[模型重试](/openai-agents-js/zh/guides/models#model-retries)。

### 自动审批决定

手动 `interruptions` 是最通用的模式，但并非唯一模式：

- 本地 `shellTool()` 和 `applyPatchTool()` 可以使用 `onApproval`，立即在代码中批准或拒绝。
- 远程 MCP 服务器工具可以结合使用 `requireApproval` 和 `onApproval`，作出同类的编程式决定。
- 普通函数工具使用本页介绍的手动中断流程。

当这些回调返回决定时，运行会继续，而无需暂停等待人工响应。对于 Realtime 会话 API，请参阅[构建语音智能体](/openai-agents-js/zh/guides/voice-agents/build#approval-before-tool-execution)中的审批流程。

### 流式传输与会话

相同的中断流程也适用于流式运行。流式运行暂停后，请等待 `stream.completed`，读取 `stream.interruptions` 并处理它们；如果希望恢复后的输出继续进行流式传输，请使用 `{ stream: true }` 再次调用 `run()`。有关此模式的流式版本，请参阅[流式传输中的人机协作](/openai-agents-js/zh/guides/streaming#human-in-the-loop-while-streaming)。

如果您同时使用 `session`，从 `RunState` 恢复时请继续传入同一个 `session`。随后，恢复的轮次会追加到会话记忆中，而无需重新准备输入。有关会话生命周期的详细信息，请参阅[会话](/openai-agents-js/zh/guides/sessions)。

## 较长审批时间的处理

人机协作流程的设计支持长时间中断，而无需让服务器持续运行。如果您需要关闭请求并稍后继续，可以序列化状态并在之后恢复。

您可以使用 `result.state.toString()`（或 `JSON.stringify(result.state)`）序列化状态，之后再将序列化状态传入 `RunState.fromString(agent, serializedState)` 以恢复运行，其中 `agent` 是触发整个运行的智能体实例。

当已批准的函数工具结果可能成为运行的最终输出时，输出护栏会施加更严格的恢复边界。当 SDK 能够确定归属关系时，当前的 `RunState` 模式会记录当前响应所生成项的确切归属关系，因此受支持且可能产生输出的部分审批检查点可以通过序列化状态完成往返转换。SDK 会在进一步产生模型、工具或会话副作用之前验证该归属关系。对于缺少归属关系、归属关系无效或存在歧义的旧快照和检查点，仍会采取安全失败策略并引发 `UserError`。发生这种情况时，请基于安全输入开始新的运行。请重新构建相同的智能体图，并保留原始 `toolUseBehavior`；不要通过重放原始项来规避归属关系错误。

序列化 `RunState` 时，SDK 会记录交接和 `Agent.asTool()` 图中稳定的智能体标识。这样，即使不同智能体具有相同的 `name`，暂停的运行仍可恢复，前提是恢复运行的进程重新构建了相同的智能体图。

传入 `RunState.fromString(agent, serializedState)` 的 `agent` 是重建图的根节点。反序列化期间，SDK 会遍历该智能体的交接和 `Agent.asTool()` 引用，然后将状态中的每个序列化智能体引用解析到重建图中。这包括当前智能体，以及生成项、已处理的模型响应和排队的后续步骤所持有的嵌套引用。

如果需要使用替换后的图恢复运行，例如智能体的模型或工具已由另一个运行时包装，请先使用原始图反序列化状态，再次将其序列化，然后使用替换后的根智能体反序列化该字符串。调用 `state.setCurrentAgent(agent)` 只会更改活动智能体，不会重写反序列化期间已解析的嵌套引用。

如果恢复运行的进程需要注入新的上下文对象，请改用 `RunState.fromStringWithContext(agent, serializedState, context, { contextStrategy })`。

- `contextStrategy: 'merge'`（默认）会保留提供的 `RunContext`，合并序列化的审批状态，并在新上下文尚未定义 `toolInput` 时恢复序列化的 `toolInput`。
- `contextStrategy: 'replace'` 会直接使用提供的 `RunContext` 重新构建运行。

序列化的运行状态包括您的应用上下文，以及由 SDK 管理的运行时元数据，例如审批、用量、嵌套的 `toolInput` 和待处理的嵌套智能体工具恢复信息。如果您计划存储或传输序列化状态，请将 `runContext.context` 视为持久化数据；除非您有意让密钥随状态一起传输，否则请避免将密钥放入其中。

默认情况下，追踪 API 密钥不会包含在序列化状态中，以免您意外持久化密钥。仅当确实需要随状态传输追踪凭据时，才传入 `result.state.toString({ includeTracingApiKey: true })`。

请将序列化状态存储在由应用控制的存储中，例如服务器端数据库。

### 服务器端审批状态的保留

序列化的 `RunState` 包含执行状态，其中包括审批决定、待处理工具调用、工具参数和应用上下文。`RunState.fromString()` 会恢复该状态；该方法不会对快照或提交快照的人员进行身份验证。只有当快照来自可信存储，或您的应用已验证完整快照的完整性、归属和重放保护时，才能对其进行反序列化。模式验证和工具调用指纹无法验证快照的真实性。SDK 中对智能体或生成项归属关系的引用也不能为应用用户授予权限。

对于浏览器或移动端审批界面，请将完整快照保存在由应用控制的服务器存储中。仅向审核者发送已获授权的展示详情，以及待处理决定的不透明标识符。运行 ID 或决定 ID 不能作为授权证明。请将工具名称和参数视为不可信的展示内容：过滤敏感值，并在渲染 HTML 时对内容进行转义。将完整的运行结果和错误保留在服务器上，仅向客户端返回应用选择的输出。

收到决定后，服务器必须：

1. 使用应用的会话或身份验证中间件对审核者进行身份验证。切勿从审批请求正文中获取已验证身份。
2. 根据存储的运行和所选待处理调用，验证审核者的权限。
3. 根据服务器上存储的待处理请求验证决定标识符和布尔决定。不要接受来自客户端的替换工具调用、参数、审批记录或序列化状态。
4. 在反序列化和恢复执行之前，以原子方式检查归属并消费待处理请求。并发提交或重放提交不得导致同一快照恢复两次。在共享存储中，请使用事务或等效的原子条件转换。
5. 加载服务器持有的快照，使用 `state.getInterruptions()` 获取待处理项，并且在恢复运行前，仅对这些项目应用 `state.approve()` 或 `state.reject()`。

### 待处理任务的版本控制

<Aside>这主要适用于您尝试长期存储序列化状态，同时又在修改智能体的情况。</Aside>

如果审批请求需要较长时间处理，并且您计划以有意义的方式对智能体定义进行版本控制，或升级 Agents SDK 版本，我们目前建议您使用软件包别名并行安装两个版本的 Agents SDK，以实现自己的分支逻辑。

实际上，这意味着为您自己的代码分配版本号，将该版本号与序列化状态一同存储，并在反序列化时引导系统使用正确版本的代码。
