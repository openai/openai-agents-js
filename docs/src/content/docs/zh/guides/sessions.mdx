会话为 Agents SDK 提供了一个**持久化记忆层**。向 `Runner.run` 提供任何实现 `Session` 接口的对象，其余工作由 SDK 处理。存在会话时，运行器会自动：

1. 获取之前存储的对话项，并将其添加到下一轮输入之前。
2. 在每次运行完成后持久化新的用户输入和助手输出。
3. 保留会话以供后续轮次使用，无论您是使用新的用户文本调用运行器，还是从中断的 `RunState` 恢复运行。

这样便无需手动调用 `toInputList()`，也不必在各轮之间拼接历史记录。TypeScript SDK 提供了两种实现：用于 Conversations API 的 `OpenAIConversationsSession`，以及面向本地开发的 `MemorySession`。由于它们共用 `Session` 接口，您也可以接入自己的存储后端。除 Conversations API 外，您还可以查看 `examples/memory/` 下的示例会话后端以获取灵感（Prisma、文件后端等）。使用 OpenAI Responses 模型时，可用 `OpenAIResponsesCompactionSession` 包装任何会话，通过 [`responses.compact`](https://platform.openai.com/docs/api-reference/responses/compact) 自动缩减存储的对话历史记录。

> 提示：要运行本页中的 `OpenAIConversationsSession` 示例，请设置 `OPENAI_API_KEY` 环境变量（或在构造会话时提供 `apiKey`），以便 SDK 调用 Conversations API。

如果您希望 SDK 代为管理客户端侧记忆，请使用会话。如果您已经通过 `conversationId` 或 `previousResponseId` 使用 OpenAI 服务器管理的状态，则通常无需再为同一对话历史记录使用会话。

## 核心会话行为

### 运行器对会话的使用

- **每次运行之前**，运行器会检索会话历史记录，将其与新一轮输入合并，然后把合并后的列表传递给智能体。
- **非流式运行之后**，运行器会调用一次 `session.addItems()`，同时持久化原始用户输入和最新一轮的模型输出。
- **对于流式运行**，运行器会先写入用户输入，并在该轮完成后追加流式输出。
- **从 `RunResult.state` 恢复运行时**（用于审批或其他中断），请继续传入同一个 `session`。恢复后的轮次会被添加到记忆中，无需重新准备输入。

自定义会话允许您强制执行保留策略、添加加密，或在持久化前为每轮对话附加元数据。

### 自定义持久化的原子性与幂等性

对于能够以原子方式更新历史记录并记录操作标识符的后端，请实现可选的 `SessionHistoryTransactionAwareSession` 接口。其 `applyHistoryTransaction(...)` 方法会接收一个稳定的 `operationId` 和以下两种事务结构之一：

- `append_items` 追加一组历史记录项。
- `replace_suffix` 仅在当前存储的后缀仍然匹配时，替换预期的历史记录后缀。

请在同一个后端事务中持久化操作标识符和历史记录变更。使用相同事务重复提交同一操作标识符时，必须成功且不能重复应用。使用不同内容复用该标识符，或在预期后缀发生变化后应用 `replace_suffix`，必须失败且不能更改历史记录。这样，运行器便可在重试和可恢复的输出护栏流程中安全地协调持久化输出。

`MemorySession` 实现了此约定，可作为参考。现有的 `Session` 实现即使不支持此约定也仍然有效，但不会启用事务感知的持久化路径。

### 使用运行上下文确定自定义会话作用域

当自定义会话需要使用当前 `RunContext` 进行存储路由或添加元数据时，请实现 `RunContextAwareSession<TContext>`，并将 `acceptsRunContext` 设置为 `true`。在一次运行期间，运行器会将同一个上下文实例传递给所有历史记录操作，包括流式持久化和恢复运行。仅实现 `Session` 的会话会保留现有的方法签名，并且调用时不会传入额外参数。

## 高级功能：历史记录压缩

### OpenAI Responses 历史记录的自动压缩

`OpenAIResponsesCompactionSession` 可包装任何 `Session`，并使用 OpenAI Responses API 将较长的已存储历史记录替换为更短但等效的对话项列表。每一轮持久化后，运行器都会将最新的 `responseId` 传入 `runCompaction`；当您的决策钩子返回 true 时，它会调用 `responses.compact`。根据 `compactionMode`，请求会基于最新的 Responses API 链或会话的当前项目构建。默认触发器会在累积至少 10 个非用户项目后执行压缩；您可以覆盖 `shouldTriggerCompaction`，根据 token 数量或自定义启发式规则作出决定。压缩返回后，装饰器会清除底层会话，并使用精简后的项目列表重写会话。因此，请避免将其与 `OpenAIConversationsSession` 搭配使用，后者采用不同的服务器管理历史记录流程。

`OpenAIResponsesCompactionSession` 构造函数选项：

| 选项 | 类型 | 说明 |
| --- | --- | --- |
| `client` | `OpenAI` | 用于 `responses.compact` 的 OpenAI 客户端。 |
| `underlyingSession` | `Session` | 用于清除并以压缩项目重写的底层会话存储。演示中默认为内存会话，且不得为 `OpenAIConversationsSession`。 |
| `model` | `OpenAI.ResponsesModel` | 用于压缩请求的模型。默认为 SDK 当前的默认 OpenAI 模型。 |
| `compactionMode` | `'auto' \| 'previous_response_id' \| 'input'` | 控制压缩使用服务器响应链还是本地输入项目。 |
| `shouldTriggerCompaction` | `(context) => boolean \| Promise<boolean>` | 自定义触发钩子，根据 `responseId`、`compactionMode`、候选项目和当前会话项目作出决定。 |

当您已使用 Responses API 响应 ID 串联各轮时，`compactionMode: 'previous_response_id'` 很有用。 `compactionMode: 'input'` 则会基于当前会话项目重新构建压缩请求，适用于响应链不可用，或希望将底层会话内容作为事实来源的情况。

`runCompaction(args)` 选项：

| 选项 | 类型 | 说明 |
| --- | --- | --- |
| `responseId` | `string` | `previous_response_id` 模式下最新的 Responses API 响应 ID。 |
| `compactionMode` | `'auto' \| 'previous_response_id' \| 'input'` | 可选的单次调用模式覆盖设置。 |
| `store` | `boolean` | 指示上一次运行是否存储了服务器状态。 |
| `force` | `boolean` | 绕过 `shouldTriggerCompaction` 并立即压缩。 |

`OpenAIResponsesCompactionSession` 会将通过同一个包装器实例发起的变更串行化。对 `runCompaction()`、`addItems()`、`popItem()` 和 `clearSession()` 的调用会按调用顺序运行，即使某项操作被拒绝，队列也会继续执行，因此后续包装器变更不会与替换或回滚操作交错。成功的替换或回滚会使包装器缓存的历史记录与底层会话保持一致。如果替换和恢复均失败，请先恢复底层会话再继续。此顺序保证不会协调其他包装器实例或对 `underlyingSession` 的直接变更；请在应用中协调这些访问路径。

#### 低延迟流式传输的手动压缩

压缩会清除并重写底层会话，因此 SDK 会等待压缩完成后才结束流式运行。如果压缩任务较重，最后一个输出 token 产生后，`result.completed` 可能仍会保持待定状态数秒。对于低延迟流式传输或更快速的轮次交互，请禁用自动压缩，并在各轮之间（或空闲时）自行调用 `runCompaction`。

您可以随时调用 `runCompaction({ force: true })`，在归档或交接前缩减历史记录。使用 `DEBUG=openai-agents:openai:compaction` 启用调试日志，以追踪压缩决策。
