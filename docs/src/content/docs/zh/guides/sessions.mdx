会话为 Agents SDK 提供了一个**持久化记忆层**。将任何实现了 `Session` 接口的对象传给 `Runner.run`，SDK 就会处理其余工作。使用会话时，运行器会自动：

1. 获取先前存储的对话条目，并将其添加到下一轮输入的开头。
2. 在每次运行完成后，持久化新的用户输入和助手输出。
3. 保留会话以供后续轮次使用，无论您是使用新的用户文本调用运行器，还是从中断的 `RunState` 恢复运行。

这样就无需手动调用 `toInputList()`，也不必在轮次之间拼接历史记录。TypeScript SDK 内置了两种实现：面向 Conversations API 的 `OpenAIConversationsSession`，以及用于本地开发的 `MemorySession`。由于它们共用 `Session` 接口，您可以接入自己的存储后端。如果希望参考 Conversations API 之外的方案，可以查看 `examples/memory/` 下的会话后端代码示例（Prisma、基于文件的存储等）。使用 OpenAI Responses 模型时，可以通过 `OpenAIResponsesCompactionSession` 包装任意会话，利用 [`responses.compact`](https://platform.openai.com/docs/api-reference/responses/compact) 自动压缩已存储的对话历史记录。

> 提示：要运行本页中的 `OpenAIConversationsSession` 代码示例，请设置 `OPENAI_API_KEY` 环境变量（或在构造会话时提供 `apiKey`），以便 SDK 调用 Conversations API。

如果希望 SDK 为您管理客户端记忆，请使用会话。如果您已经通过 `conversationId` 或 `previousResponseId` 使用 OpenAI 服务器管理的状态，通常就不需要再使用会话来管理同一份对话历史记录。

## 会话的核心行为

### 运行器如何使用会话

- **每次运行前**，运行器会获取会话历史记录，将其与新一轮的输入合并，并将合并后的列表传给智能体。
- **非流式运行结束后**，运行器会通过一次 `session.addItems()` 调用，同时持久化原始用户输入和最新一轮的模型输出。
- **对于流式运行**，运行器会先写入用户输入，并在该轮完成后追加流式输出。
- **从 `RunResult.state` 恢复时**（用于审批或其他中断），请继续传入同一个 `session`。恢复的轮次会被添加到记忆中，而不会重新准备输入。

当输出护栏拒绝作为最终输出的函数工具结果时，运行器不会将被拒绝的原始结果添加到新的会话历史记录中。对于已识别的函数调用及其结果对，运行器会持久化一个可安全重放的占位内容；对于归属不明确的当前响应尾部条目，则会将其省略，而不是存储无法确认归属的输出。这项保护不会撤销外部工具的副作用，也不会清除应用在会话处理流程之外存储的数据。

自定义会话允许您在持久化之前实施保留策略、添加加密，或为每一轮对话附加元数据。

### 确保自定义持久化的原子性和幂等性

如果后端能够以原子方式更新历史记录并记录操作标识符，请实现可选的 `SessionHistoryTransactionAwareSession` 接口。其 `applyHistoryTransaction(...)` 方法接收一个固定的 `operationId`，以及以下两种事务形式之一：

- `append_items` 追加一组历史记录条目。
- `replace_suffix` 仅在当前存储的历史记录后缀仍与预期匹配时，才替换该后缀。

请在同一个后端事务中持久化操作标识符和历史记录变更。使用相同的操作标识符重复提交同一事务时，必须成功，但不能重复应用该事务。使用相同标识符提交不同内容，或在预期后缀已发生变化后应用 `replace_suffix` 时，必须失败，且不得更改历史记录。这样，运行器就能在重试和可恢复的输出护栏流程中，安全地协调已持久化的输出。

`MemorySession` 实现了这一约定，可供参考。现有的 `Session` 实现即使不实现此接口也仍然有效，但不会启用支持事务的持久化路径。

### 使用运行上下文限定自定义会话的作用域

当自定义会话需要使用当前的 `RunContext` 来进行存储路由或处理元数据时，请实现 `RunContextAwareSession<TContext>`，并将 `acceptsRunContext` 设为 `true`。运行器会将同一个上下文实例传给一次运行中的所有历史记录操作，包括流式持久化和恢复运行中的操作。仅实现 `Session` 的会话会保留现有的方法签名，调用时不会传入额外参数。

当您从先前的 `RunState` 恢复时，新一轮会追加到同一份记忆记录中，以保持单一的对话历史记录。大多数人工干预（HITL）审批检查点都通过 `RunState` 完成往返传递，同时由会话保持对话历史记录的完整性。

当获批的函数工具结果可能成为最终输出时，输出护栏会施加更严格的边界限制。当前的 `RunState` 模式会在 SDK 能够确认归属时，准确记录当前响应中生成条目的归属，使受支持的、包含输出的审批检查点能够在保持会话历史记录完整的情况下恢复运行。在产生进一步的模型、工具或会话副作用之前，SDK 会验证这些归属信息。对于旧版快照，以及归属信息缺失、无效或不明确的检查点，SDK 仍会拒绝继续执行，以确保安全。当 SDK 报告此情况时，请从安全的输入开始一次新运行；不要通过重放原始条目来绕过这一限制。

## 进阶：历史记录压缩

### 自动压缩 OpenAI Responses 历史记录

`OpenAIResponsesCompactionSession` 可包装任意 `Session`，并使用 OpenAI Responses API 将较长的已存储历史记录替换为更短的等效对话条目列表。每轮持久化后，运行器都会将最新的 `responseId` 传入 `runCompaction`；当您的决策钩子返回 true 时，该方法会调用 `responses.compact`。根据 `compactionMode` 的设置，请求会基于最新的 Responses API 响应链或会话的当前条目构建。默认触发条件是在累积至少 10 个非用户条目后进行压缩；您可以覆盖 `shouldTriggerCompaction`，根据 token 数量或自定义启发式规则做出决策。压缩返回后，包装器会清空底层会话，并写入精简后的条目列表，因此请避免将其与 `OpenAIConversationsSession` 搭配使用，后者采用的是另一套服务器端历史记录管理流程。

  title="使用 OpenAIResponsesCompactionSession 包装会话"
/>

`OpenAIResponsesCompactionSession` 构造函数选项：

| 选项 | 类型 | 说明 |
| --- | --- | --- |
| `client` | `OpenAI` | 用于调用 `responses.compact` 的 OpenAI 客户端。 |
| `underlyingSession` | `Session` | 用于存储的底层会话，压缩后会被清空并写入压缩后的条目。默认为供演示使用的内存会话，且不能是 `OpenAIConversationsSession`。 |
| `model` | `OpenAI.ResponsesModel` | 用于压缩请求的模型。默认为 SDK 当前的默认 OpenAI 模型。 |
| `compactionMode` | `'auto' \| 'previous_response_id' \| 'input'` | 控制压缩使用服务器端响应链还是本地输入条目。 |
| `shouldTriggerCompaction` | `(context) => boolean \| Promise<boolean>` | 自定义触发钩子，可根据 `responseId`、`compactionMode`、候选条目和当前会话条目做出决策。 |

如果您已经使用 Responses API 响应 ID 将各轮串联起来，`compactionMode: 'previous_response_id'` 会很有用。`compactionMode: 'input'` 则会根据当前会话条目重新构建压缩请求，适用于响应链不可用，或希望以底层会话内容为准的情况。

`runCompaction(args)` 选项：

| 选项 | 类型 | 说明 |
| --- | --- | --- |
| `responseId` | `string` | 用于 `previous_response_id` 模式的最新 Responses API 响应 ID。 |
| `compactionMode` | `'auto' \| 'previous_response_id' \| 'input'` | 可选，用于在本次调用中覆盖已配置的模式。 |
| `store` | `boolean` | 指示上一次运行是否存储了服务器状态。 |
| `force` | `boolean` | 跳过 `shouldTriggerCompaction` 并立即压缩。 |

`OpenAIResponsesCompactionSession` 会串行执行通过同一包装器实例发起的变更操作。对 `runCompaction()`、`addItems()`、`popItem()` 和 `clearSession()` 的调用会按调用顺序执行，且某个操作被拒绝后队列仍会继续处理，因此后续通过包装器发起的变更不会与替换或回滚交错执行。成功的替换或回滚会使包装器缓存的历史记录与底层会话保持一致。如果替换和恢复都失败，请先恢复底层会话，再继续操作。这一顺序保证不会协调其他包装器实例，也不会协调对 `underlyingSession` 的直接修改；请在应用中自行协调这些访问路径。

自动压缩还会验证该次运行是否仍拥有它所读取的历史记录快照。如果在自动压缩开始前，另一个操作更改了包装器的历史记录，SDK 会保留较新的历史记录，并跳过此次压缩尝试。后续运行或显式调用 `runCompaction()` 可以压缩更新后的历史记录。

#### 面向低延迟流式传输的手动压缩

压缩会清空并重写底层会话，因此 SDK 会等待压缩完成后，才将流式运行标记为完成。如果压缩耗时较长，`result.completed` 可能在最后一个输出 token 之后仍保持待完成状态数秒。为了实现低延迟流式传输或更快的轮次切换，请禁用自动压缩，并在轮次之间（或空闲时）自行调用 `runCompaction`。

<Code
  lang="typescript"
  code={manualCompactionSession}
  title="禁用自动压缩并在轮次之间进行压缩"
/>

您可以随时调用 `runCompaction({ force: true })`，在归档或交接之前压缩历史记录。使用 `DEBUG=openai-agents:openai:compaction` 启用调试日志，以追踪压缩决策。
