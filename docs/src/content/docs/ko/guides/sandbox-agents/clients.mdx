이 페이지를 사용하여 샌드박스 작업을 실행할 위치를 선택합니다. 대부분의 경우 `SandboxAgent` 정의는 그대로 유지하고 `sandbox` 실행 옵션에서 샌드박스 클라이언트와 클라이언트별 옵션만 변경합니다.

<Aside type="caution" title="베타 기능">
  샌드박스 에이전트는 베타 버전입니다. 정식 출시 전까지 API 세부 정보, 기본값 및
  지원 기능이 변경될 수 있으며, 향후 더 많은 고급 기능이 추가될 예정입니다.
</Aside>

## 선택 가이드

| 목표 | 시작할 항목 | 이유 |
| --- | --- | --- |
| macOS 또는 Linux에서 가장 빠른 로컬 반복 작업 | `UnixLocalSandboxClient` | 추가 서비스 종속성이 없고 로컬 파일 시스템 워크플로가 간단합니다. |
| 기본적인 컨테이너 격리 | `DockerSandboxClient` | 특정 이미지가 적용된 Docker 내에서 작업을 실행합니다. |
| 호스티드 실행 또는 프로덕션 수준의 격리 | 호스티드 샌드박스 클라이언트 | 작업 공간 경계를 공급자가 관리하는 환경으로 이동합니다. |

## 로컬 클라이언트

대부분의 사용자는 다음 두 샌드박스 클라이언트 중 하나로 시작하는 것이 좋습니다.

| 클라이언트 | 설치 | 선택해야 하는 경우 |
| --- | --- | --- |
| `UnixLocalSandboxClient` | 없음 | macOS 또는 Linux에서 가장 빠르게 로컬 반복 작업을 수행하려는 경우. 로컬 개발을 위한 적절한 기본 선택입니다. |
| `DockerSandboxClient` | 로컬에서 Docker CLI 사용 가능 | 컨테이너 격리 또는 로컬 환경과의 일관성을 위한 특정 이미지가 필요한 경우. |

Unix 로컬은 로컬 파일 시스템을 대상으로 개발을 시작하는 가장 간단한 방법입니다. 더 강력한 환경 격리 또는 프로덕션 수준의 일관성이 필요하면 Docker나 호스티드 공급자로 전환하세요.

Unix 로컬에서 Docker로 전환하려면 에이전트 정의를 그대로 유지하고 클라이언트만 변경합니다.

### 세션 소유권

두 가지 수명 주기 방식이 있습니다.

| 방식 | 전달하는 항목 | 세션을 종료하는 주체 | 사용해야 하는 경우 |
| --- | --- | --- | --- |
| SDK 소유 | `sandbox: { client }` | 러너 | 샌드박스가 한 번의 실행 동안만 유지되면 되는 경우. |
| 개발자 소유 | `sandbox: { session }` | 사용자 코드 | 이후에 파일을 검사하거나, 동일한 활성 세션을 재사용하거나, 여러 실행을 조정해야 하는 경우. |

정상적으로 완료되거나 실패하면 러너가 SDK 소유 세션을 종료합니다. 실행이 승인 인터럽션(중단 처리)으로 일시 중지되거나 완료되지 않은 스트리밍 실행이 취소되면, 러너는 동일한 실행을 계속할 수 있도록 소유한 샌드박스 상태를 `RunState`에 보존합니다.

### 재개 및 스냅샷

샌드박스 상태와 대화 상태는 서로 별개입니다.

- SDK 대화 상태는 `result.history`, SDK `Session`, `conversationId` 또는 `previousResponseId`에 저장됩니다.
- 샌드박스 상태는 활성 샌드박스 세션, 직렬화된 `sessionState`, `RunState` 샌드박스 페이로드 또는 스냅샷에 저장됩니다.

샌드박스 클라이언트를 통해 동일한 백엔드 세션에 다시 연결하려면 `sessionState`를 사용합니다. 저장된 작업 공간 콘텐츠로 초기화된 새 세션이 필요하면 스냅샷을 사용합니다.

더 큰 워크플로를 일시 중지하거나 재개할 때 `RunState`를 사용하여 러너가 관리하는 샌드박스 상태를 보존할 수도 있습니다. 샌드박스 수명 주기가 직렬화된 실행 외부에서 관리되는 경우에는 명시적 `sessionState`를 사용합니다.

Docker에서 동일한 인메모리 `RunState`를 재개할 경우, SDK가 컨테이너의 ID를 확인하고 현재 매니페스트, 환경 및 경로 접근 권한을 다시 검증한 후에만 활성 컨테이너를 재사용할 수 있습니다. 활성 컨테이너 재사용이 불가능하거나 거부되면 Docker는 복원 가능한 스냅샷으로 대체합니다. `RunState.fromString(...)`을 사용하여 직렬화한 후 재구성한 `RunState`에는 신뢰할 수 있는 활성 컨테이너 권한 정보가 포함되지 않으므로, Docker는 직렬화된 컨테이너 ID에 연결하는 대신 스냅샷에서 복원합니다. 복원 가능한 스냅샷이 구성되지 않은 경우, 검증되지 않은 컨테이너에 연결하지 않고 재개에 실패합니다.

명시적 `baseDir`이 없는 로컬 스냅샷의 저장 디렉터리를 재정의하려면 `OPENAI_AGENTS_SANDBOX_SNAPSHOT_DIR`을 설정합니다. 그렇지 않으면 SDK는 macOS에서 `~/Library/Application Support/openai-agents-js/sandbox-snapshots`, Windows에서 `%LOCALAPPDATA%\openai-agents-js\sandbox-snapshots`, 기타 플랫폼에서 `$XDG_STATE_HOME/openai-agents-js/sandbox-snapshots`를 사용합니다. 해당 위치를 사용할 수 없으면 홈 디렉터리와 임시 디렉터리를 대체 경로로 사용합니다.

### 파일 시스템 존재 여부 확인

세션이 `pathExists()`를 구현하는 경우 `false`는 백엔드가 해당 경로가 없음을 확인했다는 의미입니다. 권한 오류, I/O 실패 및 공급자 확인 실패는 경로가 없는 것으로 처리되지 않고 공급자 오류와 함께 거부됩니다. 이를 통해 존재하지만 접근할 수 없는 경로를 편집기, 매니페스트 및 메모리 흐름에서 덮어쓰거나 교체하지 않도록 방지합니다.

## 마운트 및 원격 스토리지

마운트 항목은 노출할 스토리지를 설명하고, 마운트 전략은 샌드박스 백엔드가 해당 스토리지를 연결하는 방식을 설명합니다. 기본 제공 마운트 항목과 범용 전략은 `@openai/agents/sandbox`에서 가져옵니다.

일반적인 마운트 옵션은 다음과 같습니다.

- `mountPath`: 샌드박스에서 스토리지가 표시되는 위치입니다. 상대 경로는 매니페스트 루트를 기준으로 해석되며, 절대 경로는 그대로 사용됩니다.
- `readOnly`: 샌드박스가 마운트된 스토리지에 다시 쓰지 않아야 할 때 설정합니다.
- `mountStrategy`: 마운트 항목과 샌드박스 백엔드 모두에 적합한 전략을 사용합니다.

마운트는 임시 작업 공간 항목으로 취급됩니다. 스냅샷 및 지속성 흐름은 마운트된 원격 스토리지를 저장된 작업 공간으로 복사하는 대신 마운트된 경로를 분리하거나 건너뜁니다.

범용 로컬/컨테이너 전략은 다음과 같습니다.

| 전략 또는 패턴 | 사용해야 하는 경우 | 참고 |
| --- | --- | --- |
| `inContainerMountStrategy(...)` | 샌드박스 이미지에서 `rclone`, `mount-s3` 또는 `blobfuse2`와 같은 마운트 명령을 실행할 수 있는 경우. | 범용 전략으로 제공되며 지원 여부는 백엔드에 따라 다릅니다. |
| `dockerVolumeMountStrategy(...)` | 컨테이너가 시작되기 전에 Docker에서 볼륨 드라이버 기반 마운트를 연결해야 하는 경우. | Docker 전용입니다. |
| `localBindMountStrategy()` | 로컬 백엔드에서 절대 로컬 경로를 작업 공간에 바인드해야 하는 경우. | 허용되는 경우 로컬 작업 공간 실체화에서 지원됩니다. |

백엔드 지원 범위는 의도적으로 명시되어 있습니다.

| 백엔드 | 마운트 참고 사항 |
| --- | --- |
| `UnixLocalSandboxClient` | 로컬 작업 공간 모델을 통해 로컬 바인드 방식 마운트를 지원합니다. |
| `DockerSandboxClient` | Docker에서 스토리지를 연결할 수 있는 경우 로컬 바인드 마운트와 Docker 볼륨 방식 전략을 지원합니다. |
| 호스티드 공급자 | 공급자별 전략은 각 공급자 구현에 포함됩니다. 지원되는 마운트와 필요한 설정은 해당 공급자의 문서를 확인하세요. |

마운트 항목이 모든 백엔드에서 작동한다고 가정하지 마세요. 클라이언트가 매니페스트 메타데이터, ID 또는 마운트 동작을 적용할 수 없다면 매니페스트의 해당 부분을 자동으로 무시하는 대신 조기에 실패해야 합니다.

## 지원되는 호스티드 플랫폼

호스티드 환경이 필요한 경우 일반적으로 동일한 `SandboxAgent` 정의를 그대로 사용하고 `sandbox` 실행 옵션에서 샌드박스 클라이언트만 변경할 수 있습니다.

호스티드 공급자 구현은 `@openai/agents-extensions`의 공급자 하위 경로에서 제공됩니다. 정확한 환경 변수, 실행 가능한 예제, 포트 동작, PTY 지원, 스냅샷 동작 및 정리 동작은 공급자 문서를 확인하세요.

`@openai/agents-extensions`를 설치하고 패키지 수준의 피어 종속성을 충족해야 합니다. 각 공급자에는 공급자 SDK 패키지 또는 백엔드 설정이 추가로 필요할 수 있습니다.

| 클라이언트 | 가져오기 경로 | 공급자 요구 사항 |
| --- | --- | --- |
| `BlaxelSandboxClient` | `@openai/agents-extensions/sandbox/blaxel` | npm 피어: `@blaxel/core` |
| `CloudflareSandboxClient` | `@openai/agents-extensions/sandbox/cloudflare` | Cloudflare Sandbox 브리지 Worker URL 및 Worker 인증 |
| `DaytonaSandboxClient` | `@openai/agents-extensions/sandbox/daytona` | npm 피어: `@daytonaio/sdk` |
| `E2BSandboxClient` | `@openai/agents-extensions/sandbox/e2b` | npm 피어: `e2b` 또는 `@e2b/code-interpreter` |
| `ModalSandboxClient` | `@openai/agents-extensions/sandbox/modal` | npm 피어: `modal` |
| `RunloopSandboxClient` | `@openai/agents-extensions/sandbox/runloop` | npm 피어: `@runloop/api-client` |
| `VercelSandboxClient` | `@openai/agents-extensions/sandbox/vercel` | npm 피어: `@vercel/sandbox` |

`CloudflareSandboxClient`는 Cloudflare npm SDK를 가져오지 않습니다. 대신 배포된 Cloudflare Sandbox 브리지 Worker와 HTTP를 통해 통신합니다.

`VercelSandboxClient`는 각 PAT 자격 증명 필드를 생성별 옵션, 생성자 옵션, `VERCEL_PROJECT_ID`, `VERCEL_TEAM_ID`, `VERCEL_TOKEN` 순으로 확인합니다. 결과로 얻은 `projectId`, `teamId`, `token`이 모두 비어 있지 않은 경우에만 자격 증명을 전달합니다. 그렇지 않으면 세 필드를 모두 생략하고 플랫폼 OIDC 또는 로컬 공급자 자격 증명을 포함한 인증을 `@vercel/sandbox`에서 확인하도록 합니다. 완전히 확인된 자격 증명은 세션을 직렬화하고 재개할 때 보존됩니다. 직렬화된 자격 증명은 완전한 세 필드 조합으로 취급되며 현재 옵션 또는 환경 변수와 혼합되지 않습니다. 불완전한 직렬화 자격 증명은 대체 구성으로 현재 구성을 확인하기 전에 삭제됩니다. 토큰은 직렬화된 세션 상태에 계속 포함되므로 해당 상태를 안전하게 보관하세요.

호스티드 샌드박스 클라이언트는 공급자별 마운트 전략을 제공합니다. 스토리지 공급자에 가장 적합한 백엔드와 마운트 전략을 선택하세요.

샌드박스 내부에서 도우미를 실행하는 자격 증명 포함 마운트는 모델이 제어하는 코드가 해당 도우미 프로세스의 자격 증명에 접근할 수 있으므로 기본적으로 거부됩니다. 여기에는 지원되는 마운트 필드를 통해 제공되는 자격 증명, 환경에서 제공되는 AWS 또는 GCP 환경 변수, `RCLONE_CONFIG_*` 값, 워크로드 ID 또는 관리형 ID 검색이 포함됩니다. 자격 증명이 없는 rclone 및 마운트 지점 도우미는 환경 또는 메타데이터 인증을 비활성화하고 백엔드에서 지원하는 경우 익명 접근을 사용합니다. Docker 볼륨, Modal 클라우드 버킷 또는 Cloudflare 버킷 마운트와 같은 외부 또는 공급자 네이티브 전략을 우선적으로 사용하세요.

샌드박스 내 도우미가 필요한 경우 애플리케이션에서 생성한 매니페스트의 신뢰할 수 있는 각 유효 마운트 경로를 승인해야 합니다. 타입이 지정된 마운트 필드를 통해 직접 제공되는 마운트 범위 자격 증명에는 `manifest.withInContainerMountCredentialExposureAcknowledged('mounted/path')`에서 반환한 매니페스트를 사용합니다. 환경 자격 증명, 워크로드 또는 관리형 ID, 외부 자격 증명 또는 구성 파일에는 `manifest.withInContainerMountBroadCredentialExposureAcknowledged('mounted/path')`에서 반환한 매니페스트가 필요합니다. 두 종류의 권한을 모두 사용하는 마운트에는 두 승인 모두 필요합니다. 이러한 정확한 경로 승인은 런타임 전용이며 매니페스트 초기화 객체 또는 직렬화된 매니페스트 데이터에서는 절대 허용되지 않습니다. 이 승인은 선택한 도우미가 자격 증명을 받도록 허용하지만 해당 자격 증명을 마운트 경로에 한정하지는 않으므로, 동일한 샌드박스에서 모델이 제어하는 다른 코드가 여전히 자격 증명을 복구할 수 있습니다. 샌드박스 범위의 수명이 짧고 최소 권한만 가진 자격 증명을 사용하세요.

마운트가 참조하는 자격 증명 파일은 직접 또는 심볼릭 링크를 통해 직렬화 가능한 매니페스트 항목을 가리킬 수 없습니다. 동적 매니페스트 변경은 세션별로 직렬 처리됩니다. 권한이 필요한 마운트 전환 또는 교체 과정에서 공급자 작업이 이미 시작되었을 수 있는 상태로 언마운트에 실패하면, SDK는 모호한 상태를 재사용하거나 지속하지 않고 해당 세션을 무효화하고 종료합니다.

직렬화된 샌드박스 상태에서는 샌드박스 내 마운트 도우미가 선택한 환경 자격 증명을 포함하여 마운트 자격 증명이 생략됩니다. 지속된 마운트 구성은 재개하기 전에 신뢰할 수 있는 현재 매니페스트가 필요합니다. 재개 가능한 외부 또는 공급자 네이티브 마운트의 경우, SDK는 자격 증명을 제외한 현재 마운트 구성과 지속된 마운트 구성이 일치한 후에만 자격 증명을 복원합니다. 명시적 `sessionState`는 마스킹되지 않은 활성 권한 정보가 신뢰할 수 있는 현재 매니페스트와 여전히 일치하는 경우에만 기존 공급자 네이티브 마운트에 다시 연결할 수 있습니다. 권한 정보가 마스킹되었거나, 교체되었거나, 제거된 경우에는 새 샌드박스가 필요합니다. 자격 증명을 제외한 구성으로 분리할 수 없는 불투명한 구성은 재개할 수 없습니다. Runner가 샌드박스 내 마운트 도우미를 사용한 직렬화된 `RunState` 항목을 복원하면 저장된 세션을 폐기하고 신뢰할 수 있는 현재 구성으로 새 샌드박스를 생성합니다. 호출자가 제공한 명시적 `sessionState`와 공급자 직접 재개는 대신 컨테이너 내 마운트 상태를 거부하므로, 새 샌드박스를 명시적으로 시작해야 합니다. 불투명한 `secretRefs`를 통해 제공되는 Runloop 자격 증명 파일 변수는 컨테이너 내 마운트에서 거부됩니다. 마운트 전에 SDK가 유효 경로를 검증할 수 있도록 신뢰할 수 있는 현재 경로를 `managedSecrets`를 통해 제공하세요.

| 백엔드 | 마운트 참고 사항 |
| --- | --- |
| Docker | `inContainerMountStrategy()` 및 `dockerVolumeMountStrategy()` 같은 로컬 전략으로 `s3Mount()`, `gcsMount()`, `r2Mount()`, `azureBlobMount()`, `boxMount()`, `s3FilesMount()`를 지원합니다. |
| `ModalSandboxClient` | S3, R2 및 HMAC 인증 GCS 마운트 항목에서 `ModalCloudBucketMountStrategy`를 사용하는 클라우드 버킷 마운트를 지원합니다. |
| `CloudflareSandboxClient` | S3, R2 및 HMAC 인증 GCS 마운트 항목에서 `CloudflareBucketMountStrategy`를 사용하는 Cloudflare 버킷 마운트를 지원합니다. |
| `BlaxelSandboxClient` | S3, R2 및 GCS 마운트 항목에서 `BlaxelCloudBucketMountStrategy`를 사용하는 클라우드 버킷 마운트를 지원합니다. 자격 증명이 포함된 클라우드 마운트에는 SDK 소유 샌드박스가 필요합니다. 재사용되는 비소유 명명된 샌드박스는 자격 증명이 없는 클라우드 마운트 또는 `BlaxelDriveMount`와 `BlaxelDriveMountStrategy`를 사용하는 영구 Blaxel Drive를 사용할 수 있습니다. |

| `E2BSandboxClient` | S3, GCS, R2, Azure Blob 및 Box 마운트 항목에서 `E2BCloudBucketMountStrategy`를 사용하는 rclone 기반 마운트를 지원합니다. |
| `RunloopSandboxClient` | S3, GCS, R2, Azure Blob 및 Box 마운트 항목에서 `RunloopCloudBucketMountStrategy`를 사용하는 rclone 기반 마운트를 지원합니다. |
| `VercelSandboxClient` | `VercelCloudBucketMountStrategy`를 사용하는 생성 시점 S3 마운트를 지원합니다. 새 코드에서는 각 정확한 마운트 경로에 대해 `withInContainerMountCredentialExposureAcknowledged()`를 사용하여 인라인 자격 증명을 승인하세요. 지원이 중단된 `allowS3CredentialExposure: true` 옵션은 출시된 인라인 S3 자격 증명 구성과의 호환성을 위해 계속 허용되지만, 환경 자격 증명이나 기타 광범위한 권한을 승인하지는 않습니다. 직렬화된 마운트 상태는 직접 재개할 수 없으므로 활성 마운트 세션을 재사용하세요. |

E2B 및 Runloop의 rclone 기반 마운트에서 SDK는 사용 가능한 기존 `rclone` 바이너리를 사용합니다. 그렇지 않으면 SHA-256 체크섬을 검증한 후에만 SDK에서 버전을 고정한 Linux 아카이브를 설치합니다. 지원되지 않는 아키텍처나 체크섬 검증 실패가 발생하면 마운트를 중단합니다.

"예"는 백엔드에서 해당 스토리지 마운트 유형을 실행할 수 있다는 의미이며, 앞서 설명한 자격 증명 경계를 우회한다는 의미는 아닙니다. Docker의 `dockerVolumeMountStrategy()`, Modal 클라우드 버킷 마운트 및 Cloudflare 버킷 마운트는 모델이 제어하는 샌드박스 외부에 마운트 자격 증명을 유지합니다. Docker의 `inContainerMountStrategy()`와 Daytona, E2B 및 Runloop의 rclone 전략은 자격 증명을 받을 때마다 정확한 경로 승인이 필요합니다. Box 마운트에는 인증이 필요하므로 Box 권한 정보가 타입이 지정된 마운트 필드를 통해 제공되는지, 외부 자격 증명 또는 구성 파일을 통해 제공되는지에 맞는 승인을 선택하세요. Docker S3 Files 마운트는 광범위한 워크로드 ID를 사용하므로 `withInContainerMountBroadCredentialExposureAcknowledged()`가 필요합니다.

로컬 PTY 지원은 SDK 프로세스에서 작은 Python 3 브리지를 사용합니다. 이 브리지는 Node.js가 기본 제공 PTY API를 지원하지 않고 SDK가 대화형 stdin, 신호 처리 및 종료 상태 보고를 위해 표준 POSIX PTY 동작을 필요로 하는 `tty: true` 세션에서만 사용됩니다. SDK 코드를 실행하는 환경에 `python3`를 설치하거나 `OPENAI_AGENTS_PYTHON`을 Python 3 실행 파일로 설정하세요. 이는 Docker 샌드박스 이미지 내부에 설치된 Python 버전이 있는 경우 해당 버전과는 별개입니다.

호스티드 공급자 지원은 공급자마다 다릅니다. 정확한 옵션, 환경 변수, 포트 동작, PTY 지원, 스냅샷 동작 및 정리 동작은 공급자별 문서를 확인하세요.
