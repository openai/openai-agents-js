## Runner 수명 주기 및 설정

### 에이전트 루프

Runner의 run 메서드를 사용할 때는 시작 에이전트와 입력을 전달합니다. 입력은 문자열(사용자 메시지로 간주됨) 또는 OpenAI Responses API의 입력 항목 목록일 수 있습니다.

러너는 다음과 같은 루프를 실행합니다.

1. 현재 입력으로 현재 에이전트의 모델을 호출합니다.
2. LLM 응답을 확인합니다.
   - **최종 출력** → 반환합니다.
   - **핸드오프** → 새 에이전트로 전환하고, 누적된 대화 기록을 유지한 채 1단계로 돌아갑니다.
   - **도구 호출** → 도구를 실행하고, 결과를 대화에 추가한 후 1단계로 돌아갑니다.
3. `maxTurns`가 `null`이 아닌 경우, `maxTurns`에 도달하면 [`MaxTurnsExceededError`](/openai-agents-js/openai/agents-core/classes/maxturnsexceedederror)를 발생시킵니다.

<Aside type="note">
  LLM 출력이 "최종 출력"으로 간주되려면 원하는 타입의 텍스트 출력이 생성되고
  도구 호출이 없어야 합니다.
</Aside>

#### Runner 수명 주기

앱이 시작될 때 `Runner`를 만들고 여러 요청에서 재사용합니다. 이 인스턴스는 모델 제공자, 트레이싱 옵션 등의 전역 설정을 저장합니다. 완전히 다른 설정이 필요한 경우에만 다른 `Runner`를 만듭니다. 간단한 스크립트에서는 내부적으로 기본 러너를 사용하는 `run()`을 호출할 수도 있습니다.

### 실행 인수

`run()` 메서드에는 실행을 시작할 초기 에이전트, 실행 입력, 옵션 집합을 전달합니다.

입력은 문자열(사용자 메시지로 간주됨), [입력 항목](/openai-agents-js/openai/agents-core/type-aliases/agentinputitem) 목록, 또는 [휴먼 인 더 루프 (HITL)](/openai-agents-js/ko/guides/human-in-the-loop) 에이전트를 구축하는 경우 [`RunState`](/openai-agents-js/openai/agents-core/classes/runstate) 객체일 수 있습니다.

추가 옵션은 다음과 같습니다.

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `stream` | `false` | `true`이면 호출이 `StreamedRunResult`를 반환하고 모델에서 이벤트가 도착할 때마다 내보냅니다. |
| `context` | – | 모든 도구 / 가드레일 / 핸드오프에 전달되는 컨텍스트 객체입니다. 자세한 내용은 [컨텍스트 관리](/openai-agents-js/ko/guides/context)를 참고합니다. |
| `maxTurns` | `10` | 안전을 위한 제한입니다. 한도에 도달하면 [`MaxTurnsExceededError`](/openai-agents-js/openai/agents-core/classes/maxturnsexceedederror)를 발생시킵니다. `null`을 전달하면 제한을 비활성화합니다. |
| `signal` | – | 취소에 사용하는 `AbortSignal`입니다. |
| `session` | – | 세션 영속성 구현입니다. [세션](/openai-agents-js/ko/guides/sessions)을 참고합니다. |
| `sessionInputCallback` | – | 세션 기록과 새 입력을 병합하는 사용자 정의 로직입니다. 모델 호출 전에 실행됩니다. [세션](/openai-agents-js/ko/guides/sessions)을 참고합니다. |
| `callModelInputFilter` | – | 모델을 호출하기 직전에 모델 입력(항목 + 선택적 instructions)을 수정하는 훅입니다. [모델 호출 입력 필터](#call-model-input-filter)를 참고합니다. |
| `toolErrorFormatter` | – | 모델에 반환되는 도구 오류 메시지를 사용자 정의하는 훅입니다. [도구 오류 포매터](#tool-error-formatter)를 참고합니다. |
| `reasoningItemIdPolicy` | – | 이전 실행 항목을 모델 입력으로 다시 변환할 때 추론 항목의 `id`를 유지할지 생략할지 제어합니다. [추론 항목 ID 정책](#reasoning-item-id-policy)을 참고합니다. |
| `tracing` | – | 실행별 트레이싱 설정 재정의입니다. `includeTaskAndTurnSpans: false`로 설정하면 기본 작업/턴 스팬 계층 구조를 생략합니다. |
| `sandbox` | – | `SandboxAgent` 실행에 사용할 샌드박스 클라이언트, 활성 세션, 세션 상태, 스냅샷, 매니페스트 재정의 또는 동시성 제한입니다. [개념](/openai-agents-js/ko/guides/sandbox-agents/concepts)을 참고합니다. |
| `toolExecution` | – | 로컬 도구 호출을 위한 SDK 측 실행 설정입니다. `toolExecution.maxFunctionToolConcurrency`로 동시에 실행되는 함수 도구 수를 제한하고, `toolExecution.preApprovalInputGuardrails`로 승인 대기 요청 전에 함수 도구 입력 가드레일을 실행합니다. |
| `toolNotFoundBehavior` | `'raise_error'` | 모델이 생성했으나 대응하는 함수 도구를 찾을 수 없는 호출을 제어합니다. `'return_error_to_model'`을 사용하면 모델에 도구 오류를 반환하고 실행을 계속합니다. |
| `toolNameCollisionPolicy` | `'warn'` | 활성화된 함수 도구와 핸드오프 간의 이름 충돌을 제어합니다. 경고를 남기고 현재 디스패치 대상으로 선택된 항목만 노출하는 대신, 모델 요청 전에 실패하도록 하려면 `'error'`를 사용합니다. |
| `errorHandlers` | – | 지원되는 런타임 오류의 핸들러입니다. [오류 핸들러](#error-handlers)를 참고합니다. |
| `conversationId` | – | 서버 측 대화를 재사용합니다(OpenAI Responses API + Conversations API에서만 사용 가능). |
| `previousResponseId` | – | 대화를 생성하지 않고 이전 Responses API 호출에서 이어갑니다(OpenAI Responses API에서만 사용 가능). |

### 스트리밍

스트리밍을 사용하면 LLM이 실행되는 동안 이벤트도 제공됩니다. `StreamedRunResult`는 실행이 진행됨에 따라 정보를 누적합니다. 결과의 `completed` 프로미스가 이행되면 결과의 요약 속성에 새로 생성된 모든 출력이 포함됩니다. `for await` 루프로 스트리밍 이벤트를 순회할 수 있습니다. 자세한 내용은 [스트리밍](/openai-agents-js/ko/guides/streaming)을 참고합니다.

### 실행 설정

직접 `Runner` 인스턴스를 만드는 경우 `RunConfig` 객체를 전달하여 러너를 설정할 수 있습니다.

| 필드 | 타입 | 용도 |
| --- | --- | --- |
| `model` | `string \| Model` | 실행에 참여하는 **모든** 에이전트가 특정 모델을 사용하도록 강제합니다. |
| `modelProvider` | `ModelProvider` | 모델 이름에 해당하는 모델을 찾습니다. 기본값은 OpenAI 제공자입니다. |
| `modelSettings` | `ModelSettings` | 에이전트별 설정을 재정의하는 전역 조정 매개변수입니다. 선택적으로 활성화할 수 있는 재시도 설정을 비롯한 자세한 내용은 [모델](/openai-agents-js/ko/guides/models#modelsettings)을 참고합니다. |
| `handoffInputFilter` | `HandoffInputFilter` | 핸드오프를 수행할 때 입력 항목을 수정합니다(핸드오프 자체에 이미 필터가 정의되어 있지 않은 경우). |
| `inputGuardrails` | `InputGuardrail[]` | _최초_ 사용자 입력에 적용되는 가드레일입니다. |
| `outputGuardrails` | `OutputGuardrail[]` | _최종_ 출력에 적용되는 가드레일입니다. |
| `tracingDisabled` | `boolean` | OpenAI 트레이싱을 완전히 비활성화합니다. |
| `traceIncludeSensitiveData` | `boolean` | 스팬은 계속 내보내면서 트레이스에서 LLM/도구의 입력과 출력을 제외합니다. |
| `workflowName` | `string` | Traces 대시보드에 표시되며, 관련 실행을 그룹화하는 데 도움이 됩니다. |
| `traceId` / `groupId` | `string` | SDK가 생성하도록 두는 대신 트레이스 또는 그룹 ID를 직접 지정합니다. |
| `traceMetadata` | `Record<string, string>` | 모든 스팬에 첨부할 임의의 메타데이터입니다. |
| `tracing` | `TracingConfig` | 내보내기용 API 키와 `includeTaskAndTurnSpans`를 포함한 Runner 수준의 트레이싱 기본값입니다. 개별 실행 옵션으로 이 값을 재정의할 수 있습니다. |
| `sessionInputCallback` | `SessionInputCallback` | 이 러너의 모든 실행에 적용되는 기본 기록 병합 전략입니다. |
| `callModelInputFilter` | `CallModelInputFilter` | 각 모델 호출 전에 모델 입력을 수정하는 전역 훅입니다. |
| `toolErrorFormatter` | `ToolErrorFormatter` | 모델에 반환되는 도구 오류 메시지를 사용자 정의하는 전역 훅입니다. |
| `reasoningItemIdPolicy` | `ReasoningItemIdPolicy` | 생성된 항목을 이후 모델 호출의 입력으로 다시 사용할 때 추론 항목의 `id`를 유지할지 생략할지 정하는 기본 정책입니다. |
| `sandbox` | `SandboxRunConfig` | `SandboxAgent` 실행을 위한 기본 샌드박스 런타임 설정입니다. |
| `toolExecution` | `ToolExecutionConfig` | 로컬 도구 호출을 위한 기본 SDK 측 실행 설정입니다. `maxFunctionToolConcurrency`는 각 턴에서 로컬 함수 도구의 동시 실행 수를 제한합니다. 설정하지 않거나 `null`이면 한 턴에서 생성된 모든 함수 도구 호출을 시작합니다. `preApprovalInputGuardrails`는 승인 대기 요청 전에 함수 도구 입력 가드레일을 실행하도록 활성화합니다. |
| `toolNotFoundBehavior` | `ToolNotFoundBehavior` | 대응하는 함수 도구를 찾을 수 없는 호출의 기본 동작입니다. `'raise_error'`는 `ModelBehaviorError`를 발생시키고, `'return_error_to_model'`은 모델에 도구 오류를 반환하고 실행을 계속할 수 있게 합니다. |
| `toolNameCollisionPolicy` | `ToolNameCollisionPolicy` | 활성화된 함수 도구와 핸드오프의 이름에 적용되는 기본 충돌 정책입니다. `'warn'`은 로그를 남기고 현재 디스패치 대상으로 선택된 항목을 노출하며, `'error'`는 모델을 호출하기 전에 `UserError`를 발생시킵니다. |

`toolExecution.maxFunctionToolConcurrency`는 `1` 이상의 정수여야 합니다. 이 설정은 로컬 함수 도구의 SDK 측 실행만 제한합니다. 제공자 측 `modelSettings.parallelToolCalls`는 변경하지 않습니다.

`toolExecution.preApprovalInputGuardrails`는 기본적으로 비활성화되어 있습니다. `true`로 설정하면 승인이 필요한 로컬 함수 도구는 SDK가 승인 대기 인터럽션(중단 처리)을 기록하기 전에 입력 가드레일을 실행합니다. 가드레일이 `rejectContent`를 반환하면 SDK는 승인을 요청하는 대신 해당 거부 메시지를 도구 출력으로 반환합니다. 가드레일이 호출을 허용하더라도 승인 요청은 여전히 발생하며, 승인이 처리된 후 도구를 실행하기 직전에 동일한 입력 가드레일이 다시 실행됩니다.

`toolNameCollisionPolicy`는 활성화된 함수 도구와 핸드오프 간의 충돌만 제어합니다. 네임스페이스가 지정된 도구, 지연 도구, 중복된 로컬 MCP 도구 이름에 대한 기존의 엄격한 검증은 변경되지 않습니다.

## 상태 및 대화 관리

### 하나의 메모리 전략 선택

상태를 다음 턴으로 전달하는 일반적인 방법은 네 가지입니다.

| 전략 | 상태 저장 위치 | 적합한 용도 | 다음 턴에 전달할 내용 |
| --- | --- | --- | --- |
| `result.history` | 앱 메모리 | 소규모 채팅 루프, 완전한 수동 제어, 모든 제공자 | `result.history` |
| `session` | 자체 스토리지 + SDK | 영속적인 채팅 상태, 재개 가능한 실행, 사용자 정의 저장소 | 동일한 `session` 인스턴스(또는 저장소에 연결된 인스턴스) |
| `conversationId` | OpenAI Conversations API | 워커/서비스 간 서버 측 상태 공유 | 동일한 `conversationId`와 새 사용자 턴만 전달 |
| `previousResponseId` | OpenAI Responses API에서만 지원 | 대화를 생성하지 않고 서버에서 관리하는 가장 간단한 이어가기 방식 | `result.lastResponseId`와 새 사용자 턴만 전달 |

`result.history`와 `session`은 클라이언트에서 관리합니다. `conversationId`와 `previousResponseId`는 OpenAI에서 관리하며, OpenAI Responses API를 사용할 때만 적용됩니다. 대부분의 애플리케이션에서는 대화마다 하나의 영속성 전략을 선택합니다. 두 계층을 의도적으로 조정하지 않는 한, 클라이언트에서 관리하는 기록과 서버에서 관리하는 상태를 혼용하면 컨텍스트가 중복될 수 있습니다.

샌드박스 에이전트는 활성 샌드박스 작업 공간이라는 또 하나의 상태 계층을 추가합니다. 대화 기록에는 일반 SDK `session`, `conversationId` 또는 `previousResponseId`를 사용하고, 샌드박스 파일 시스템 상태에는 `sandbox.session`, `sandbox.sessionState`, `RunState` 또는 스냅샷을 사용합니다. 작업 공간 수명 주기는 [개념](/openai-agents-js/ko/guides/sandbox-agents/concepts)을 참고합니다.

#### 서버에서 관리하는 대화

매 턴마다 전체 로컬 대화 기록을 보내는 대신 OpenAI Responses API가 대화 기록을 영속적으로 저장하도록 할 수 있습니다. 긴 대화나 여러 서비스를 조율할 때 유용합니다. 아래의 두 서버 관리 방식 모두 각 요청에 새 턴의 입력만 전달합니다. API가 이전 상태를 재사용합니다. 자세한 내용은 [대화 상태 가이드](https://developers.openai.com/api/docs/guides/conversation-state)를 참고합니다.

## 훅 및 사용자 정의

### 모델 호출 입력 필터

`callModelInputFilter`를 사용하면 모델을 호출하기 _직전에_ 모델 입력을 수정할 수 있습니다. 이 훅은 현재 에이전트, 컨텍스트, 병합된 입력 항목(세션 기록이 있으면 포함)을 받습니다. 업데이트된 `input` 배열과 선택적 `instructions`를 반환하여 민감한 데이터를 가리거나, 오래된 메시지를 삭제하거나, 추가 시스템 지침을 주입할 수 있습니다.

`runner.run(..., { callModelInputFilter })`에서 실행별로 설정하거나, `Runner` 설정에서 기본값으로 설정합니다(`RunConfig`의 `callModelInputFilter`).

반환값은 `ModelInputData` 객체여야 합니다: `{ input: AgentInputItem[], instructions? }`. `input` 필드는 필수이며 배열이어야 합니다. 다른 형태를 반환하면 `UserError`가 발생합니다.

SDK는 필터를 호출하기 전에 준비된 턴 입력을 복제합니다. `session`도 사용하고 있다면 필터링된 복제본이 저장되므로, 여기에서 적용한 데이터 가리기나 잘라내기가 저장된 세션 기록에도 반영됩니다.

필터가 반복되는 모델 호출 간에 작업을 메모이제이션하기 위해 객체 동일성에 의존한다면 필터에 `preserveInputIdentity = true`를 설정합니다. 그러면 SDK는 각 필터 호출에 새 배열을 전달하더라도, SDK가 준비한 각 항목이 준비된 입력에 남아 있는 동안 해당 항목의 동일성을 유지합니다. 이 옵션은 호출자가 소유한 객체, 즉 원래 `run()`에 전달한 객체의 동일성은 유지하지 않습니다.

SDK는 준비된 항목이나 그 안에 중첩된 값을 동결하지 않으므로 이 모드는 명시적으로 활성화해야 합니다. 필터와 필터가 호출하는 모든 헬퍼는 항목을 불변으로 취급하고, 직접 수정하는 대신 대체 값을 반환해야 합니다. 필터가 반환된 후에도 모델 요청과 세션 입력은 서로 독립된 복사본으로 유지됩니다.

`conversationId` 또는 `previousResponseId`를 사용하면 다음 Responses API 호출을 위해 준비된 페이로드에 훅이 실행됩니다. 이전의 서버 관리 컨텍스트는 API가 복원하므로, 해당 호출의 필터링된 배열은 이전 기록 전체가 아니라 새 턴의 변경분만 나타낼 수 있습니다. 이 최종 필터 단계 전에 저장된 기록과 현재 턴을 병합하는 방식을 변경해야 한다면 `sessionInputCallback`을 사용합니다.

### 도구 오류 포매터

`toolErrorFormatter`를 사용하면 모델에 반환되는 도구 오류 메시지를 사용자 정의할 수 있습니다. 이를 통해 SDK 기본 메시지 대신 도메인에 특화된 문구(예: 규정 준수 지침)를 반환할 수 있습니다.

포매터는 실행별로 설정하거나(`runner.run(..., { toolErrorFormatter })`), `RunConfig`에서 전역으로 설정할 수 있습니다(`new Runner(...)`의 `toolErrorFormatter`).

이 포매터는 승인 거부에 대한 전역 폴백입니다. `result.state.reject(interruption, { message: '...' })`로 특정 인터럽션(중단 처리)을 거부하면 해당 호출의 `message`가 `toolErrorFormatter`보다 우선합니다. 둘 다 제공되지 않으면 SDK는 기본 거부 문구인 `Tool execution was not approved.`를 사용합니다.

`toolNotFoundBehavior: 'return_error_to_model'`이 대응하는 함수 도구를 찾을 수 없는 호출을 모델에 전달할 도구 출력으로 변환할 때도 포매터가 실행됩니다. 이 경우 기본 메시지는 `Tool '<name>' not found.`입니다.

포매터는 다음을 받습니다.

- `kind` (`'approval_rejected'` 또는 `'tool_not_found'`)
- `toolType` (`'function'`, `'computer'`, `'shell'` 또는 `'apply_patch'`)
- `toolName`
- `callId`
- `defaultMessage` (현재 오류 종류에 대한 SDK 폴백 메시지)
- `runContext`

문자열을 반환하면 메시지를 재정의하고, `undefined`를 반환하면 SDK 기본값을 유지합니다. 포매터가 예외를 발생시키거나 문자열이 아닌 값을 반환하면 SDK는 경고를 로그에 남기고 현재 오류 종류에 대한 기본 메시지를 사용합니다.

### 추론 항목 ID 정책

`reasoningItemIdPolicy`를 사용하면 SDK가 이전에 생성된 실행 항목을 이후 모델 입력에 사용할 `AgentInputItem[]`로 다시 변환할 때 추론 항목의 `id` 필드를 유지할지 제어할 수 있습니다.

이는 SDK가 생성된 모델 항목을 입력으로 다시 사용하는 다음과 같은 경우에 영향을 미칩니다.

- 동일한 실행 내의 후속 모델 호출(예: 도구 실행 후)
- 생성된 항목을 입력/기록으로 재사용하는 후속 턴
- 저장된 `RunState`에서 재개한 실행
- `result.history` / `result.output`과 같은 파생 결과 뷰(모델 입력 형태의 배열)
- `'preserve'`(기본값)는 추론 항목 ID를 유지합니다.
- `'omit'`은 추론 항목을 입력으로 다시 보내기 전에 `id` 필드를 제거합니다.
- 추론 항목이 아닌 항목은 영향을 받지 않습니다.

이 정책으로 변경되지 **않는** 항목은 다음과 같습니다.

- 모델 응답 원문(`result.rawResponses`)
- 실행 항목(`result.newItems`)
- 제공자가 반환한 모델의 현재 턴 출력

즉, 이 정책은 SDK가 이전에 생성된 항목으로 **다음 입력**을 구성할 때 적용됩니다.

정책은 실행별로 설정하거나(`runner.run(..., { reasoningItemIdPolicy: 'omit' })`), 러너의 기본값으로 설정할 수 있습니다(`new Runner({ reasoningItemIdPolicy: 'omit', ... })`). 저장된 `RunState`에서 재개할 때는 재정의하지 않는 한 이전에 결정된 정책을 재사용합니다.

#### `callModelInputFilter`와의 상호작용

`reasoningItemIdPolicy`는 `callModelInputFilter` 전에 적용됩니다. 사용자 정의 동작이 필요하다면 `callModelInputFilter`에서 준비된 입력을 확인하고 모델 호출 전에 추론 ID를 직접 다시 추가하거나 제거할 수 있습니다.

#### `'omit'`의 사용 시점

다시 입력으로 사용하는 추론 항목을 ID 없이 정규화하려면 `'omit'`을 사용합니다(예: 전달되거나 다시 사용되는 모델 입력을 단순하게 유지하거나 앱 파이프라인의 연동 요구 사항에 맞추기 위해).

백엔드/제공자가 다시 입력으로 사용된 추론 항목을 요청 검증 오류로 거부하는 경우에도 유용한 문제 해결 옵션입니다(예: 후속 입력의 추론 항목 ID와 관련된 HTTP `400` 오류). 이 경우 `'omit'`으로 다시 입력에 포함되는 추론 ID를 제거하면 백엔드가 새 요청에 대해 유효하지 않다고 판단하는 ID를 보내지 않을 수 있습니다.

SDK가 다시 사용하는 입력에서도 추론 항목 ID를 유지하기를 원하고 연동 대상이 이를 허용한다면 `'preserve'`를 유지합니다.

## 오류 및 복구

### 오류 핸들러

`errorHandlers`를 사용하면 지원되는 런타임 오류를 예외로 발생시키는 대신 최종 출력으로 변환할 수 있습니다. 지원되는 키는 `maxTurns`, `modelRefusal`, `invalidFinalOutput`입니다.

- `errorHandlers.maxTurns`는 최대 턴 수 초과 오류만 처리합니다.
- `errorHandlers.modelRefusal`은 [`ModelRefusalError`](/openai-agents-js/openai/agents-core/classes/modelrefusalerror)로 전달되는 모델의 응답 거부를 처리합니다.
- `errorHandlers.invalidFinalOutput`은 구조화된 최종 출력이 없거나 출력 스키마 검증에 실패할 때 발생하는 [`ModelBehaviorError`](/openai-agents-js/openai/agents-core/classes/modelbehaviorerror) 인스턴스를 처리합니다. 핸들러는 모델을 재시도하거나 도구의 부수 효과를 다시 발생시키지 않고 검증된 폴백을 반환합니다.
- `errorHandlers.default`는 지원되는 오류 종류의 폴백으로 사용됩니다.
- 핸들러는 `{ error, context, runData }`를 받고 `{ finalOutput, includeInHistory? }`를 반환할 수 있습니다. 반환된 `finalOutput`은 현재 에이전트의 `outputType`과 일치해야 합니다. structured outputs의 경우 SDK는 실행을 완료하기 전에 폴백을 검증합니다. `undefined`를 반환하면 해당 오류의 기본 동작을 유지합니다.

### 예외

SDK는 다음과 같이 처리할 수 있는 몇 가지 오류를 발생시킵니다.

- [`MaxTurnsExceededError`](/openai-agents-js/openai/agents-core/classes/maxturnsexceedederror) – `maxTurns`에 도달
- [`ModelBehaviorError`](/openai-agents-js/openai/agents-core/classes/modelbehaviorerror) – 모델이 유효하지 않은 출력 생성(예: 형식이 잘못된 JSON, 알 수 없는 도구)
- [`ModelRefusalError`](/openai-agents-js/openai/agents-core/classes/modelrefusalerror) – 모델이 요청된 출력 생성을 거부
- [`ModelTimeoutError`](/openai-agents-js/openai/agents-core/classes/modeltimeouterror) – 재시도 처리 후에도 시간 초과된 모델 요청 시도가 최종 실패로 남음
- [`InputGuardrailTripwireTriggered`](/openai-agents-js/openai/agents-core/classes/inputguardrailtripwiretriggered) / [`OutputGuardrailTripwireTriggered`](/openai-agents-js/openai/agents-core/classes/outputguardrailtripwiretriggered) – 가드레일 위반
- [`ToolInputGuardrailTripwireTriggered`](/openai-agents-js/openai/agents-core/classes/toolinputguardrailtripwiretriggered) / [`ToolOutputGuardrailTripwireTriggered`](/openai-agents-js/openai/agents-core/classes/tooloutputguardrailtripwiretriggered) – 도구 가드레일 위반
- [`GuardrailExecutionError`](/openai-agents-js/openai/agents-core/classes/guardrailexecutionerror) – 가드레일 실행을 완료하지 못함
- [`ToolTimeoutError`](/openai-agents-js/openai/agents-core/classes/tooltimeouterror) – 함수 도구가 `timeoutMs`를 초과했으며 `timeoutBehavior: 'raise_exception'`을 사용함
- [`ToolCallError`](/openai-agents-js/openai/agents-core/classes/toolcallerror) – 시간 초과가 아닌 오류로 함수 도구 실행 실패
- [`UserError`](/openai-agents-js/openai/agents-core/classes/usererror) – 설정 또는 사용자 입력에 따라 발생하는 모든 오류

모두 기본 `AgentsError` 클래스를 상속하며, 이 클래스는 현재 실행 상태에 접근할 수 있는 `state` 속성을 제공할 수 있습니다.

다음은 `GuardrailExecutionError`를 처리하는 코드 예제입니다. 입력 가드레일은 첫 번째 사용자 입력에만 실행되므로, 이 예제는 원래 입력과 컨텍스트로 실행을 다시 시작합니다. 또한 모델을 다시 호출하지 않고 저장된 상태를 재사용하여 출력 가드레일을 재시도하는 방법도 보여줍니다.

입력과 출력의 재시도 비교:

- 입력 가드레일은 실행의 맨 첫 번째 사용자 입력에만 실행되므로, 재시도하려면 동일한 입력/컨텍스트로 새 실행을 시작해야 합니다. 저장된 `state`를 전달해도 입력 가드레일은 다시 실행되지 않습니다.
- 출력 가드레일은 모델 응답 후에 실행되므로, `GuardrailExecutionError`에 저장된 `state`를 재사용하여 모델을 다시 호출하지 않고 출력 가드레일을 다시 실행할 수 있습니다.

위 예제를 실행하면 다음과 같은 출력이 표시됩니다.

```
Guardrail execution failed (input): Error: Input guardrail failed to complete: Error: Something is wrong!
Math homework input guardrail tripped on retry
Guardrail execution failed (output): Error: Output guardrail failed to complete: Error: Output guardrail crashed.
Output guardrail tripped after retry with saved state
```
