아키텍처를 초기에 선택하세요:

- `OpenAIRealtimeWebRTC`는 브라우저에서 가장 간단하게 사용할 수 있는 방식으로, 오디오 입력과 출력을 자동으로 처리합니다. 내장 연결은 Realtime 이벤트에 데이터 채널도 사용합니다. 브라우저는 오디오만 처리하고 애플리케이션 서버가 Realtime 이벤트, 도구 및 비즈니스 로직을 담당해야 한다면 [Browser audio with server-side controls](/openai-agents-js/ko/guides/voice-agents/transport#browser-audio-with-server-side-controls)를 참고하세요.
- `OpenAIRealtimeWebSocket`은 더 세밀한 제어를 제공하지만, 오디오 캡처와 재생을 직접 관리해야 합니다.
- 함수 도구는 `RealtimeSession`이 실행되는 위치에서 실행됩니다. 세션이 브라우저에서 실행되면 도구도 브라우저에서 실행됩니다.
- Realtime 핸드오프는 동일한 라이브 세션 모델을 유지합니다. 음성 변경은 세션이 오디오 출력을 생성하기 전에만 가능합니다. 다른 백엔드 모델이 필요하다면 핸드오프 대신 도구를 통해 위임하세요.

## 세션 설정

### 오디오 처리

기본값인 `OpenAIRealtimeWebRTC`와 같은 일부 전송 계층은 오디오 입력과 출력을 자동으로 처리합니다. `OpenAIRealtimeWebSocket`과 같은 다른 전송 방식에서는 세션 오디오를 직접 처리해야 합니다:

<Code lang="typescript" code={handleAudioExample} />

기반 전송 계층이 지원하는 경우, `session.muted`는 현재 음소거 상태를 나타내고 `session.mute(true | false)`는 마이크 캡처를 켜거나 끕니다. `OpenAIRealtimeWebSocket`은 음소거를 구현하지 않습니다. `session.muted`는 `null`을 반환하고 `session.mute()`는 예외를 발생시키므로, WebSocket 구성에서는 직접 캡처를 일시 중지하고 마이크를 다시 활성화할 때까지 `sendAudio()` 호출을 중단해야 합니다.

### 세션 구성

[`RealtimeSession`](/openai-agents-js/openai/agents-realtime/classes/realtimesession/)을 생성할 때 세션 자체를 구성하며, 일반적으로 `model` 옵션과 `config` 객체를 사용합니다. `connect(...)`는 임의의 세션 필드를 설정하는 용도가 아니라 자격 증명, 엔드포인트 URL, 기존 Realtime 통화 연결 등 연결 시점의 사항을 처리하는 용도입니다.

<Code lang="typescript" code={configureSessionExample} />

내부적으로 SDK는 이 구성을 Realtime [`session.update`](https://developers.openai.com/api/reference/resources/realtime/client-events/#session.update) 형식으로 정규화합니다. [RealtimeSessionConfig](/openai-agents-js/openai/agents-realtime/type-aliases/realtimesessionconfig/)에 대응하는 속성이 없는 원문 세션 필드가 필요하다면 `providerData`를 사용하거나 `session.transport.sendEvent(...)`를 통해 원문 `session.update`를 전송하세요.

`outputModalities`, `audio.input`, `audio.output`을 사용하는 최신 SDK 구성 형식을 권장합니다. `modalities`, `inputAudioFormat`, `outputAudioFormat`, `inputAudioTranscription`, `turnDetection`과 같은 이전 SDK 별칭도 하위 호환성을 위해 정규화되지만, 새 코드에서는 여기에 표시된 중첩 `audio` 구조를 사용해야 합니다.

`gpt-realtime-2.1`과 같이 추론을 지원하는 Realtime 모델에서는 세션 구성에 `reasoning.effort`를 설정하세요. 추론 강도가 높을수록 지연 시간과 토큰 사용량이 늘어날 수 있습니다. 모델이 여러 도구를 병렬로 호출할 수 있는지 제어하려면 `parallelToolCalls`도 설정할 수 있습니다.

입력 오디오 전사에서 `audio.input.transcription`은 정식 출시(GA) 전사 모델과 해당 모델의 컨텍스트 옵션을 지원합니다. 지연 시간이 짧은 스트리밍 전사에는 `gpt-live-transcribe`를 사용하세요. 이 모델의 `delay` 설정으로 부분 전사의 속도와 최종 전사의 품질 간 균형을 조절할 수 있습니다. `gpt-live-transcribe`와 `gpt-transcribe`는 모두 자유 형식의 `prompt`, 리터럴 `keywords`, `languages` 배열을 지원합니다. 이 모델들은 `languages`를 사용하며, 단일 언어 힌트를 지원하는 이전 전사 모델은 계속 단수형 `language` 필드를 사용합니다. 모델별 워크플로는 공식 [전사 컨텍스트 지침](https://developers.openai.com/api/docs/guides/transcription/#improve-transcription-quality)과 [Realtime 전사 가이드](https://developers.openai.com/api/docs/guides/realtime-transcription/)를 참고하세요.

음성 대 음성 세션에서는 일반적으로 `outputModalities: ['audio']`를 사용하며, 오디오 출력과 전사를 함께 제공합니다. 텍스트 전용 응답이 필요할 때만 `['text']`로 전환하세요.

[RealtimeSessionConfig](/openai-agents-js/openai/agents-realtime/type-aliases/realtimesessionconfig/)에 대응하는 매개변수가 없는 새로운 매개변수에는 `providerData`를 사용할 수 있습니다. `providerData`에 전달된 모든 값은 원문 `session` 객체의 일부로 전달됩니다.

### 대화 수명 주기

`RealtimeSession`은 장시간 유지되는 Realtime 연결 위에서 동작합니다. 대화 기록의 로컬 복사본을 유지하고, 전송 이벤트를 수신하며, 도구와 출력 가드레일을 실행하고, 활성 에이전트 구성을 전송 계층과 동기화합니다.

기반 API의 동작도 여전히 중요합니다:

- 연결에 성공하면 `session.created` 이벤트로 시작하며, 이후 구성을 변경하면 `session.updated`가 발생합니다.
- 대부분의 세션 속성은 시간이 지나면서 변경할 수 있지만, 대화 도중에는 `model`을 변경할 수 없고, `voice`는 세션이 오디오 출력을 생성하기 전에만 변경할 수 있습니다. 또한 Realtime API는 트레이싱을 활성화한 후에는 수정할 수 없으므로 트레이싱 여부를 미리 결정해야 합니다.
- Realtime API는 현재 단일 세션을 60분으로 제한합니다.
- 입력 오디오 전사는 비동기적으로 처리되므로, 최신 발화의 전사가 응답 생성이 이미 시작된 후에 도착할 수 있습니다.

SDK 계층에서 `await session.connect()`는 "대화를 시작할 수 있을 만큼 전송 계층이 준비되었다"는 의미이지만, 정확한 시점은 전송 방식에 따라 다릅니다:

- 기본 브라우저 WebRTC 전송 계층에서 SDK는 데이터 채널이 열리자마자 초기 `session.update`를 전송하고, 이에 대응하는 `session.updated` 이벤트를 기다린 후 `connect()`를 완료하려고 시도합니다. WebRTC 전송 계층이 이 확인을 기다리는 이유는 instructions, tools 및 모달리티가 적용되기 전에 오디오가 서버에 도달하는 것을 방지하기 위해서입니다. 확인이 도착하지 않으면 `connect()`는 짧은 제한 시간이 지난 후 완료됩니다.
- 기본 서버 측 WebSocket 전송 계층에서 `connect()`는 소켓이 열리고 초기 구성이 전송되면 완료됩니다. 따라서 이에 대응하는 `session.updated` 이벤트는 `connect()`가 이미 완료된 후에 도착할 수 있습니다.

원문 이벤트 모델이 필요하다면 이 페이지와 함께 공식 [Realtime 대화 가이드](https://developers.openai.com/api/docs/guides/realtime-conversations/)를 읽어보세요.

## 상호작용 흐름

### 턴 감지 및 음성 활동 감지

기본적으로 Realtime 세션은 내장 음성 활동 감지(VAD)를 사용하여 사용자가 말하기 시작하거나 멈춘 시점과 응답을 생성할 시점을 API가 판단할 수 있도록 합니다. SDK는 이를 `audio.input.turnDetection`을 통해 제공합니다.

<Code lang="typescript" code={turnDetectionExample} />

일반적으로 사용되는 두 가지 모드는 다음과 같습니다:

- `semantic_vad`는 더 자연스러운 턴 경계를 목표로 하며, 사용자가 아직 말을 마치지 않은 것처럼 들리면 조금 더 기다릴 수 있습니다.
- `server_vad`는 임계값에 더 크게 의존하며 `threshold`, `prefixPaddingMs`, `silenceDurationMs`, `idleTimeoutMs`와 같은 설정을 제공합니다.

턴 경계를 직접 관리하려면 `audio.input.turnDetection`을 `null`로 설정하세요. 기반 동작에 대한 자세한 내용은 공식 [음성 활동 감지 가이드](https://developers.openai.com/api/docs/guides/realtime-vad/)와 [Realtime 대화 가이드](https://developers.openai.com/api/docs/guides/realtime-conversations/#voice-activity-detection)를 참고하세요.

<Code lang="typescript" code={multiAgentsExample} />

일반 에이전트와 달리 음성 에이전트의 핸드오프는 약간 다르게 동작합니다. 핸드오프가 수행되면 진행 중인 세션이 새 에이전트 구성으로 즉시 업데이트됩니다. 따라서 새 에이전트는 진행 중인 대화 기록에 자동으로 접근할 수 있으며, 현재는 입력 필터가 적용되지 않습니다.

세션이 계속 유지되므로 핸드오프 중에 해당 세션의 모델은 변경되지 않습니다. 음성 변경은 기반 Realtime API 규칙을 따릅니다. 즉, 세션이 오디오 출력을 생성하기 전에만 변경할 수 있습니다. Realtime 핸드오프는 주로 동일한 세션에서 `RealtimeAgent` 구성을 교체하기 위한 기능입니다. `gpt-5.4`와 같은 추론 모델 등 다른 모델을 사용하거나 비실시간 백엔드 에이전트에 위임해야 한다면 [delegation through tools](#delegation-through-tools)를 사용하세요.

### 도구

일반 에이전트와 마찬가지로 음성 에이전트는 도구를 호출하여 작업을 수행할 수 있습니다. Realtime은 **함수 도구**(로컬에서 실행)와 **호스티드 MCP 도구**(Realtime API가 원격으로 실행)를 지원합니다. 일반 에이전트에서 사용하는 것과 동일한 `tool()` 헬퍼로 함수 도구를 정의할 수 있습니다.

Responses 전용 도구 옵션은 음성 에이전트에 적용되지 않습니다. 함수 도구의 `outputSchema`와 `'programmatic'`을 포함하는 `allowedCallers` 값은 거부되며, 호스티드 MCP 도구의 프로그래밍 방식 호출자도 거부됩니다. Realtime 세션에서는 직접 호출할 수 있는 함수 도구나 호스티드 MCP 도구를 사용하거나, Programmatic Tool Calling이 필요한 작업을 Responses 에이전트에 위임하세요.

#### 함수 도구

함수 도구는 `RealtimeSession`과 동일한 환경에서 실행됩니다. 즉, 브라우저에서 세션을 실행하면 도구도 브라우저에서 실행됩니다. 민감한 작업을 수행해야 한다면 도구 내부에서 백엔드를 호출하고 권한이 필요한 작업은 서버가 수행하도록 하세요.

이를 통해 브라우저 측 도구가 서버 측 로직에 연결되는 간단한 백채널 역할을 할 수 있습니다. 예를 들어 [`examples/realtime-next`](https://github.com/openai/openai-agents-js/tree/main/examples/realtime-next)는 요청과 현재 대화 기록을 서버의 `handleRefundRequest(...)`에 전달하는 `refundBackchannel` 도구를 브라우저에 정의합니다. 서버에서는 별도의 `Runner`가 다른 에이전트나 모델을 사용하여 환불을 평가한 다음 결과를 음성 세션에 반환할 수 있습니다.

#### 호스티드 MCP 도구

호스티드 MCP 도구는 `hostedMcpTool`로 구성할 수 있으며 원격으로 실행됩니다. 사용 가능한 MCP 도구가 변경되면 세션은 `mcp_tools_changed`를 내보냅니다. MCP 도구 호출이 완료된 후 세션이 모델 응답을 자동으로 트리거하지 않도록 하려면 `automaticallyTriggerResponseForMcpToolCalls: false`를 설정하세요.

현재 필터링된 MCP 도구 목록은 `session.availableMcpTools`로도 확인할 수 있습니다. 이 속성과 `mcp_tools_changed` 이벤트는 모두 에이전트 구성의 `allowed_tools` 필터를 적용한 후 활성 에이전트에서 활성화된 호스티드 MCP 서버만 반영합니다.

호스티드 MCP 설정은 보안이 필요한 서버 선택, 헤더 및 승인을 연결 전 구성으로 다루면 가장 쉽게 이해할 수 있습니다. `RealtimeSession.connect()`가 전송 계층을 열기 전에 SDK는 활성 에이전트의 호스티드 MCP 도구 정의를 해석하고, 지원되는 MCP 필드를 Realtime API에 보내는 초기 세션 구성에 포함합니다.

`connect()` 전에 안전한 호스티드 MCP 구성을 제공하는 것은 브라우저 WebRTC 앱에서 특히 중요합니다. 임시 클라이언트 시크릿은 항상 서버에서 발급되므로, 비밀로 유지해야 하는 호스티드 MCP 자격 증명이나 사용자 지정 `headers`는 서버 측 `POST /v1/realtime/client_secrets` 요청의 초기 `session` 페이로드에 포함해야 합니다. 장기 자격 증명을 브라우저 코드에 넣고 `connect()`가 시작된 후에 추가하려고 계획해서는 안 됩니다.

Realtime API 수준에서는 이후의 `session.update` 호출로 도구와 기타 변경 가능한 세션 필드를 계속 변경할 수 있으며, SDK 자체도 활성 에이전트가 변경되면 `session.update`를 전송합니다. 하지만 브라우저 앱에서는 보안이 필요한 호스티드 MCP 초기화를 서버 측에서 연결 전에 처리해야 하는 사항으로 다루고, 브라우저 측 `RealtimeSession` 구성을 서버에서 발급한 구성과 일치시켜야 합니다.

#### 백그라운드 결과

도구가 실행되는 동안 에이전트는 사용자의 새 요청을 처리할 수 없습니다. 사용자 경험을 개선하는 한 가지 방법은 도구를 실행하기 직전에 이를 알리거나 특정 문구를 말하도록 에이전트에 지시하여 도구를 실행할 시간을 확보하는 것입니다.

함수 도구가 완료된 직후 다른 모델 응답을 트리거하지 않도록 하려면 `@openai/agents/realtime`의 `backgroundResult(output)`을 반환하세요. 이렇게 하면 도구 출력을 세션에 다시 보내면서 응답을 트리거하는 시점은 직접 제어할 수 있습니다.

#### 제한 시간

함수 도구의 제한 시간 옵션(`timeoutMs`, `timeoutBehavior`, `timeoutErrorFunction`)은 Realtime 세션에서도 동일하게 동작합니다. 기본값인 `error_as_result`에서는 제한 시간 초과 메시지가 도구 출력으로 전송됩니다. `raise_exception`에서는 세션이 [`ToolTimeoutError`](/openai-agents-js/openai/agents-core/classes/tooltimeouterror)를 포함하는 `error` 이벤트를 내보내며, 해당 호출의 도구 출력은 전송하지 않습니다.

#### 도구 실행 전 승인

도구를 `needsApproval: true`로 정의하면 에이전트는 도구를 실행하기 전에 `tool_approval_requested` 이벤트를 내보냅니다.

이 이벤트를 수신하여 사용자가 도구 호출을 승인하거나 거부할 수 있는 UI를 표시할 수 있습니다.

`await session.approve(request.approvalItem)` 또는 `await session.reject(request.approvalItem)`으로 요청을 처리하세요. 함수 도구에서는 `{ alwaysApprove: true }` 또는 `{ alwaysReject: true }`를 전달하여 남은 세션 동안 반복되는 호출에 동일한 결정을 재사용할 수 있습니다. 또한 `session.reject(request.approvalItem, { message: '...' })`를 사용하여 해당 호출에 대한 사용자 지정 거부 메시지를 모델에 보낼 수 있습니다. 호스티드 MCP 승인은 승인/거부 결정의 유지를 지원하지 않습니다. 대신 호스티드 MCP의 `allowedTools` 구성으로 해당 도구를 제한하세요.

호출별 거부 `message`를 전달하지 않으면 세션은 `toolErrorFormatter`가 구성된 경우 이를 사용하고, 그렇지 않으면 SDK의 기본 거부 텍스트를 사용합니다.

기본적으로 함수 도구 입력 가드레일은 승인 후 도구가 실행되기 직전에 실행됩니다. `new RealtimeSession(...)`에 `toolExecution: { preApprovalInputGuardrails: true }`를 전달하면 세션이 `tool_approval_requested`를 내보내기 전에도 로컬 함수 도구 입력 가드레일이 실행됩니다. 가드레일이 호출을 거부하면 거부 메시지를 도구 출력으로 보내고 승인 이벤트를 건너뜁니다. 가드레일이 호출을 허용하면 승인 이벤트가 정상적으로 발생하며, `session.approve(...)` 후 실행 전에 가드레일이 다시 실행됩니다.

### 가드레일

가드레일은 에이전트의 발언이 규칙을 위반했는지 모니터링하고 응답을 즉시 중단하는 방법을 제공합니다. 이 검사는 에이전트 응답의 출력 스트림을 대상으로 실행됩니다. 텍스트 전용 세션에서 SDK는 출력 텍스트 델타를 평가합니다. 오디오 세션에서는 출력 오디오의 전사와 전사 델타를 사용하므로, 중요한 전제 조건은 별도의 텍스트 출력 모달리티가 아니라 전사의 가용성입니다.

제공한 가드레일은 모델 응답이 반환되는 동안 비동기적으로 실행되므로, "특정 금지 단어 언급"과 같이 사전에 정의된 분류 트리거에 따라 응답을 중단할 수 있습니다.

가드레일이 발동하면 세션은 `guardrail_tripped` 이벤트를 내보냅니다. 이 이벤트는 가드레일을 발동시킨 `itemId`가 포함된 `details` 객체도 제공합니다.

3. 인터럽션(중단 처리)으로 잘린 응답에는 최종 전사가 유지되지 않습니다.
4. 입력 오디오 전사는 모델이 오디오를 해석한 방식의 정확한 복사본이 아니라 사용자가 말한 내용을 대략적으로 파악하는 참고 자료로 다루는 것이 좋습니다.
