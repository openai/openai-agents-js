オーケストレーションとは、アプリ内でのエージェントの処理の流れを指します。どのエージェントを、どの順序で実行し、次に何をするかをどのように決めるのでしょうか。エージェントのオーケストレーションには、主に 2 つの方法があります。

> このページは、[クイックスタート](/openai-agents-js/ja/guides/quickstart)または[エージェント](/openai-agents-js/ja/guides/agents#composition-patterns)を読んだ後にお読みください。このページでは、`Agent` コンストラクター自体ではなく、複数のエージェントにまたがるワークフローの設計を扱います。

1. LLM に判断を任せる方法：LLM の知能を活用して計画と推論を行い、それに基づいて実行するステップを決定します。
2. コードによるオーケストレーション：コードでエージェントの処理の流れを決定します。

これらのパターンは組み合わせて使えます。それぞれにトレードオフがあり、以下で説明します。

## LLM によるオーケストレーション

エージェントとは、指示、ツール、ハンドオフを備えた LLM です。つまり、自由度の高いタスクを与えられると、LLM はそのタスクへの取り組み方を自律的に計画し、ツールでアクションを実行してデータを取得し、ハンドオフでサブエージェントにタスクを委譲できます。たとえば、調査エージェントには次のようなツールを用意できます。

- オンラインで情報を見つけるための Web 検索
- 独自のデータや接続先を検索するためのファイル検索と取得
- コンピューター上でアクションを実行するためのコンピュータ操作
- データ分析を行うためのコード実行
- 計画やレポート作成などを得意とする専門エージェントへのハンドオフ

### SDK の主要なパターン

Agents SDK では、次の 2 つのオーケストレーションパターンがよく使われます。

| パターン | 仕組み | 適した状況 |
| --- | --- | --- |
| Agents as tools | マネージャーエージェントが会話の制御を維持し、`agent.asTool()` を通じて専門エージェントを呼び出します。 | 1 つのエージェントに最終回答の責任を持たせたい場合、複数の専門エージェントの出力を組み合わせたい場合、または共通のガードレールを一元的に適用したい場合。 |
| ハンドオフ | トリアージエージェントが会話を専門エージェントに振り分け、その専門エージェントがターンの残りを担当するアクティブなエージェントになります。 | 専門エージェントにユーザーと直接対話させたい場合、プロンプトの焦点を絞りたい場合、または専門エージェントごとに異なる指示やモデルを使いたい場合。 |

専門エージェントにサブタスクを支援させつつ、ユーザーとの会話は引き継がせたくない場合は、 **agents as tools** を使います。どのツールを呼び出すか、最終的な応答をどのように提示するかは、引き続きマネージャーが責任を持って決定します。API の詳細は[ツール](/openai-agents-js/ja/guides/tools#4-agents-as-tools)を、両パターンを並べて比較できる例は[エージェント](/openai-agents-js/ja/guides/agents#composition-patterns)を参照してください。

振り分け自体がワークフローの一部であり、選択した専門エージェントに会話の次の部分を任せたい場合は、 **ハンドオフ** を使います。ハンドオフでは会話のコンテキストを保持しつつ、有効な指示を専門エージェントのものに絞り込みます。API については[ハンドオフ](/openai-agents-js/ja/guides/handoffs)を、最小限のエンドツーエンドの例については[クイックスタート](/openai-agents-js/ja/guides/quickstart#define-your-handoffs)を参照してください。

この 2 つのパターンは組み合わせられます。トリアージエージェントから専門エージェントへハンドオフし、その専門エージェントが範囲を限定したサブタスクのために、さらに他のエージェントをツールとして使うこともできます。

このパターンは、タスクの自由度が高く、LLM の知能を頼りにしたい場合に適しています。特に重要な取り組みは次のとおりです。

1. 質の高いプロンプトの作成に力を入れます。利用できるツール、その使い方、守るべき制約を明確にします。
2. アプリを監視し、改善を繰り返します。どこで問題が起きているかを確認し、プロンプトを改善します。
3. エージェントが内省して改善できるようにします。たとえば、ループ内で実行して自身の出力を批評させたり、エラーメッセージを与えて改善させたりします。
4. 何でも得意であることを期待する汎用エージェントではなく、1 つのタスクに優れた専門エージェントを用意します。
5. [評価](https://platform.openai.com/docs/guides/evals)に力を入れます。これにより、エージェントを訓練して改善し、タスクの遂行能力を高められます。

このスタイルのオーケストレーションを支える SDK の基本コンポーネントについて知りたい場合は、[ツール](/openai-agents-js/ja/guides/tools)、[ハンドオフ](/openai-agents-js/ja/guides/handoffs)、[エージェントの実行](/openai-agents-js/ja/guides/running-agents)から始めてください。

## コードによるオーケストレーション

LLM によるオーケストレーションは強力ですが、コードによるオーケストレーションでは、速度、コスト、性能の面でタスクの決定性と予測可能性が高まります。一般的なパターンは次のとおりです。

- [structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) を使い、コードで検査できる適切な形式のデータを生成します。たとえば、エージェントにタスクをいくつかのカテゴリーに分類させ、そのカテゴリーに基づいて次のエージェントを選べます。
- あるエージェントの出力を次のエージェントの入力に変換して、複数のエージェントを連鎖させます。ブログ記事の執筆などのタスクは、調査、構成案の作成、記事の執筆、批評、改善という一連のステップに分解できます。
- タスクを実行するエージェントを、評価とフィードバックを行うエージェントとともに `while` ループ内で実行します。評価担当のエージェントが、出力は所定の基準を満たしていると判断するまで繰り返します。
- たとえば JavaScript の `Promise.all` のような基本機能を使って、複数のエージェントを並列で実行します。互いに依存しないタスクが複数ある場合に、処理速度の向上に役立ちます。

[`examples/agent-patterns`](https://github.com/openai/openai-agents-js/tree/main/examples/agent-patterns) に多数のコード例を用意しています。
