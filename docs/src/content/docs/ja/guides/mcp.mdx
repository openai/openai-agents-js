[**Model Context Protocol (MCP)**](https://modelcontextprotocol.io) は、アプリケーションが LLM にツールやコンテキストを提供する方法を標準化するオープンプロトコルです。MCP のドキュメントでは、次のように説明されています。

> MCP は、アプリケーションが LLM にコンテキストを提供する方法を標準化するオープンプロトコルです。MCP は AI アプリケーション向けの USB-C ポートのようなものと考えてください。USB-C がデバイスをさまざまな周辺機器やアクセサリーに接続するための標準的な方法を提供するように、MCP は AI モデルをさまざまなデータソースやツールに接続するための標準的な方法を提供します。

この SDK は、次の 3 種類の MCP サーバーをサポートしています。

1. **リモート MCP サーバーツール** – [OpenAI Responses API](https://platform.openai.com/docs/guides/tools-remote-mcp) がツールとして使用するリモート MCP サーバー
2. **Streamable HTTP MCP サーバー** – [Streamable HTTP トランスポート](https://modelcontextprotocol.io/docs/concepts/transports#streamable-http) を実装したローカルまたはリモートのサーバー
3. **Stdio MCP サーバー** – 標準入出力を介してアクセスするサーバー（最もシンプルな選択肢）

> 注：SDK には従来の Server-Sent Events トランスポート向けの `MCPServerSSE` も含まれていますが、MCP プロジェクトでは SSE は非推奨となっています。新たに連携する場合は、Streamable HTTP または stdio を優先してください。

ユースケースに応じてサーバーの種類を選択してください。

| 必要な機能 | 推奨オプション |
| --- | --- |
| デフォルトの OpenAI Responses モデルで、公開アクセス可能なリモートサーバーを呼び出す | **1. リモート MCP ツール** |
| 公開アクセス可能なリモートサーバーを使用しつつ、ツール呼び出しをローカルで開始する | **2. Streamable HTTP** |
| ローカルで稼働する Streamable HTTP サーバーを使用する | **2. Streamable HTTP** |
| OpenAI Responses 以外のモデルで任意の Streamable HTTP サーバーを使用する | **2. Streamable HTTP** |
| 標準入出力プロトコルのみをサポートするローカル MCP サーバーを使用する | **3. Stdio** |

## MCP SDK v2 と v1 サーバーの互換性

Agents SDK は内部で MCP TypeScript SDK v2 クライアントを使用しています。これに伴って MCP サーバーを v2 サーバーパッケージに移行する必要はありません。stdio および Streamable HTTP 接続では、Agents SDK がプロトコルを自動的にネゴシエーションします。MCP TypeScript SDK v1 で実装された既存のサーバーも、互換性のあるプロトコルバージョンをサポートしていれば、引き続き利用できます。

アプリケーションが Agents SDK の `MCPServerStdio`、`MCPServerStreamableHttp`、`MCPServerSSE` クラスのみを使用している場合、この互換性のために MCP v1 と v2 のパッケージをインストールしたり、両者を橋渡ししたりする必要はありません。v2 MCP SDK の API を採用する際は、アプリケーション側で管理する MCP SDK オブジェクトを別途移行してください。MCP TypeScript SDK の [v1 から v2 への移行ガイド](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/upgrade-to-v2.md)を参照してください。

### リモート MCP のオプションリファレンス

`hostedMcpTool(...)` は、MCP サーバーの URL と、コネクターを利用するサーバーの両方をサポートしています。

| オプション | 型 | 説明 |
| --- | --- | --- |
| `serverLabel` | `string` | イベントやトレースでリモート MCP サーバーを識別するための必須ラベル。 |
| `serverUrl` | `string` | リモート MCP サーバーの URL（通常のリモート MCP サーバーにはこちらを使用します）。 |
| `connectorId` | `string` | OpenAI コネクターの ID（コネクターを利用するリモートサーバーには、`serverUrl` の代わりにこちらを使用します）。 |
| `authorization` | `string` | リモート MCP バックエンドに送信する認可トークン（省略可能）。 |
| `headers` | `Record<string, string>` | 追加のリクエストヘッダー（省略可能）。 |
| `allowedTools` | `string[] \| object` | モデルに公開するツール名の許可リスト。`string[]` または `{ toolNames?: string[] }` を渡します。 |
| `allowedCallers` | `('direct' \| 'programmatic')[]` | リモート MCP ツールを直接呼び出すか、プログラムによるツール呼び出し経由で呼び出すか、両方を許可するかを制御する空でないリスト。Responses 専用です。 |
| `deferLoading` | `boolean` | リモート MCP ツールの遅延読み込み。Responses 専用で、同じエージェント内に `toolSearchTool()` が必要です。 |
| `requireApproval` | `'never' \| 'always' \| object` | リモート MCP ツール呼び出しの承認ポリシー。ツールごとに上書きするにはオブジェクト形式を使用します。デフォルトは `'never'` です。 |
| `onApproval` | 承認コールバック | `requireApproval` が承認処理を要求する場合に、プログラムで承認または拒否するためのコールバック（省略可能）。 |

リモート MCP サーバーのツール定義を最初から公開するのではなく、モデルがツール検索を通じて必要に応じて読み込むようにするには、`deferLoading: true` を設定します。これは OpenAI Responses API でのみ動作し、同じリクエスト内に `toolSearchTool()` が必要です。GPT-5.4 以降の対応モデルリリースで使用してください。遅延読み込みの設定全体については、[ツール](/openai-agents-js/ja/guides/tools#deferred-tool-loading-with-tool-search)を参照してください。

リモート MCP ツールをモデルが生成した JavaScript からのみ呼び出せるようにするには、`allowedCallers: ['programmatic']` を設定します。どちらの経路も許可するには、`'direct'` と `'programmatic'` の両方を含めてください。同じエージェントに `programmaticToolCallingTool()` を追加します。プログラムが MCP ツールを呼び出す場合も、既存の `requireApproval` と `onApproval` のポリシーが適用されます。設定全体については、[プログラムによるツール呼び出し](/openai-agents-js/ja/guides/tools#programmatic-tool-calling)を参照してください。

`requireApproval` のオブジェクト形式では、省略可能な `always` および `never` エントリーを指定できます。各エントリーでは、`toolNames` または読み取り専用アノテーションによってツールを選択できます。省略可能な `onApproval` コールバックは、現在の実行コンテキストと承認アイテムを受け取り、`approve` と省略可能な `reason` を含む Promise を返します。

注意点：

- `convertSchemasToStrict` はベストエフォート方式です。スキーマを変換できない場合は、元のスキーマが使用されます。
- `errorFunction` は、MCP ツール呼び出しの失敗をモデルにどのように伝えるかを制御します。
- `errorFunction` が未設定の場合、SDK はデフォルトのツールエラーフォーマッターを使用します。
- サーバーレベルの `errorFunction` の値は、そのサーバーに対する `Agent.mcpConfig.errorFunction` を上書きします。
- `includeServerInToolNames` は明示的に有効にする必要があります。有効にすると、各ローカル MCP ツールは、サーバー名を接頭辞として付けた決定的な名前でモデルに公開されます。これにより、複数の MCP サーバーが同名のツールを公開する際の衝突を回避しやすくなります。
- SDK は、ログ、トレース、エラーメッセージに表示する前に、URL 由来のサーバー名とトランスポートエラーから URL の認証情報、クエリパラメーター、フラグメントを削除します。安定したサーバーラベルが必要な場合は、一意で機密情報を含まない `name` を明示的に設定してください。
- 異なる URL 由来のサーバー名が、認証情報、クエリパラメーター、フラグメントの削除後に同一となり、かつそれらのサーバーが同名のツールを公開している場合、モデルへのリクエスト前に設定エラーになります。それらのサーバーには、一意で機密情報を含まない `name` の値を明示的に設定してください。

## MCP サーバーのライフサイクル管理

複数の MCP サーバーを扱う場合は、`connectMcpServers` を使用して、一括で接続し、失敗を追跡し、接続を閉じる処理を一元化できます。このヘルパーは、`active`、`failed`、`errors` のコレクションを持つ `MCPServers` インスタンスを返すため、正常なサーバーのみをエージェントに渡せます。

ユースケース：

- **複数のサーバーの一括処理**：すべてのサーバーに並列で接続し、エージェントには `mcpServers.active` を使用します。
- **部分的な失敗の処理**：`failed` + `errors` を調べ、続行するか再試行するかを判断します。
- **失敗したサーバーの再試行**：`mcpServers.reconnect()` を呼び出します（デフォルトでは、失敗したサーバーのみを再試行します）。

厳密な「すべて成功するか、すべて失敗するか」の接続動作や、異なるタイムアウトが必要な場合は、`connectMcpServers(servers, options)` を使用し、環境に合わせてオプションを調整してください。

`connectMcpServers` のオプション：

| オプション | 型 | デフォルト値 | 説明 |
| --- | --- | --- | --- |
| `connectTimeoutMs` | `number \| null` | `10000` | 各サーバーの `connect()` のタイムアウト。無効にするには `null` を使用します。 |
| `closeTimeoutMs` | `number \| null` | `10000` | 各サーバーの `close()` のタイムアウト。無効にするには `null` を使用します。 |
| `dropFailed` | `boolean` | `true` | 失敗したサーバーを `active` から除外します。 |
| `strict` | `boolean` | `false` | いずれかのサーバーへの接続に失敗した場合に例外をスローします。 |
| `suppressAbortError` | `boolean` | `true` | 失敗したサーバーの追跡は継続しつつ、中断に類するエラーを無視します。 |
| `connectInParallel` | `boolean` | `false` | すべてのサーバーに順次ではなく並行して接続します。 |

`mcpServers.reconnect(options)` は、次のオプションをサポートしています。

| オプション | 型 | デフォルト値 | 説明 |
| --- | --- | --- | --- |
| `failedOnly` | `boolean` | `true` | 失敗したサーバーのみを再試行するか（`true`）、すべてのサーバーに再接続するか（`false`）を指定します。 |

再接続の前に、`MCPServers` は選択されたサーバーの接続を閉じます。正常に接続を閉じられたサーバーにのみ再接続します。クリーンアップの失敗は、引き続き `failed` と `errors` から確認できます。

## その他の注意点

**Streamable HTTP** および **Stdio** サーバーでは、`Agent` の実行ごとに、利用可能なツールを検出するために `list_tools()` が呼び出されることがあります。この往復処理は、特にリモートサーバーでレイテンシーを増やす可能性があるため、`MCPServerStdio` または `MCPServerStreamableHttp` に `cacheToolsList: true` を渡して、結果をメモリにキャッシュできます。

ツールリストが変更されないと確信できる場合にのみ有効にしてください。後でキャッシュを無効化するには、サーバーインスタンスの `invalidateToolsCache()` を呼び出します。`getAllMcpTools(...)` による共有 MCP ツールキャッシュを使用している場合は、`invalidateServerToolsCache(serverName)` でサーバー名を指定して無効化することもできます。

高度なユースケースでは、`getAllMcpTools({ generateMCPToolCacheKey })` を使用してキャッシュの分割方法をカスタマイズできます（たとえば、サーバー + エージェント + 実行コンテキストごとに分割できます）。

### サーバー名を接頭辞に持つツール名

デフォルトでは、ローカル MCP ツールは MCP サーバーが報告するツール名をそのまま使用します。2 つのローカル MCP サーバーが同じツール名を公開すると、モデルがそれらを安全に選び分けられないため、SDK はツール名の重複エラーを発生させます。

サーバー名を接頭辞として付けた決定的な名前を使用するには、エージェントで `mcpConfig.includeServerInToolNames: true` を設定します。

この設定では、`docs` サーバーの `search` ツールは `mcp_docs__search` としてモデルに公開され、`calendar` サーバーの `search` ツールは `mcp_calendar__search` として公開されます。SDK は引き続き、元のサーバー上で元の MCP ツール名を使用して呼び出します。

生成される名前は ASCII で安全に扱える形式で、`FunctionTool` インスタンスの名前の長さ制限に収まり、同じエージェント上のローカル `FunctionTool` インスタンスや有効なハンドオフの名前と衝突しません。この設定は、Streamable HTTP、SSE、stdio を含むすべてのローカル MCP トランスポートに適用されます。リモート MCP ツールは、リモートサーバーのラベルとツールのメタデータをそのまま保持します。
