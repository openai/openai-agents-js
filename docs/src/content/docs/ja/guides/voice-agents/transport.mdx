## デフォルトのトランスポートレイヤー

### ブラウザーのデフォルトとなる WebRTC

デフォルトのブラウザートランスポートは WebRTC を使用します。マイクからの音声キャプチャと再生が自動的に行われるため、[クイックスタート](/openai-agents-js/ja/guides/voice-agents/quickstart)では一時トークンと `session.connect(...)` だけで接続できます。

この方式では、音声の送受信が始まる前に指示とツールが適用されるよう、`session.connect()` は初期セッション設定の確認応答である `session.updated` を受信するまで待機してから完了しようとします。確認応答が届かない場合には、タイムアウトによるフォールバックも用意されています。

独自のメディアストリームや音声要素を使用するには、セッションの作成時に `OpenAIRealtimeWebRTC` インスタンスを指定します。

<Code lang="typescript" code={customWebRTCTransportExample} />

`OpenAIRealtimeWebRTC` に渡した `mediaStream` は、引き続きアプリケーションが所有します。トランスポートを閉じても、そのストリームのトラックは停止しないため、レベルメーター、レコーダー、再接続などに引き続き使用できます。アプリケーションでそのストリームが本当に不要になった時点で、各トラックの `stop()` を呼び出してください。トランスポートがデフォルトのマイクを自ら開いた場合は、`close()` によって SDK が所有するトラックが引き続き停止されます。

より低レベルのカスタマイズのために、`OpenAIRealtimeWebRTC` は `changePeerConnection` も受け付けます。これにより、オファーが生成される前に、新しく作成された `RTCPeerConnection` を検査または置換できます。

組み込みのブラウザートランスポートは、ブラウザー側の `RealtimeSession` が Realtime イベントを使用してセッションの設定と制御を行うため、データチャネルを作成します。これらのイベントと制御をアプリケーションサーバー側に保持する必要がある場合は、ブラウザー側のピア接続のカスタマイズをアクセス制御の境界とみなすのではなく、以下のサーバー側制御パターンを使用してください。

### Azure OpenAI の GA プロトコル対応

組み込みの Realtime トランスポートは GA プロトコルで送信します。カスタム URL を設定しても、セッションの更新が Azure の従来のプレビュー形式に変換されるわけではありません。非推奨のリージョン別 `realtimertc` エンドポイントは、`session.type` や `output_modalities` などの GA フィールドを拒否することがあり、その場合、サーバーは同じ更新に含まれる指示とツールを適用できなくなります。

Azure WebRTC については、Microsoft の [GA WebRTC セットアップガイド](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/realtime-audio-webrtc)に従ってください。

1. アプリケーションサーバーで、Azure リソースの `/openai/v1/realtime/client_secrets` エンドポイントから一時クライアントトークンを取得します。Azure リソースの認証情報はサーバー上に保持してください。
2. `RealtimeSession` コンストラクターの `model` オプションを Azure のデプロイ名に設定します。`RealtimeAgent` に指示と実行可能なツールを定義します。
3. 一時トークンを `apiKey` として、リソースの `https://<resource>.openai.azure.com/openai/v1/realtime/calls` URL とともに `session.connect()` に渡します。SDK はエージェントの設定をトランスポートに転送します。`initialSessionConfig` はトランスポートレベルのオプションであり、`RealtimeSession.connect()` のオプションではありません。

Azure が発行した一時トークンが `ek_` で始まらない場合、ブラウザートランスポートのキープレフィックスチェックに対応するため、`useInsecureApiKey: true` を設定した `OpenAIRealtimeWebRTC` インスタンスを明示的に使用する必要があります。このオプションが無効にするのはプレフィックスチェックだけです。引き続き一時トークンを渡し、有効期間の長いリソースの認証情報をブラウザーコードに渡すことは絶対に避けてください。

GA を使用する場合は、`session.type` を削除しないでください。GA ではこのフィールドが必須です。エンドポイントとプロトコルの違いについては、Microsoft の[プレビューから GA への移行ガイド](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/realtime-audio-preview-api-migration-guide)を参照してください。

### サーバー側の制御とブラウザー音声の組み合わせ

アプリケーションによっては、ブラウザーでマイクからの音声キャプチャと再生を行いながら、Realtime イベント、ツール、ビジネスロジックをアプリケーションサーバーで管理する必要があります。このアーキテクチャでは、Realtime API の[統合 WebRTC インターフェース](https://developers.openai.com/api/docs/guides/realtime-webrtc#creating-a-session-via-the-unified-interface)と[サーバー側の制御](https://developers.openai.com/api/docs/guides/realtime-server-controls#with-webrtc)を組み合わせます。

1. ブラウザーは標準の WebRTC API を使って音声のみのピア接続を作成し、その SDP オファーをアプリケーションサーバーに送信します。ブラウザーは SDK の組み込み WebRTC トランスポートを使用せず、Realtime データチャネルも作成しません。
2. アプリケーションサーバーはユーザーを認証し、SDP ポリシーを適用してから、標準の API キーを使って、オファーとサーバーが管理するセッション設定を `/v1/realtime/calls` に送信します。
3. アプリケーションサーバーは SDP アンサーを検証し、レスポンスの `Location` ヘッダーから通話 ID を読み取ります。
4. アプリケーションサーバーは WebSocket トランスポートを使用するサーバー側の `RealtimeSession` を作成し、イベントリスナーを登録して、通話 ID を `session.connect(...)` に渡し、最初の `session.updated` イベントを待ちます。
5. アプリケーションサーバーは SDP アンサーをブラウザーに返します。ブラウザーはそのアンサーをリモートディスクリプションとして設定し、ブラウザーと Realtime API の間で音声が直接送受信されます。
6. アプリケーションサーバーは Realtime イベントとツールを処理します。ブラウザーにステータスの更新を送る必要がある場合、アプリケーションサーバーは元の Realtime イベントストリームを転送するのではなく、許可リストにあるアプリケーションイベントに変換して送信します。

<Aside type="caution">
  ブラウザーコードで `createDataChannel()`
  を省略しても、アクセス制御の境界にはなりません。
  改変されたクライアントは、自身のコードや SDP
  オファーを変更できるためです。Realtime 通話を作成する前に、
  アプリケーションサーバーでメディアポリシーを適用してください。
  権限を必要とするすべてのツール操作は、`runContext.context`
  など、信頼できる認証済みの
  アプリケーションコンテキストまたはセッションコンテキストに基づいて認可し、
  モデルが指定したツール引数に基づいて認可することは絶対に避けてください。
</Aside>

音声のみのブラウザーピア接続、サーバーで適用する SDP ポリシー、サイドバンドの `RealtimeSession`、ブラウザー向けに変換したイベント、クリーンアップ処理を備えた完全なアプリケーションについては、[`realtime-server-controlled` のコード例](https://github.com/openai/openai-agents-js/tree/main/examples/realtime-server-controlled)を参照してください。

### React Native でのアプリ管理トランスポートの使用

`@openai/agents-core` と `@openai/agents-realtime` は、React Native 向けのパッケージ条件を公開しているため、Metro は Node.js 組み込みモジュールを使わずに、移植可能な SDK シムを解決できます。組み込みの `OpenAIRealtimeWebRTC` は、ブラウザーの WebRTC グローバルオブジェクトと DOM 音声要素に依存するため、引き続きブラウザー向けのトランスポートです。React Native では、ネイティブ WebRTC 実装をインストールしてアプリ側で管理し、カスタムの `RealtimeTransportLayer` を介して `RealtimeSession` に接続してください。

[`examples/realtime-react-native`](https://github.com/openai/openai-agents-js/tree/main/examples/realtime-react-native) の Expo 開発ビルドのコード例では、アプリが管理する `react-native-webrtc` トランスポート、マイクの権限、音声ルーティング、サーバー側の一時トークンエンドポイントを示しています。`react-native-webrtc` にはネイティブコードが含まれるため、Expo Go はサポートされていません。標準の OpenAI API キーはサーバー上に保持し、モバイルアプリには有効期間の短い一時クライアントトークンだけを渡してください。

### サーバーのデフォルトとなる WebSocket

WebRTC の代わりに WebSocket 接続を使用するには、セッションの作成時に `transport: 'websocket'` または `OpenAIRealtimeWebSocket` のインスタンスを渡します。これは、サーバー側のユースケース、テレフォニーブリッジ、カスタム音声パイプラインに適しています。

WebSocket を使用する場合、`session.connect()` はソケットが開かれ、初期設定が送信された時点で完了します。対応する `session.updated` イベントは少し遅れて届くことがあるため、`connect()` の完了時点で、その更新がすでに返されているとは考えないでください。

元の PCM16 音声バイト列の処理には、任意の録音・再生ライブラリを使用してください。

高度な連携向けに、`OpenAIRealtimeWebSocket` は独自のソケット実装を提供するための `createWebSocket()` を受け付けます。また、そのカスタムコネクターがソケットを接続済み状態に遷移させる役割を担う場合に使用する `skipOpenEventListeners` も受け付けます。`@openai/agents-extensions` の Cloudflare トランスポートは、これらのフックを使って構築されています。

### 通話プロバイダーとテレフォニーブリッジ向けの SIP

SIP で開始された既存の Realtime 通話に `RealtimeSession` を接続するには、`OpenAIRealtimeSIP` を使用します。これは SIP に対応した軽量なトランスポートです。音声は SIP 通話自体が処理し、SDK のセッションは `callId` を使って接続します。

1. `OpenAIRealtimeSIP.buildInitialConfig()` で初期セッション設定を生成して、着信通話を受け入れます。これにより、SIP インビテーションと後続の SDK セッションが同じデフォルト設定で開始されます。
2. `OpenAIRealtimeSIP` トランスポートを使用する `RealtimeSession` を接続し、プロバイダーの Webhook が発行した `callId` を使って接続します。
3. プロバイダー固有のメディア転送やイベントの橋渡しが必要な場合は、Twilio 拡張などの連携トランスポートを使用します。

<Aside type="caution">
  SIP 通話の受け入れでサポートされるのは、Realtime
  のターン検出フィールドの一部だけです。 設定に
  `threshold`、`prefixPaddingMs`、`silenceDurationMs`（またはそれらの
  スネークケース表記）が含まれている場合、`OpenAIRealtimeSIP.buildInitialConfig()`
  はローカルで例外をスローします。 Realtime Calls API が、SIP
  セッションにおけるこれらの `session.audio.input.turn_detection`
  プロパティを拒否するためです。
</Aside>

### Twilio の電話通話

`RealtimeSession` は、元の WebSocket を使用するか、`@openai/agents-extensions` の専用 Twilio トランスポートを使用して Twilio に接続できます。Twilio Media Streams の割り込みタイミングと音声転送を SDK に処理させたい場合は、専用トランスポートを標準の選択肢とすることをお勧めします。

セットアップの全体については、[Twilio 上の音声エージェント](/openai-agents-js/ja/extensions/twilio)を参照してください。

### 独自のトランスポートの使用

別の音声対話 API を使用したい場合や、独自のカスタムトランスポート機構がある場合は、`RealtimeTransportLayer` インターフェースを実装し、`RealtimeTransportEventTypes` イベントを自分で発行できます。

## 必要に応じた元の Realtime イベントへのアクセス

基盤となる Realtime API により直接的にアクセスしたい場合は、2 つの方法があります。

### 方法 1 - トランスポートレイヤーへのアクセス

`RealtimeSession` のすべての機能を引き続き利用したい場合は、`session.transport` を介してトランスポートレイヤーにアクセスできます。

トランスポートレイヤーは、受信したすべてのイベントを `*` イベントとして発行します。また、`sendEvent()` を使って元のイベントを送信できます。`*` リスナーは、元の解析済み JSON ペイロードの構造化クローンを受け取ります。これには、現在の SDK スキーマが認識していないフィールドも含まれます。名前付きイベントおよび派生イベントのリスナーは、引き続き検証・正規化済みのイベントオブジェクトを受け取ります。これは、`session.update`、`response.create`、`response.cancel` などの低レベル操作を行うための手段です。
