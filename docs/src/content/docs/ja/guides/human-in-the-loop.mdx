このガイドでは、SDK の承認ベースの人間の介入（HITL）フローについて説明します。ツール呼び出しに承認が必要な場合、SDK は実行を一時停止して `interruptions` を返し、後で同じ `RunState` から再開できるようにします。

この承認の仕組みは、現在のトップレベルのエージェントに限らず、実行全体が対象です。ツールが現在のエージェントに属する場合も、ハンドオフ先のエージェントに属する場合も、ネストされた `agent.asTool()` の実行に属する場合も、同じパターンが適用されます。ネストされた `agent.asTool()` の場合でも、中断は外側の実行に通知されるため、外側の `result.state` で承認または拒否し、元のルートの実行を再開します。

`agent.asTool()` では、承認は 2 つの異なる層で発生する可能性があります。エージェントツール自体が `asTool({ needsApproval })` によって承認を要求する場合と、ネストされた実行の開始後に、そのエージェント内のツールが独自に承認を要求する場合です。どちらも、外側の実行における同じ中断フローで処理されます。

このページでは、`interruptions` による手動の承認フローを中心に説明します。アプリケーションがコードで判断できる場合、一部のツールタイプではプログラムによる承認コールバックもサポートされているため、一時停止せずに実行を続行できます。`agent.asTool()` 自体の設定については、[ツール](/openai-agents-js/ja/guides/tools#4-agents-as-tools)を参照してください。このページでは、その実行階層内のいずれかのツールが承認を必要とした後の動作を説明します。

`computerTool()` では、`onSafetyCheck` を使用して、Responses API が返す安全性チェックを受け入れるか拒否します。このコールバックは、`id` と `code` がどちらも空でない値を持つ保留中のチェックがあるコンピュータ呼び出しでのみ実行され、このページで説明する一時停止と再開による承認フローは使用しません。詳細とコード例については、[コンピュータの安全性チェック](/openai-agents-js/ja/guides/tools#pending-computer-safety-checks)を参照してください。

### フロー

1. ツール呼び出しが実行される直前に、SDK はその承認ルール（`needsApproval` またはリモート MCP の同等のルール）を評価します。
2. 承認が必要で、まだ判断が保存されていない場合、そのツール呼び出しは実行されません。代わりに、実行に [`RunToolApprovalItem`](/openai-agents-js/openai/agents/classes/runtoolapprovalitem) が記録されます。
3. そのターンの終了時に実行が一時停止し、保留中のすべての承認が[エージェントの実行結果](/openai-agents-js/ja/guides/results)の `interruptions` 配列に返されます。これには、ネストされた `agent.asTool()` の実行内で要求された承認も含まれます。
4. 保留中の各アイテムを `result.state.approve(interruption)` または `result.state.reject(interruption)` で解決します。同じツールをその実行の残りの期間中ずっと承認済みまたは拒否済みにする場合は、`{ alwaysApprove: true }` または `{ alwaysReject: true }` を渡します。拒否する場合は、`{ message: '...' }` を渡して、その特定のツール呼び出しについてモデルに返す拒否メッセージを指定することもできます。
5. 更新された `result.state` を `runner.run(agent, state)` に渡して再開します。ここで `agent` は、その実行を開始した元のトップレベルのエージェントです。SDK は、ネストされたエージェントツールの実行も含めて、中断した時点から続行します。

デフォルトでは、関数ツールの入力ガードレールは承認後、ツールが実行される直前にのみ実行されます。承認待ちの要求が表示される前に、同じ入力ガードレールでローカル関数ツールの呼び出しを検証したい場合は、`run()` または `Runner` に `toolExecution: { preApprovalInputGuardrails: true }` を渡してください。承認前のガードレールが呼び出しを拒否した場合、SDK は承認のための中断を作成せず、ガードレールのメッセージをツール出力としてモデルに返します。呼び出しが許可された場合でも、実行は承認のために一時停止します。また、待機中にツール呼び出しが安全でなくなった可能性を考慮して、承認後に入力ガードレールが再度実行されます。

`needsApproval` が関数の場合、SDK はツールの引数が検査可能なオブジェクトにパースされた後にのみ、その関数を呼び出します。不正な JSON やオブジェクト以外の値に対しては安全側に倒し、SDK はコールバックの呼び出しやツールの実行をせずに承認を要求します。その呼び出しを承認してもツールは実行されず、通常の引数のパースエラー処理に進みます。Realtime 関数ツールも同じルールに従い、不正な呼び出しに対して `tool_approval_requested` を発行します。

`{ alwaysApprove: true }` または `{ alwaysReject: true }` で作成された、継続して適用される判断は実行状態に保存されるため、後で同じ一時停止中の実行を再開する際も、`toString()` / `fromString()` を通じて保持されます。

GA モデルでは、コンピュータツールの中断は、1 つの `computer_call` に含まれるアクションのバッチを表す場合があります。SDK は実行前にアクションごとに `needsApproval` を評価するため、1 つの保留中の承認が、移動 + クリックのような一連の操作を対象にすることがあります。UI の表示に `interruption.rawItem` を使用する場合は、GA の `actions` 配列と従来の単一の `action` フィールドの両方に対応してください。

シリアライズされた `RunState` は、現在の `computer` というツール名と従来の `computer_use_preview` という名前の両方にわたってコンピュータの承認も保持するため、プレビュー版から GA への移行中でも、一時停止中の実行を問題なく再開できます。

`message` を指定しない場合、SDK は設定された `toolErrorFormatter`（存在する場合）にフォールバックし、次にデフォルトの拒否メッセージにフォールバックします。

保留中のすべての承認を一度に解決する必要はありません。一部のアイテムだけを承認または拒否して再実行した場合、解決済みの呼び出しは続行できますが、未解決のものは `interruptions` に残り、実行が再び一時停止します。

`alwaysApprove: true` または `alwaysReject: true` で作成された、継続して適用される判断は、その後の同じツールの呼び出しに対するデフォルトになります。特定の呼び出し ID に対する個別の判断は、この継続適用のデフォルトよりも優先されます。ほかの呼び出しのデフォルトを変更せずに、継続的に承認されているツールの 1 つの呼び出しを拒否したり、継続的に拒否されているツールの 1 つの呼び出しを承認したりできます。後でその個別の判断を置き換えた場合、その呼び出しには新しい個別の判断が適用され、残りの呼び出しには引き続き継続適用のデフォルトが使用されます。

### 再開前の入力の追加

実行の一時停止中に新しいユーザー入力が届き、再開後の次のモデル呼び出しの前に取り込む必要がある場合は、`RunState.addInput()` を使用します。承認を解決し、同じ状態を `Runner.run()` に渡す前に入力を追加してください。取り込み待ちの入力はシリアライズされた状態の一部になるため、未解決の承認やローカルのツール処理によってモデル呼び出しが遅れる場合でも、`toString()` / `fromString()` を通じて保持されます。

`state.pendingInput` を読み取ると、取り込み待ちのアイテムの複製されたスナップショットを確認できます。また、再開前に `state.clearPendingInput()` を呼び出すと、それらをすべて削除できます。`addInput()` は文字列または入力アイテムの配列を受け取ります。終了状態、残りのターンがない状態、ツールの実行結果によって実行が終了する可能性がある中断など、状態が次のモデル呼び出しに安全に到達できない場合は、`UserError` を発生させます。

取り込まれると、取り込み待ちだった各入力エントリーは実行の `newItems` 内の [`RunInputItem`](/openai-agents-js/openai/agents/classes/runinputitem) になり、その元の入力アイテムは `history` に含まれます。ローカルの `session` を使用している場合、SDK はモデルへのリクエストを開始する前に、取り込まれた入力を一度だけ永続化します。`conversationId` または `previousResponseId` を使用している場合、入力はサーバーがレスポンスを受け付けるまで保留状態に残るため、受け付け前に発生したことが判明している失敗であれば、入力を失わずに再開できます。プロバイダーが、リクエストはすでに受け付けられた可能性があると報告した場合、SDK はその入力エントリーをチェックポイントに記録し、黙って再送するのではなく、安全側に倒して処理を停止します。安全でない再送を明示的に許可する別途の設定については、[モデルのリトライ](/openai-agents-js/ja/guides/models#model-retries)を参照してください。

### 自動承認判断

手動の `interruptions` は最も汎用的なパターンですが、唯一の方法ではありません。

- ローカルの `shellTool()` と `applyPatchTool()` は、`onApproval` を使用してコード内で即座に承認または拒否できます。
- リモート MCP ツールは、`requireApproval` と `onApproval` を組み合わせて、同様にプログラムで判断できます。
- 通常の関数ツールは、このページの手動の中断フローを使用します。

これらのコールバックが判断を返すと、人間の応答を待つために一時停止することなく、実行が続行されます。Realtime セッション API については、[音声エージェントの構築](/openai-agents-js/ja/guides/voice-agents/build#approval-before-tool-execution)の承認フローを参照してください。

### ストリーミングとセッション

同じ中断フローは、ストリーミングによる実行でも機能します。ストリーミングによる実行が一時停止したら、`stream.completed` を待ち、`stream.interruptions` を読み取って解決してください。再開後の出力も引き続きストリーミングする場合は、`{ stream: true }` を指定して `run()` を再度呼び出します。このパターンのストリーミング版については、[ストリーミング中の人間の介入（HITL）](/openai-agents-js/ja/guides/streaming#human-in-the-loop-while-streaming)を参照してください。

`session` も使用している場合は、`RunState` から再開する際も同じ `session` を渡し続けてください。そうすると、入力を再準備することなく、再開されたターンがセッションメモリに追加されます。セッションのライフサイクルの詳細については、[セッション](/openai-agents-js/ja/guides/sessions)を参照してください。

## 承認に時間がかかる場合の対応

人間の介入（HITL）フローは、サーバーを稼働させ続けなくても長期間中断できるように設計されています。リクエストの処理を終了して後で続行する必要がある場合は、状態をシリアライズして後で再開できます。

`result.state.toString()`（または `JSON.stringify(result.state)`）を使用して状態をシリアライズし、後でそのシリアライズされた状態を `RunState.fromString(agent, serializedState)` に渡すことで再開できます。ここで `agent` は、実行全体を開始したエージェントのインスタンスです。

承認された関数ツールの実行結果が実行の最終出力になり得る場合、出力ガードレールによって再開の条件がより厳しくなります。現在の `RunState` スキーマは、SDK が証明できる場合に、現在のレスポンスで生成されたアイテムの正確な所有関係を記録します。そのため、出力を含むサポート対象の部分承認チェックポイントは、シリアライズされた状態を介して保存・復元できます。SDK は、モデル、ツール、セッションで追加の副作用が発生する前に、その所有関係を検証します。古いスナップショットや、所有関係が欠落している、不正である、または曖昧なチェックポイントでは、引き続き安全側に倒し、`UserError` で処理を停止します。この場合は、安全な入力から新しい実行を開始してください。同じエージェントグラフを再構築し、元の `toolUseBehavior` を維持してください。元のアイテムを再実行して所有関係のエラーを回避しないでください。

`RunState` がシリアライズされると、SDK はハンドオフと `Agent.asTool()` のグラフに対して、安定したエージェント識別情報を記録します。これにより、実行を再開するプロセスが同じエージェントグラフを再構築する限り、異なるエージェントが同じ `name` を共有していても、一時停止中の実行を再開できます。

`RunState.fromString(agent, serializedState)` に渡す `agent` は、その再構築されたグラフのルートです。デシリアライズ中、SDK はそのエージェントのハンドオフと `Agent.asTool()` の参照をたどり、状態内のシリアライズされたすべてのエージェント参照を、再構築されたグラフに照らして解決します。これには、現在のエージェントと、生成されたアイテム、処理済みのモデルレスポンス、キューに入っている次のステップが保持するネストされた参照が含まれます。

モデルやツールが別のランタイムでラップされたエージェントなど、置き換えたグラフで再開する必要がある場合は、元のグラフで状態をデシリアライズし、再度シリアライズしてから、その文字列を置き換え後のルートエージェントでデシリアライズしてください。`state.setCurrentAgent(agent)` を呼び出しても、アクティブなエージェントが変わるだけで、デシリアライズ時にすでに解決されたネストされた参照は書き換えられません。

再開するプロセスで新しいコンテキストオブジェクトを注入する必要がある場合は、代わりに `RunState.fromStringWithContext(agent, serializedState, context, { contextStrategy })` を使用してください。

- `contextStrategy: 'merge'`（デフォルト）は、指定された `RunContext` を保持し、シリアライズされた承認状態をマージします。また、新しいコンテキストで `toolInput` がまだ定義されていない場合は、シリアライズされた `toolInput` を復元します。
- `contextStrategy: 'replace'` は、指定された `RunContext` をそのまま使用して実行を再構築します。

シリアライズされた実行状態には、アプリケーションのコンテキストに加えて、承認、使用量、ネストされた `toolInput`、ネストされたエージェントツールの保留中の再開処理など、SDK が管理するランタイムメタデータが含まれます。シリアライズされた状態を保存または送信する予定がある場合は、`runContext.context` を永続化されるデータとして扱い、機密情報を状態と一緒に移動させる意図がある場合を除き、そこに格納しないでください。

デフォルトでは、誤って機密情報を永続化しないように、トレーシング用の API キーはシリアライズされた状態から除外されます。トレーシングの認証情報を状態と一緒に移動させる必要があることを意図している場合にのみ、`result.state.toString({ includeTracingApiKey: true })` を渡してください。

シリアライズされた状態は、サーバー側のデータベースなど、アプリケーションが管理するストレージに保存してください。

### 承認状態のサーバーでの保持

シリアライズされた `RunState` には、承認判断、保留中のツール呼び出し、ツールの引数、アプリケーションのコンテキストなどの実行状態が含まれます。`RunState.fromString()` はその状態を復元しますが、このメソッドはスナップショットの真正性の検証も、送信者の本人確認も行いません。信頼できるストレージにあるスナップショット、またはアプリケーションでスナップショット全体の完全性、所有権、リプレイ対策を検証済みのものだけをデシリアライズしてください。スキーマ検証やツール呼び出しのフィンガープリントは、スナップショットの真正性を保証しません。エージェントや生成アイテムの所有関係についての SDK 内の参照情報も、アプリケーションユーザーの認可にはなりません。

ブラウザーやモバイルの承認インターフェースでは、完全なスナップショットを、アプリケーションが管理するサーバー側のストレージに保持してください。レビュー担当者には、閲覧が認可された表示用の詳細情報と、保留中の判断に対応する不透明な識別子だけを送信してください。実行 ID や判断 ID は、認可の証明にはなりません。ツール名と引数は、信頼できない表示コンテンツとして扱ってください。機密性の高い値を除外し、HTML として表示する際にはコンテンツをエスケープしてください。完全な実行結果とエラーはサーバーに保持し、アプリケーションが選択した出力だけをクライアントに返してください。

判断が届いたら、サーバーは次の処理を行う必要があります。

1. アプリケーションのセッションまたは認証ミドルウェアを使って、レビュー担当者を認証します。認証済みのユーザー識別情報を承認リクエストの本文から取得してはいけません。
2. 保存された実行と、選択された保留中の呼び出しに対して、レビュー担当者を認可します。
3. 判断の識別子と真偽値の判断を、サーバーに保存された保留中のリクエストに照らして検証します。置き換え用のツール呼び出し、引数、承認レコード、シリアライズされた状態をクライアントから受け入れないでください。
4. デシリアライズと実行の再開の前に、所有権の確認と保留中のリクエストの消費をアトミックに行います。同時送信や再送信によって、同じスナップショットが二度再開されてはいけません。共有ストレージでは、トランザクションまたは同等のアトミックな条件付き状態遷移を使用してください。
5. サーバーが保持するスナップショットを読み込み、`state.getInterruptions()` で保留中のアイテムを取得し、実行を再開する前に、それらのアイテムに対してのみ `state.approve()` または `state.reject()` を適用します。

### 保留中のタスクのバージョン管理

<Aside>
  これは主に、エージェントに変更を加えながら、シリアライズされた状態を
  長期間保存しようとしている場合に適用されます。
</Aside>

承認リクエストに時間がかかり、エージェントの定義を適切にバージョン管理するか、Agents SDK のバージョンを上げる予定がある場合は、現時点では、パッケージエイリアスを使って Agents SDK の 2 つのバージョンを並行してインストールし、独自の分岐ロジックを実装することをお勧めします。

具体的には、独自のコードにバージョン番号を付け、シリアライズされた状態と一緒に保存して、デシリアライズ時に正しいバージョンのコードを使用するように振り分けます。
