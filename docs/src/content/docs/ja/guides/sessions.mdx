セッションは、Agents SDK に **永続的なメモリ層** を提供します。`Session` インターフェースを実装した任意のオブジェクトを `Runner.run` に渡すだけで、残りの処理は SDK が行います。セッションがある場合、ランナーは次の処理を自動的に行います。

1. 以前に保存された会話項目を取得し、次のターンの入力の先頭に追加します。
2. 各実行の完了後に、新しいユーザー入力とアシスタントの出力を永続化します。
3. 新しいユーザーテキストでランナーを呼び出す場合も、中断された `RunState` から再開する場合も、以降のターンでセッションを利用できる状態に保ちます。

これにより、`toInputList()` を手動で呼び出したり、ターン間で履歴をつなぎ合わせたりする必要がなくなります。TypeScript SDK には、Conversations API 向けの `OpenAIConversationsSession` と、ローカル開発向けの `MemorySession` という 2 つの実装が付属しています。どちらも `Session` インターフェースを共有しているため、独自のストレージバックエンドに差し替えられます。Conversations API 以外の実装の参考として、`examples/memory/` にあるセッションバックエンドのコード例（Prisma、ファイルベースなど）をご覧ください。OpenAI Responses モデルを使用する場合は、任意のセッションを `OpenAIResponsesCompactionSession` でラップすると、[`responses.compact`](https://platform.openai.com/docs/api-reference/responses/compact) を通じて保存済みの会話履歴を自動的に縮小できます。

> ヒント：このページの `OpenAIConversationsSession` のコード例を実行するには、SDK が Conversations API を呼び出せるように、環境変数 `OPENAI_API_KEY` を設定してください（またはセッションの構築時に `apiKey` を指定してください）。

クライアント側のメモリ管理を SDK に任せたい場合は、セッションを使用してください。`conversationId` または `previousResponseId` を使って、OpenAI のサーバー管理の状態をすでに利用している場合、通常は同じ会話履歴に対してセッションを併用する必要はありません。

## セッションの基本動作

### ランナーによるセッションの使用方法

- **各実行の前に** セッション履歴を取得し、新しいターンの入力とマージして、結合したリストをエージェントに渡します。
- **非ストリーミング実行の後に** `session.addItems()` を 1 回呼び出して、最新のターンの元のユーザー入力とモデル出力の両方を永続化します。
- **ストリーミング実行では** 最初にユーザー入力を書き込み、ターンが完了するとストリーミングされた出力を追加します。
- **`RunResult.state` から再開する場合**（承認やその他の中断への対応）は、同じ `session` を渡し続けてください。入力を再準備することなく、再開されたターンがメモリに追加されます。

出力ガードレールが、最終出力となる関数ツールの実行結果を拒否した場合、ランナーは拒否された元の実行結果を新しいセッション履歴に追加しません。認識できた関数呼び出しと実行結果のペアに対しては、リプレイしても安全なプレースホルダーを永続化します。また、現在のレスポンスの末尾部分の帰属が曖昧な場合、帰属先を証明できない出力を保存するのではなく、その部分を省略します。この保護によって、外部ツールの副作用が取り消されたり、アプリケーションがセッションパイプラインの外部に保存したデータが消去されたりすることはありません。

カスタムセッションでは、保持ポリシーの適用、暗号化の追加、永続化前の各会話ターンへのメタデータの付与が可能です。

### カスタム永続化のアトミック性と冪等性の確保

履歴の更新と操作識別子の記録をアトミックに行えるバックエンドでは、オプションの `SessionHistoryTransactionAwareSession` インターフェースを実装してください。その `applyHistoryTransaction(...)` メソッドは、固定の `operationId` と、次の 2 つの形式のいずれかのトランザクションを受け取ります。

- `append_items` は、履歴項目のグループを追加します。
- `replace_suffix` は、現在保存されている履歴の末尾部分が想定どおりの内容と一致している場合に限り、その部分を置き換えます。

操作識別子と履歴の変更は、同じバックエンドトランザクションで永続化してください。同じ操作識別子で同じトランザクションを繰り返した場合、変更を二重に適用せずに成功する必要があります。異なる内容で識別子を再利用した場合や、想定していた履歴の末尾部分が変更された後に `replace_suffix` を適用した場合は、履歴を変更せずに失敗する必要があります。これにより、ランナーは再試行や再開可能な出力ガードレールフローにまたがって、永続化された出力の整合性を安全に保てます。

`MemorySession` は、リファレンスとしてこの契約を実装しています。既存の `Session` 実装はこのインターフェースがなくても引き続き有効ですが、トランザクション対応の永続化処理は利用しません。

### 実行コンテキストによるカスタムセッションのスコープ設定

カスタムセッションがストレージのルーティングやメタデータのためにアクティブな `RunContext` を必要とする場合は、`RunContextAwareSession<TContext>` を実装し、`acceptsRunContext` を `true` に設定してください。ランナーは、ストリーミング中の永続化や再開された実行を含め、実行中のすべての履歴操作に同じコンテキストインスタンスを渡します。`Session` のみを実装するセッションは既存のメソッドシグネチャを維持し、追加の引数なしで呼び出されます。

### 履歴と新しい項目のマージ方法の制御

`AgentInputItem` の配列を実行の入力として渡す場合は、保存済みの履歴と決定論的にマージするための `sessionInputCallback` を指定してください。ランナーは既存の履歴を読み込み、 **モデルの呼び出し前に** コールバックを呼び出し、返された配列をそのターンの完全な入力としてモデルに渡します。このフックは、古い項目の削除、ツールの実行結果の重複排除、モデルに見せたいコンテキストだけを強調する場合に最適です。

<Code

文字列入力の場合はランナーが履歴を自動的にマージするため、コールバックは省略できます。コールバックは、ターンの入力がすでに項目の配列になっている場合にのみ実行されます。

`conversationId` または `previousResponseId` も使用している場合は、現在のターンの新しい項目を少なくとも 1 つ、コールバックの戻り値に含めてください。これらのサーバー管理の API は、現在のターンの差分に依存します。コールバックが新しい項目をすべて削除した場合、SDK は空の差分を送信する代わりに、元の新しい入力を復元して警告をログに記録します。

## 再開可能な実行

### 承認と再開可能な実行の処理

Human in the loop (人間の介入) のフローでは、承認を待つために実行を一時停止することがよくあります。

<Code
  lang="typescript"
  code={resumableRunExample}
  title="同じセッションでの実行の再開"
/>

以前の `RunState` から再開すると、新しいターンが同じメモリレコードに追加され、単一の会話履歴が維持されます。人間の介入（HITL）におけるほとんどの承認チェックポイントでは、`RunState` を介して中断と再開が行われ、その間もセッションが完全な会話履歴を保持します。

承認された関数ツールの実行結果が最終出力になり得る場合、出力ガードレールはより厳格な境界を設けます。現在の `RunState` スキーマは、生成項目が現在のレスポンスに帰属することを SDK が証明できる場合に、その正確な帰属情報を記録します。これにより、サポートされている出力を伴う承認チェックポイントでは、セッション履歴を保持したまま再開できます。SDK は、モデル、ツール、セッションに対してさらに副作用を発生させる前に、その帰属情報を検証します。古いスナップショットや、帰属情報が欠落している、不正である、または曖昧であるチェックポイントでは、引き続き安全側に倒して処理を拒否します。SDK がこの状態を報告した場合は、安全な入力から新しい実行を開始してください。元の項目をリプレイして回避しようとしないでください。

## 応用：履歴の圧縮

### OpenAI Responses の履歴の自動圧縮

`OpenAIResponsesCompactionSession` は任意の `Session` をラップし、OpenAI Responses API を使用して、保存済みの長い履歴を、それと同等の内容を持つ、より短い会話項目のリストに置き換えます。各ターンの永続化後、ランナーは最新の `responseId` を `runCompaction` に渡します。判断用フックが true を返すと、`runCompaction` が `responses.compact` を呼び出します。`compactionMode` に応じて、リクエストは最新の Responses API チェーン、またはセッションの現在の項目から構築されます。デフォルトのトリガーは、ユーザー以外の項目が 10 件以上蓄積すると圧縮を行います。トークン数やカスタムのヒューリスティクスに基づいて判断するには、`shouldTriggerCompaction` を上書きしてください。圧縮処理が返った後、デコレーターは基になるセッションをクリアし、削減された項目リストで書き直します。そのため、異なるサーバー管理の履歴フローを使用する `OpenAIConversationsSession` との併用は避けてください。

<Code
  lang="typescript"
  code={responsesCompactionSession}
  title="OpenAIResponsesCompactionSession によるセッションのラップ"
/>

`OpenAIResponsesCompactionSession` のコンストラクターオプション：

| オプション | 型 | 備考 |
| --- | --- | --- |
| `client` | `OpenAI` | `responses.compact` に使用する OpenAI クライアントです。 |
| `underlyingSession` | `Session` | 圧縮された項目でクリア・書き直しを行う、基になるセッションストアです。デフォルトはデモ用のインメモリセッションです。`OpenAIConversationsSession` は指定できません。 |
| `model` | `OpenAI.ResponsesModel` | 圧縮リクエストに使用するモデルです。デフォルトは SDK の現在のデフォルトの OpenAI モデルです。 |
| `compactionMode` | `'auto' \| 'previous_response_id' \| 'input'` | 圧縮にサーバーのレスポンスチェーンを使用するか、ローカルの入力項目を使用するかを制御します。 |
| `shouldTriggerCompaction` | `(context) => boolean \| Promise<boolean>` | `responseId`、`compactionMode`、候補項目、現在のセッション項目に基づくカスタムトリガーフックです。 |

`compactionMode: 'previous_response_id'` は、Responses API のレスポンス ID でターンをすでにつなげている場合に便利です。`compactionMode: 'input'` は、代わりに現在のセッション項目から圧縮リクエストを再構築します。これは、レスポンスチェーンが利用できない場合や、基になるセッションの内容を信頼できる情報源としたい場合に役立ちます。

`runCompaction(args)` のオプション：

| オプション | 型 | 備考 |
| --- | --- | --- |
| `responseId` | `string` | `previous_response_id` モードで使用する、最新の Responses API レスポンス ID です。 |
| `compactionMode` | `'auto' \| 'previous_response_id' \| 'input'` | 設定済みのモードを呼び出しごとに上書きするための省略可能なオプションです。 |
| `store` | `boolean` | 直前の実行でサーバーの状態を保存したかどうかを示します。 |
| `force` | `boolean` | `shouldTriggerCompaction` を無視して、直ちに圧縮します。 |

`OpenAIResponsesCompactionSession` は、同じラッパーインスタンスを通じて発行された変更操作を直列化します。`runCompaction()`、`addItems()`、`popItem()`、`clearSession()` の呼び出しは呼び出し順に実行され、操作が拒否された後もキューの処理は続きます。そのため、後続のラッパー経由の変更操作が、置換やロールバックに割り込むことはありません。置換またはロールバックが成功すると、ラッパーのキャッシュ済み履歴は基になるセッションと整合した状態に保たれます。置換と復元の両方が失敗した場合は、処理を続ける前に基になるセッションを復旧してください。この順序保証は、別のラッパーインスタンスや `underlyingSession` の直接変更とは連携しません。それらのアクセス経路の調整は、アプリケーションで行ってください。

自動圧縮では、読み取った履歴スナップショットの所有権を、その実行が引き続き持っているかどうかも検証します。自動圧縮が始まる前に別の操作がラッパーの履歴を変更した場合、SDK は新しい履歴を保持し、その圧縮処理をスキップします。更新された履歴は、後続の実行や明示的な `runCompaction()` の呼び出しで圧縮できます。

#### 低レイテンシーのストリーミングのための手動圧縮

圧縮は基になるセッションをクリアして書き直すため、SDK は圧縮が終わるまでストリーミング実行の完了を待ちます。圧縮処理が重い場合、最後の出力トークンの後も `result.completed` が数秒間保留状態になることがあります。ストリーミングのレイテンシーを低く抑えたり、ターンの切り替えを速めたりするには、自動圧縮を無効にして、ターン間（またはアイドル時間中）に自分で `runCompaction` を呼び出してください。
